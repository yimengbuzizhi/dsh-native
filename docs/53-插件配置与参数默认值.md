## 一、这一轮补的是什么

DSH 插件契约（`docs/04`）：

```js
export const Config = z.object({ city: z.string().default('Shanghai') })
export function apply(ctx, config) {
  ctx.tools.register(defineTool({
    name: 'weather_now',
    parameters: z.object({ city: z.string().default('Shanghai') }),
    execute: (args) => { … }
  }))
}
```

M29 之前只处理 `parameters`。这一轮把同一套 schemastery 能力用到两个新地方：

| 能力 | M29 之前 | M30 |
|---|---|---|
| `Config` 导出 | 不读、不落盘，`apply` 永远收到 `{}` | 读出来转 JSON Schema，落 `plugins.json` |
| 配置默认值 | 无 | 按 schema 递归补；`apply` 收到合并后的配置 |
| 用户改配置 | 无入口 | 插件详情「配置（Config）」+ 调试参数 |
| 工具参数 `default` | 不写进 schema（怕骗模型） | 显式 default 写进 schema，执行前宿主补 |
| 工具参数校验 | 不校验 | 必填 / 类型 / enum / 嵌套属性，错误原文给模型 |
| 覆盖安装 | 配置丢 | 同 id 且 schema 认识的键保留 |

## 二、实现

### 1. JS 侧：只负责把 `Config` 序列化出来

`PluginModule` 的 `EXPORTS_APPLY` 在调用 `apply` 前：

```js
if (__e.Config !== undefined && __e.Config !== null) {
  __dsh.configSchema = __dshSchema(__e.Config);   // schemastery → {uid,refs} 图；简写/JSON Schema → 原样
  if (__dsh.configSchema === null) __dsh.configError = 'Config 序列化不出来…';
}
__e.apply(__ctx, __dshConfigRaw);                 // 宿主已经合并好默认值
```

`moduleScript` 多接一个 `configJson` 参数，用 `JSON.parse(<带引号的 JSON>)` 注入成 `__dshConfigRaw`，
不拼裸对象字面量（避免插件配置里的字符串把 JS 语法弄坏）。`dryRunScript` / `invokeScript`
都把这个参数透传下去。

**不在 JS 里算默认值**：默认值只在 Kotlin 的 `PluginSchema.withDefaults` 里算一份；
JS 只把 schema 交出来。这样不会出现「JS 和 Kotlin 两套默认值语义」。

### 2. Kotlin：`PluginSchema.withDefaults` 照 schemastery `Schema.resolve`

用真实 `@deepseek-ai/schemastery@3.18.2` 在 node 里验证过语义（`m30-probe.cjs`，不进仓库）：

```
Config = z.object({
  city: z.string().default('Shanghai'),
  verbose: z.boolean().default(false),
  limit: z.number().default(3),
  nested: z.object({ flag: z.boolean().default(true) }),
  list: z.array(z.string()).default(['a']),
})
Config({}) => {"city":"Shanghai","verbose":false,"limit":3,"nested":{"flag":true},"list":["a"]}
Config({city:'Beijing'}) => {…,"city":"Beijing",…}
```

`withDefaults` 的规则：

- 标量缺省且有 `default` → 用 default；没有 → **不出现**（插件读到 undefined，和 schemastery 一致）；
- object 缺省 → `{}`，再递归补内层；
- array 缺省 → `[]`；
- 已有对象/数组只补缺项，不覆盖用户/模型给的值；
- 只认 `properties` / `items` / `default`，不处理 `anyOf/oneOf`，不做严格校验。

`schemastery → JSON Schema` 转换器（`SchemasterySchema`）新增：

- 标量/枚举的显式 `default` 写进 schema（`"default":"Shanghai"` 这种）；
- **隐式空对象/空数组默认不写**：`z.object` 的 `meta.default={}`、`z.array` 的 `meta.default=[]`
  是构造器行为，不是作者显式配置，写进模型参数只会让 schema 变吵；
- 显式 `.default({a:1})` / `.default(['a'])` 非空，照写；
- 顺手给 array / dict 补上 `description`（M29 漏了）。

### 3. 落盘：`PluginRecord` 多三个字段

```kotlin
val configSchema: String? = null,   // 归一化后的 JSON Schema 文本
val config: String = "{}",          // 用户改过的（稀疏）配置，只存显式设的键
val configDefaults: String = "{}",  // schema 算出的全默认配置（给「恢复默认」/展示）
val configError: String? = null,    // Config 序列化失败原因，不影响工具注册
```

`files/plugins.json` 只在非默认时写 `config` / `configDefaults`，旧记录没有这些键也能读。

**两遍试运行**（`PluginStore.dryRunForConfig`）：

1. 先用 `{}` 跑一次，拿到 `Config` schema；
2. 按「默认值 + 用户配置」算出 effective config，再跑一次 `apply`。
   这样「按 config 决定注册什么工具」的插件，试运行/重载看到的就是用户实际行为。

安装/覆盖安装时：同 id 的老配置如果还能对上新的 Config schema 就保留（只留 schema 认识的键），
不因为重装丢配置。`reload` 同理。

### 4. 运行时：先补默认值，再校验，再执行

`PluginToolRuntime` 的 `Binding` 多一个 `configJson`（`effectiveText(configSchema, config)`）；
每次工具调用：

```kotlin
val filled = PluginSchema.withDefaults(binding.schema, args)   // 补默认值
PluginSchema.validate(binding.schema, filled)?.let { … }       // 缺必填/类型错/enum 外 → 直接回错误
run(binding, filled.toString(), timeout)                       // apply 收到合并后的配置
```

`validate` 只查 `required` / `type` / `enum` / `properties` / `items`：
不拒绝多给的键（JSON Schema 默认 `additionalProperties:true`），不为了 corner case 把合法调用拒掉。
错误文案带路径，例如 `opts.n 类型不对：要 integer，实际是 number`。

### 5. UI：插件详情里的「配置（Config）」

`PluginsScreen` 新增 `ConfigSection`：

- 每个配置项一行：描述（没有就键名）+ 键名 + 当前值（未设置显示「（未设置）」）；
- 点开按类型出控件：boolean → Switch；enum → 单选；number → 数字键盘输入；string → 文本框；
  object/array → JSON 文本框（高级兜底）；
- 「恢复默认」= 清空用户值；保存时把合并后的整份配置写回（`PluginStore.setConfig` 白名单校验键）；
- `Config` 没认出来时显示 `configError`。

## 四、边界（别在群里夸口）

- **配置编辑 UI 没截图验收**：只过了编译和 store 逻辑；布局/输入法/弹层叠放要在解锁后看真机。
- **配置值只校验键名，不校验类型**：手改 JSON 里 `city: 123` 也能存进去；工具参数有最小校验，
  配置值等下一轮和「配置 schema 严格校验」一起做。
- **schemastery 仍不是完整实现**：没有 validator；`Schema.resolve` 的报错文本/transform 语义不同。
- **默认值只处理 `properties`/`items`/`default`**：`anyOf`/`oneOf` 里的默认值不补；
  配置如果直接用 JSON Schema（不是 `z.object`），显式 default 能补，复杂组合不保证。
- **`apply` 异步仍未等**、**每次调用重跑模块**：~~与 docs/50/52 相同，没变。~~ **M31 已补异步 apply**，见 `docs/54`；
  运行时仍是每次调用重跑模块。
- **配置 schema 是 `Config` 导出**；manifest 里的 `config.schema`（docs/04 §6.1）**M32 已接**，见 `docs/56`。
- 每次保存配置写的是「合并后的整份配置」，不是稀疏 diff；以后做「恢复默认」按 schema 重算，
  不会留下旧默认值（但用户改过的键会被当成显式值）。
