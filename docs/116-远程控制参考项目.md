## 二、关键技术点（我们一定会撞上的）

1. **DSH 的 `/api` 有双重门禁**：Host 必须是回环地址 + 要带签名 cookie，手机直连会 403/401（c6huli 的 README 明说）。
   → 现有两种解法：**PC 侧反代注入 cookie**（c6huli 用 Caddy），或**装一个 DSH 插件自己开通道**（dsh-link）。
2. **长连接会半开**：蜂窝/异地时 SSE 断而不报，需要看门狗 + 自动重连 + 结果补投（c6huli 有事件流看门狗，DSH-Pal 有连接管理）。
3. **通知**：手机要能收到「这轮跑完了/在等审批」，靠旁听事件流或插件回投（dsh-link 只回投手机发起的那一轮）。
4. **版本差异**：DSH 0.1.x → 0.2.x 方法名变过；把差异关在主机侧桥里，App 只讲一种协议（c6huli 的设计）。

## 三、用户决定（2026-11-13）：用鲸歌自己的页面，不要 DSH 的网页

原计划里的「WebView 打开 DSH 工作台」**作废**。用户明确：

> 远程连接电脑的 DSH，不要原生 DSH 的页面，保留我们自己的页面，把 DSH 那些东西用我们自己的页面显示出来。

也就是说：**DSH 只当远程执行后端**，界面全用鲸歌自己的 Compose 页面。

| 要显示的东西 | 来源 | 落到鲸歌哪里 |
|---|---|---|
| 会话列表 / 工作区 | DSH `session.list` / `workspace.list` | 侧边栏 / 工作区切换 |
| 聊天消息、流式输出 | DSH SSE 事件流 | 现有 `ChatScreen` 气泡 |
| 工具调用、结果 | 事件流里的 tool 事件 | 现有工具卡（折叠行） |
| 审批 / 提问 | 事件流 + 应答 RPC | 现有审批条 / 提问弹窗 |
| 模型、用量 | 事件流 / 会话元数据 | 输入栏模型 pill、上下文环 |
| 文件、下载 | DSH 文件 RPC | 工作区页 |

**方案定为 A（c6huli 式原生客户端）**，不是 B（DSH-Pal 的 WebView）。B 只留作应急参考。

### PC 侧怎么接（**不许改 DSH**）

用户 2026-11-13 追加：**电脑上的 DSH 不能做任何「关于鲸歌」的适配**——不装我们的插件、不改它的配置/代码。
所以「自家 DSH 插件」这条作废，只剩**在 DSH 外面借一条通道**：

| 通道 | 要动什么 | 优点 | 缺点 |
|---|---|---|---|
| **A. SSH 隧道**（推荐） | PC 开系统自带 OpenSSH Server；App 内置 SSH 客户端（我们已经有 jsch） | 不碰 DSH；`Host` 变成 127.0.0.1 可过回环门禁；cookie 用户从浏览器复制一次 | 要开 SSH、要一次性 cookie；手机端要跑隧道 |
| B. 独立小代理 | PC 上跑一个不隶属 DSH 的小程序（读 `~/.dsh/.credentials.yaml` 自动签 cookie） | 手机不用隧道 | 要在 PC 装/跑东西；等于又做了一层适配 |
| C. 反代（Caddy） | 同 B，配置更重 | 现成方案（c6huli） | 同上，且要手动签 cookie |
| D. DSH 自带无头/ACP 模式 | 无（若它本身能监听端口） | 最干净 | 未实测：`dsh-acp-app` / `dsh-headless` 是否支持 TCP，要先验证 |

**结论：先实测 D（如果能用最省事）；不行就走 A（SSH 隧道 + 一次性 cookie）。**

### 连接方式：按需连 + 任务时后台保护（2026-11-13 用户定）

用户原话：**「就像无线调试一样，用的时候连上，没必要做成那种一直保持连接的东西。」**
补充：**「后台保护还是要有的。」**

所以是「按需连」+「跑任务时保命」，两件事分开：

| 状态 | 连接 | 前台服务 / 通知 |
|---|---|---|
| 空闲（没连、没任务） | 不连 | 没有，不占后台 |
| 连着但空转 | 连 | 没有（可选：只在页面打开时保持） |
| **正在跑任务** | 保持 | **有**：常驻通知「鲸歌正在执行远程任务」，锁屏/切后台不杀，通知里可停止 |
| 任务完成 / 停止 / 断开 | 断开释放 | 服务退出，通知消失 |

- 复用现有的 `TurnKeepAliveService`（本地回合已经在用，`FOREGROUND_SERVICE_TYPE_SPECIAL_USE` + 常驻通知），远程回合接同一套。
- **不做**：开机自连、后台无限重连、无任务时长期挂连接。
- 断了要显式提示「连接已断开 · 点此重连」，不假装还在跑。

### 鉴权：DSH 网页端要一个签名 cookie（实测）

用户提醒得对：DSH 网页端不是打开就能用，要鉴权。本机实测：

- 直接 `GET http://127.0.0.1:63167/` 和 `/api` 都返回 **401**（没有 cookie 时）。
- 凭证在 `C:\Users\<用户>\.dsh\.credentials.yaml`，记录名 **`client-connection/browser-session`**，
  payload 里是一个 **`secret`**（浏览器 cookie 由它签名；c6huli 的文档也点名了这个字段）。
- 也就是说：手机要拿到「由这个 secret 签出来的 cookie」，否则连本机都过不去。

三条路：

1. **小助手自动签**：PC 上的小助手读同一个 `.credentials.yaml` 的 secret，自己生成 cookie 再转发。
   （不把 secret 传给手机，也不进仓库。）
2. **用户从浏览器复制一次**：电脑浏览器打开 DSH 后，从开发者工具复制 cookie，粘进手机。
3. **`dsh web` 启动时给的地址**：命令行启动可能会打印带 token 的地址（未实测，下一棒可验证）。

**安全**：secret 只在电脑本机用；手机只存「会话 cookie/token」，且只在你填过的地址上用。

### 部署这件事交给用户的 AI（2026-11-13 用户定）

用户原话：**「用户可以让 AI 弄啊，只要这个改动对平常使用影响不大。」**

所以 PC 侧允许一次性配置，前提是**日常无感**：

- **DSH 桌面版照常用**（双击图标、平时怎么用还怎么用），不要求用户改启动方式。
- **需要远程时才起一个「小助手」**（双击；不开就一直不跑），它负责：找到 DSH 当前端口 → 在局域网/Tailscale 上开一个带鉴权的转发 → 显示二维码/短码。
- 手机端只做：扫码或填「地址 + 令牌」→ 测试连接 → 按需连。
- 关掉小助手 = 远程不可用，本地一切照旧。

交付物（我们这边出）：

1. **给 AI 的部署契约**：一份 Markdown，写清要做什么、怎么验证、哪些步骤必须用户本人点（参考 DSH-Pal 的 `docs/AI-部署契约.md` 形式）。
2. **手机端连接页**：地址/令牌/扫码、连接状态、测试连接、断开。
3. 契约里同时给两条 PC 方案：`dsh web --host … --trusted-host …`（命令行用户）和小助手转发（桌面版用户）。

### 鲸歌这边的架构落点

- 新增「远程引擎」后端：实现和本地引擎同一套接口（发消息 / 收事件 / 停止 / 审批），聊天页不感知是本地还是远程。
- 界面复用现有 `ChatScreen` / 会话页 / 工具卡，只是数据来源换成远程事件映射。
- 这样「本地 / 远程」就是引擎切换，正好验证「引擎可替换」。

## 四、规矩

- 抄代码/抄思路可以，**必须看 license 并保留版权声明**：c6huli、dsh-link 是 MIT；DSH-Pal 是 Apache-2.0，但**鲸鱼娘素材是 CC BY-NC-SA，不能进我们的仓库**。
- 不引入对方的 APK 签名、密钥、cookie 示例；不把配对令牌/证书写进仓库。
- 先把「能连、能发、能收」跑通，再谈体验；每步真机验证。
- 远程连接的最终形态仍然是「鲸歌里的一个远程引擎插件」：地址 + 令牌 + 自动重连，与本地引擎可切换。
