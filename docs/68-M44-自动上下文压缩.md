## 二、上游依据（宁抄勿研）

`D:\dsh021\node_modules\@deepseek-ai\dsh-compaction-basic\lib\index.js`：

1. **触发公式**（`resolveCompactSpec()`，第 124–140 行）：

**没搬**：`agent/request-error` 的溢出恢复（`CONTEXT_WINDOW_EXCEEDED` → 最大压缩 + 重试一次）、

### 3.1 触发与保留

- 压力值 = **会话面消息**的启发式令牌和（不含 system / 工具清单 / 运行时上下文）：
  上游量的是 session surface，system 与工具本来也压不掉；真溢出由下一轮的溢出恢复兜底；
- `W` = 设置里的窗口；`O` = 本轮 `config.maxTokens`；`B = min(65536, W/8)`（唯一偏差，见 §四）；
- 选区复用 M43 的 `selectRange()`：从最新往回累计到 `retainTokens`，边界不切工具调用/结果对；
- 摘要失败/不比原文小/区间变了：写 `compaction/end{error}`，**不改会话面**，本轮照常继续
  （与上游「监听器只警告、不打断 turn」一致）；
- 取消（用户停止/切会话）：`NonCancellable` 里补一条 `compaction/end{error:"Compaction cancelled."}` 再抛。

## 四、与上游的差别（全部有意，写在这里避免下轮重复研究）

1. **headroom 缩放**：`B = min(65536, W/8)`。手机上会有 8k/16k 窗口的自定义模型，
   固定 64k 余量会让 `W−O−B ≤ 0`、自动压缩永远不成立；`W ≥ 524288` 时与上游完全一致
   （flash 的 1048576 就是这一档，阈值 727040）；
2. **压力值是启发式**（4 字符/令牌），不是真实 token meter；比真实值偏小，触发会偏晚。
   下一轮若接溢出恢复，真实溢出会兜底；
3. **窗口来自设置**，不是适配器元数据：原生没有 `/models` 拉取链路；默认表只覆盖
   `deepseek-flash` / `deepseek-chat` / `deepseek-reasoner`，其它模型默认 0（关闭），
   用户可在模型配置页自己填；
4. **不做 `compactionRetries` 循环**：压一次后若仍超阈值，下一轮 step 自然再压
   （保留段已变小，重复压的收益很低）；也没有「still above threshold」抛错；
5. **不做工具结果修剪 / 图片卸载**：因此自动路径也不会写 `compaction/prune` / `image/offload`；
6. **子代理共用同一个引擎**（也注入了 `contextWindow`），但没有单独真机验证。
