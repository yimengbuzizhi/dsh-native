## 一、一句话方案

用一个 **Kotlin 单进程应用**替换「Java 壳 + Node 引擎 + WebView」三件套：
Compose 画界面，Kotlin 跑 agent，工具直连 Android API。
行为等价用**双引擎对拍**证明，不靠人工目测。

## 二、总体架构

```
┌──────────────────────────────────────────────────┐
│ :app  (单进程；聊天运行时挂前台服务)               │
│                                                  │
│  :ui:*        Compose 界面                        │
│    chat / console / settings / theme              │
│         │ StateFlow                              │
│  ChatRuntimeHolder { MAIN, FLOATING }  ← 借鉴方案 │
│         │                                        │
│  :core:agent  Agent 循环                          │
│    ├─ :core:prompt     提示词组装（逐字节）        │
│    ├─ :core:llm        Provider + SSE 流          │
│    ├─ :core:tools      30 个工具 + 权限档位        │
│    ├─ :core:session    会话读写 (v0~v4, zstd)      │
│    └─ :core:store      SQLite / 文件              │
│         │                                        │
│  :plugins:kernel     插件内核（服务容器/生命周期）  │
│  :plugins:jsbridge   QuickJS + ctx 代理 + 权限门    │
│  :thirdparty:terminal OperitTerminalCore (LGPL)   │
│  :thirdparty:shower   Shower 虚拟屏（替换 vscreen）│
│  :device:*           shizuku / a11y / overlay /    │
│                      browser                      │
└──────────────────────────────────────────────────┘
        │ 可选：远程引擎模式（预留，不实现）
        └─ 远程 WS（未来多端复用，非本期）
```

**关键取舍**：不再有「本机回环 HTTP 服务」。旧版那套 `127.0.0.1:3080 + token + adb forward`
全部消失；内部调用是函数调用，不是 HTTP。

## 三、Gradle 模块划分

| 模块 | 职责 | 备注 |
|---|---|---|
| `:app` | 入口、导航、DI、前台服务、通知 | 唯一 application 模块 |
| `:core:model` | Session/Turn/Message/ToolDef/Content 等纯数据 | 无 Android 依赖，可单测 |
| `:core:protocol` | 请求/响应/SSE 事件解析、错误码 | 与上游 JSON 对齐 |
| `:core:prompt` | 系统提示词、工具描述拼装 | 契约 #1，逐字节 |
| `:core:llm` | Provider 接口 + DeepSeek 实现 + 重试 | 先做 1 个，其余按需 |
| `:core:agent` | 循环、工具调度、压缩、子会话、goal/schedule | 核心 |
| `:core:session` | v0→v4 格式、zstd、检查点、回收站、修复 | 契约 #3/#6 |
| `:core:tools` | 工具注册 + 30 个实现 + **权限档位解析** | 契约 #2/#4；三层照搬 Operit |
| `:core:fs` | 文件读写、原子写、搜索（glob/grep） | 复用系统 API |
| `:core:shell` | 进程执行、超时、输出截断 | ProcessBuilder |
| `:core:markdown-stream` | 流式 Markdown 解析与渲染 | **移植 Operit 的 KMP 渲染器** |
| `:plugins:kernel` | 插件内核：`PluginContext`、服务注册表、生命周期、依赖、配置 schema、启用禁用 | **本方案核心**，见 `04` |
| `:plugins:jsbridge` | QuickJS 宿主 + `ctx` 代理 + 权限门 + 模块 shim | 第三方插件入口 |
| `:plugins:compat` | DSH 兼容运行时（cordis / defineTool / schemastery / node:fs 子集） | 让原有插件零改动跑 |
| `:plugins:api` | 插件清单 / Profile / 安装器 | 本地导入、启用禁用、配置 UI |
| `:thirdparty:terminal` | 终端核心（多会话、AIDL/Flows） | **OperitTerminalCore 子模块（LGPL）** |
| `:thirdparty:shower` | 虚拟屏（server + 输入注入 + 截图 + 视频） | **showerclient 模块（LGPL）**，替换 vscreen |
| `:device:*` | Shizuku/无障碍/悬浮窗/浏览器 | 复制 Operit 对应实现 |
| `:parity` | 对拍台（JVM test + 录制回放） | 见 02 文档 |
| `:bench` | 启动耗时、内存、体积基线 | 可选 |

纪律：`core:*` 不依赖 Android（除 `:core:fs` 等必要处），保证能在 JVM 上跑对拍。
`thirdparty:*` 与 `plugins:runtime` 保持**独立、不改源码**，便于许可证隔离与升级。

## 五、五个硬难点与解法（v2）

### 1. 终端 PTY —— ✅ 已由 Operit 解决

Android 的 Java API 没有 `openpty`，原本要 JNI 或 helper。
**v2：直接引入 [OperitTerminalCore](https://github.com/AAswordman/OperitTerminalCore)**（LGPL-3.0）：
`TerminalManager`（单例，Kotlin Flows）+ `TerminalService`（AIDL，跨进程，界面关掉会话不死）+ 多会话。
唯一代价：许可证（见 `03` §四）与锁 commit（不跟 main）。

### 2. 会话格式 v0→v4 —— 只能自己搬

旧版有 5 代格式（`dsh-session-format-v0-to-v1` … `v3-to-v4`）。新 App 必须：
- 读：全部 5 代 → 内存模型
- 写：只写 v4（与旧版一致）
- 校验：旧版能读新写的文件

对拍：拿设备上 41 条真实会话做回归样本（只读，不修改）。

### 3. 流式渲染性能 —— ✅ 已由 Operit 解决

**v2：移植其 KMP 流式 Markdown 渲染器**：`StreamKmpGraph` 状态机（O(n)、零回溯）+
`StreamPlugin` 语法插件 + 两阶段（块级/内联）解析 + `BatchNodeUpdater` 批量重组。
我们要做的只是把它接到自己的消息模型上，并把样式换成我们的主题。

### 4. 后台保活 —— 架构照搬 Operit

旧版靠 Node 子进程 + 前台服务。**v2**：前台服务持有 `ChatRuntimeHolder`，
内含 `MAIN` / `FLOATING` 两个 `ChatServiceCore`；`ViewModel` 只做 UI、不持有运行时。
好处：切后台不断、主界面与悬浮窗可同时停在不同会话、loading 不串线。
（Android 14+ 前台服务类型按新规声明，不用 targetSdk 28 的老办法。）

### 5. 数据迁移 —— 仍然要自己解决

旧版数据在 `/data/data/com.deepseek.harness/files/payload/dshhome`（应用私有目录）。
新包名不同 → **无法直接读**。三条路：
- A. 首次启动引导用户从 `/sdcard/DeepSeekHarness` 导入（旧版会把备份放这）
- B. 用 `MANAGE_EXTERNAL_STORAGE` + root 读旧私有目录（重）
- C. 提供「导出/导入」桥：旧版加一个导出按钮（需要另一条线配合）

建议 A + C，B 仅对 root 用户提供。

### 6. 虚拟屏 —— ✅ 已由 Operit 解决（v2.1 新增）

我们自研的 `vscreen`（`app_process` 核心 + 8998 桥 + 预览窗 + `BUILD` 指纹机制）**退役**，
改用 `showerclient`：

- 内置 `shower-server.jar`，运行时自动落盘并用 `app_process` 拉起；
- 客户端只需：实现 `ShellRunner`（走 Shizuku/root）→ 注册 `SHOWER_BINDER_READY` 广播接收器
  → `ShowerServerManager.ensureServerStarted()` → `ShowerController.ensureDisplay(w,h,dpi,bitrate)`；
- 输入注入 `touchDown/Move/Up`、`key`，截图 `requestScreenshot()`；
- 自带 `ShowerVideoRenderer` + `ShowerSurfaceView`（视频解码渲染，我们不用再写预览窗）。

附带收益：旧版「虚拟屏核心指纹 `vs114-…` 必须跟 BUILD 同步」这类坑直接消失。

## 七、范围与取舍

| 做 | 不做（本期） |
|---|---|
| 聊天、会话、工具、设备能力、控制台、主题 | ToolPkg 的 Compose DSL UI（后置） |
| 单 provider 深度做好（DeepSeek） | 5 个 provider 全量（按需再加） |
| 本地单机 | 远程引擎 / 多端同步（架构预留） |
| 追 DSH stable 上游（季度） | 追 rc |
| QuickJS + ToolPkg（子集）插件 | 兼容 DSH 旧 JS 插件（明确不支持） |

**插件机制 v2.2 定案**：**内核级插件**（`04-插件体系设计.md`）——
cordis 风格 API（`name` / `inject` / `Config` / `apply(ctx, config)`）+ ToolPkg 包格式 + QuickJS 运行时。
三层含义：

1. **内核是插件容器**：`PluginContext` + 服务注册表（tools / llm / session / prompt / ui / hooks…）；
2. **我们自己的功能也是插件**：聊天、工具、provider、设置页全部走 `apply()`，可启用/禁用/替换；
3. **第三方插件是 JS**：跑在 QuickJS 里，用同一套 `ctx` API，按 manifest 声明权限。

与 DSH 的关系：**API 同形、不承诺二进制兼容**——简单工具插件把 import 换成宿主注入即可跑（约 10–30 行）。

### 插件安装模型（v2.4，用户定调）

> 「不用一键装社区插件；让软件里的 AI 对插件进行改造，然后装到我们的应用上。」
> 「没必要为它单独做个工具，能用就行了。」

只保留三样（详见 `05`）：

1. **兼容运行时**（宿主做厚）：提供 `@deepseek-ai/*` 与 `node:*` 子集 → 纯工具插件**零改动**就能跑；
2. **插件目录 + 加载报错 + 启用禁用 + 回滚**：插件页的普通功能，加载一次就是"干跑"，错在哪直接显示；
3. **AI 用现成能力改造**：读文件、改文件、看报错、再改——**不加专用工具、不做流水线、不做独立 Skill**。

硬约束：设备上没有 Node/npm，**插件必须是自包含 JS（打包过）**；AI 只能内联小依赖。

### 复制优先原则（v2.1，用户定调）

> 「能复制就直接复制，能不要自研就不要自研，能不用我们自己的就不用我们自己的。」

每加一个模块前先问三句：

1. **Operit 有没有？** 有 → 直接复制或模块引入，不重写。
2. **成熟的第三方库有没有？** 有 → 用库，不造轮子。
3. **只有 DSH 才有的？** （会话格式、提示词、工具行为、控制台主题、会话管理、对拍台）→ 才自己写。

20 个模块中 15 个走复制路线，详见 `03-借鉴-Operit.md` §八。

## 十、目录与工程约定

```
native/
  app/                  入口与 UI 装配
  core/                 纯 Kotlin（model/protocol/prompt/llm/agent/session/tools/fs/shell/markdown-stream）
  plugins/              kernel（服务容器/生命周期）、jsbridge（QuickJS+ctx）、api（清单/Profile/安装器）
  thirdparty/           terminal（OperitTerminalCore）、shower（虚拟屏）—— 均为 LGPL 子模块
  device/               Android 能力（shizuku/a11y/overlay/browser）
  parity/               对拍台与场景库
  docs/                 立项、方案、对拍、借鉴台账、ADRs
  tools/                构建/录制/比对脚本
```

- 每个模块一个 `README.md` 写明「对应契约编号」与「复制来源」
- 任何行为差异 → `docs/adr/NNNN-*.md` 记录
- 提交信息前缀：`port(<模块>):` / `feat:` / `fix:` / `parity:`
- 第三方代码目录**只读**；升级走 commit 切换，不做本地修改
- 根目录 `NOTICE`：汇总所有来自 Operit 的文件与 commit
