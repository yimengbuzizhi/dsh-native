## 1. M88-A 扩展点页签：停用的插件不再显示

### 现状
- `AppViewModel.refreshPluginExtensions()`（`app/.../chat/AppViewModel.kt:7124`）对 `pluginsUi` **全量**生成行；
  `!enabled` 时仍产出「声明存在；具体阶段在常驻运行时启动后展示」占位
  （工具 `:7144-7150`、请求 `:7203-7209`、存储 `:7230-7236`，另有 `:7266` 等状态分支）。
- `PluginsScreen.kt:369` 直接渲染快照，因此停用插件会以「已停用 / 声明存在」出现。
- 角色页的规则已经是用户要的：`RoleTargetVisibility.visibleInRoleList()` 只列「已启用 + 已授权」的插件实现。
- 删除链路已经是彻底的：`PluginStore.uninstall()`（`PluginStore.kt:151`）删清单记录 + 目录；
  `PluginResidentRuntime.removePlugin` 清投影与 checkpoint；`PluginRoleRefs` 清指向它的角色选择。

### 方案
1. `refreshPluginExtensions()` 的起点改成 `pluginsUi.filter { it.enabled }`；删掉所有 `!enabled` 的
   「声明存在」分支与 `statusOf` 里的「已停用」分支。
2. 「扩展点」页签空态保留三句：没有启用中的插件 / 没有匹配 / 已启用但没有注册。
3. **启用但未常驻**仍显示「未常驻（重新启用后加载）」——这不是停用，是运行时还没起来，有诊断价值。
4. 刷新时机不用新增：启用/停用/删除/重载已经都调 `refreshPluginExtensions()`（`:6883/:6937/:7020/:7059`）。

### 测试（JVM）
把行构造抽成纯函数（建议 `ui:shell-api` 的 `PluginExtensionRows.build(records, toolMeta, llmMeta, storageMeta, stats, switchOn)`）：
- 停用插件（即使声明了四条链）→ 0 行；
- 启用 + 未常驻 → 仍有一行「未常驻」；
- 缺少权限 → 「缺授权 xxx」；总开关关 → 「总开关已关（旁路）」；否则「生效」；
- records 里没有（删除后）→ 0 行。

### 真机验收
`m87e-storage` 停用 → 扩展点页签里没有它（搜索 `m87e` 也搜不到）；启用 → 四条链回来；
删除 → 导入/角色/扩展点三处都不再出现。

### 边界
「内置」页签仍列停用项（管理页必须能重新打开），这条不动。

## 2. M88-B root 与 Shizuku 合并为一条身份链

### 现状
- 执行层本来就是用户要的顺序：`DeviceShell.run()` 的 `DEFAULT` 是
  `hasRoot() → root`、否则 Shizuku、否则 App `sh`（`support/.../device/DeviceShell.kt:141-146`）。
- 但 H7（`docs/182` §H7，commit `7408c0c`）按 2026-11-16 拍板把**能力层拆成两个**：
  - `runRootOnly`：没 root 直接失败，**不降级**（`DeviceShell.kt:106-113`）；
  - `runShellOnly` / `shellOnlyIdentity`：只走 Shizuku / App，**不走 root**（`:119-124`）；
  - `CapabilityHost` 内置 `root.exec`（`:147-178`，只在探测到 root 时进候选 `:227`）、
    `shell.exec`（`:180-207`）、`shell.status`（`:209-218`）。
- 本条**取代** `docs/182` §H7 的「两个能力分开」拍板。

### 方案
1. `DeviceShell`：
   - `runShellOnly` → `runElevated(command)`：`root → Shizuku → App`；
   - `shellOnlyIdentity()` → `elevatedIdentity()`，用 `RootProbe.identity(root, shizuku, permission)`
     如实回报（`RootProbe.kt:99` 已经是这个优先级）；
   - `runRootOnly` 删除（`run()` 内部仍用私有 `runRoot`，不对外）。
2. `CapabilityHost`：
   - 删掉 `root.exec` 内置与候选过滤（`:227`）；
   - `shell.exec` 描述改成「自动选择身份：root 优先，其次 Shizuku，最后 App；返回 `identity` 说明实际身份」；
   - 直接按 id 调 `root.exec` 仍返回结构化拒绝，不静默失败：
     `{ok:false, reason:"merged_into_shell_exec", message:"root.exec 已并入 shell.exec（root → Shizuku → App 自动选择）"}`。
   - `shell.status` 增加 `preference:"root>shizuku>app"`，其余字段不变。
3. 设置 →「权限与能力」的「Shell 身份」行文案改成
   「当前身份：root / Shizuku / App（root 优先，无 root 自动用 Shizuku）」，探测写法保留。
4. 随包技能 `dsh-plugin-authoring` / `dsh-plugin-adapter`：能力表删 `root.exec`，`shell.exec` 语义更新。

### 风险与边界
- 需要 root 的命令在无 root 时会以 Shizuku / App 执行，失败由命令 stderr 体现；
  **不假装 root**，靠返回的 `identity` 字段说清。
- root 成功路径仍**不实测**（设备无 root），和 H7 的验收边界一致。

### 测试（JVM）
- `RootProbe.identity` 已有测试（root > 已授权 Shizuku > App）；
- 新增 `ShellCapability.execIdentity(root, shizuku, permission)` 三分支；
- 新增能力清单不含 `root.exec`（抽纯函数或直接测 `CapabilityRouting`）；
- `root.exec` 合并错误 JSON 结构。

### 真机验收
无 root 设备：`shell.exec` 无 Shizuku 时 `identity=app`、授权后 `identity=shizuku`；
`root.exec` 返回 `merged_into_shell_exec`；设置页「Shell 身份」行文案正确；`shell.status` JSON 带 `preference`。

## 3. M88-C 能力进工具表：通用 capability + notify 一等工具

### 现状（已确认根因）
- 能力只在 `CapabilityHost`（`app/.../data/CapabilityHost.kt`）：内置 `notify`（`:72-89`）、
  `notify.toast`、`clipboard.read/write`、`share`、`shell.*`。
- 模型工具表只有三条来源：`promptPack.androidApiTools() + pluginApiTools + pluginDevTools`
  （`AppViewModel.kt:2302-2305`）；**`capabilityHost` 不在里面**。
- `tools-android.json` 的 26 个设备工具也没有 notify。
- 所以 AI 从来「看不到」通知工具，不是模型不听话。

### 方案
1. 新内置组 `builtin.capability`（显示名「能力与通知」），两个工具：
   - `capability {id, args?}` → `capabilityHost.invoke(id, args)`；返回 `{ok, provider, value}` 或
     `{ok:false, reason}`；描述里列出内置 id，并说明插件能力见运行时清单。
   - `notify {title?, body}` → `invoke("notify")`；系统通知权限没开时返回可行动错误
     （「去 设置 → 权限与能力 → 通知 打开，或改用 notify.toast」）。
2. 动态清单：`runtimeContextText()`（`AppViewModel.kt:8939`）追加一行
   「可用能力：notify、notify.toast、clipboard.read、clipboard.write、share、shell.exec、shell.status…」
   （内置 + 已启用且拿到 `capability` 授权的插件能力，最多 20 个），让模型知道能调什么 id。
3. 注册：`BuiltinPlugins.all` 新组 + 工具名；schema 写 `tools-android.json`（宿主自有，不动上游 `tools.json`）；
   实现放 `app/.../device/tools/CapabilityTools.kt`，经 `appToolsByName` 注册。

### 测试（JVM / app 单测）
- schema 校验（缺 id、args 非对象）；
- 未知 id → 错误里列出可用 id；
- `notify` 无系统权限 → 错误文案；有权限 → `shown:true`（用假 host 注入）；
- 关掉内置组 → registry 里没有 `capability` / `notify`（`syncBuiltinTools` 已有开关逻辑，补断言）。

### 真机验收
「用 notify 通知我 xxx」→ 通知栏出现、工具卡成功、点击回聊天；
`capability{id:"clipboard.read"}` 能读到剪贴板；关内置组后模型看不到这两个工具。

### 边界
插件能力仍要「启用 + `capability` 授权」，`CapabilityRouting` 规则不变。

## 4. M88-D HTTP 请求工具（curl 等价）

### 现状
- 仓库没有 curl / HTTP 请求工具；`web_fetch` 只做 GET 抓取并解码文本
  （`core/tools/web/WebFetchTool.kt`）。
- 终端里 `curl` 是 busybox 软链（`thirdparty/terminal/.../TerminalManager.kt:226-250`），
  只在终端里可用，**不在 AI 工具表**，也没有插件化。

### 方案
1. 新工具 `http_request`，归属内置组 `builtin.web`（与 web_search/web_fetch 同组，可整体关闭）：
   - 参数：`method`（GET/POST/PUT/PATCH/DELETE/HEAD/OPTIONS，默认 GET）、`url`（仅 http/https）、
     `headers`（string→string 对象）、`body`（字符串）、`timeout_ms`（默认 15000，上限 60000）、
     `max_bytes`（默认 262144，上限 1048576）、`follow_redirects`（默认 true，最多 5 跳）。
   - 返回 JSON：`{ok, status, url, headers, body, bytes, truncated, contentType, elapsedMs}`；
     非文本 content-type → `encoding:"base64"`。
   - 错误：非法 scheme/URL、连接失败、超时、body 超限（`truncated=true` 不算错误）。
2. 实现 `core/tools/web/HttpRequestTool.kt`（OkHttp，复用 `WebFetchTool.defaultClient()` 的配置）；
   加入 `BuiltinToolCatalog` 的 `builtin.web` 组；`BuiltinPlugins` 的 `builtin.web.tools` 加 `http_request`；
   schema 加到 `tools-android.json`。
3. 安全：
   - 只允许 http/https，不跟随到其它 scheme；
   - **不回显请求头**（可能含 token），只回响应头（去 `set-cookie`）；
   - 不读本地文件；不自动重试 POST。

### 测试（JVM，JDK `HttpServer`，不依赖外网）
GET 200 + 响应头；POST body 回显；302 跟随；非法 scheme 拒绝；超时；body 截断标记；头部数量/长度上限。

### 真机验收
有网：POST 到 public echo 服务；无公网：终端起本地服务（`python -m http.server` 或 busybox `nc`）验证
GET/POST/超时；确认工具卡显示状态码与耗时。

### 边界（本轮不做）
cookie jar、自定义 CA/证书例外、代理设置、上传文件。

## 5. M88-E AI 全控制插件（授权 / 撤销 / 配置 / 角色 + 审计）

### 现状
- AI 已有：`plugin_dev_list / test / install / enable / delete / reload / call / test_shell /
  test_capability / scaffold`（`app/.../data/PluginDevTools.kt:30-53`，写名单 `:158`）。
- **没有** grant / revoke / config / role；权限授予只在 UI（`PluginStore.grant():123`、`grantAll():139`）。
- 用户原话：「用户并不会知道这个查询到底是干嘛的，建议把这个权利给 AI，AI 查的会更方便；
  尽量做到 AI 对插件的全控制。」

### 方案
1. 新工具（写类，沿用现有审批策略）：
   - `plugin_dev_grant {id, permissions?[], all?}` → 先 `PluginPermissions.sanitizeGrants` 收敛到
     「清单声明过的权限」，再写回；返回实际授予列表；
   - `plugin_dev_revoke {id, permissions?[], all?}` → 对称撤销；
   - `plugin_dev_config {id, config?object, reset?}` → 走 `PluginStore.setConfig`（schema 校验复用）；
   - `plugin_dev_role {role: shell|loading|agent|storage|prompt|model, value}` → 复用
     `AppViewModel.selectShell / selectLoading / setActiveAgent / setActiveStorage / setActivePrompt /
     setActiveModel`（`value` 支持 `builtin` / 插件 id / `插件id#实现id`）。
2. 审计：`PluginAuditLog`（`files/plugin-audit.jsonl`，追加
   `{ts, actor:"ai"|"user", action, target, detail}`，512KB 轮转保留 1 份）；
   插件详情底部显示该插件最近 5 条；`plugin_dev_list` 每条带 `lastAiAction`。
3. 可见性：聊天页 `pluginNotice` 横幅（`AppViewModel.kt:500`）显示
   「AI 已授予 m87e-storage：storage:hooks · 撤销」；插件详情权限行标「AI 授予」。
4. 设置：`SettingsStore.aiPluginControl`（默认**开**）+ 设置 →「插件」开关；
   关掉后上面四个工具返回 `ai_plugin_control_disabled`。
5. 红线：
   - 不能授予清单外的权限（`sanitizeGrants` 已保证）；
   - 不能改系统权限（Shizuku 授权 / 无障碍 / 通知仍是系统弹窗）；
   - 授予 `notify` 但系统通知未开时返回警告（插件仍发不出去，需用户去系统设置开）。
6. 与审批的关系：工具调用仍受 `approval_mode` 约束（`ask` = 用户点一次审批；`auto` = 不弹）。
   **权限授予本身不再单独弹「危险权限」确认**——这正是本条的目的；用审计 + 撤销 + 总开关兜底。

### 风险（明确写在这里）
模型可以 `plugin_dev_scaffold` → `plugin_dev_install` → `plugin_dev_grant(shell)` → `plugin_dev_call`，
等于自提权。这是用户明确要求的「全控制」。缓解手段只有：审计、撤销、开关、插件页可见。
若后续要收紧，可在 `SettingsStore` 加「红线权限需一次确认」（shell / fs:any / net:any）。

### 测试
- grant/revoke 的 sanitize（清单外权限被丢弃、`fs:any` 覆盖 `fs:workspace`）；
- 审计 JSONL 追加 / 轮转 / 读回；
- 设置关闭 → 四个工具报错；
- `plugin_dev_role` 的 value 解析（纯函数）；
- 配置写入走 schema 校验（复用现有 `setConfig` 测试）。

### 真机验收
让 AI「给 `m87e-storage` 授予 `storage:hooks` 并启用」→ 扩展点显示生效、审计有行、横幅可撤销；
关设置开关 → 工具报错；AI 选角色（回合/壳）→ 聊天页立即变化；权限撤销后扩展点回到「缺授权」。

## 6. M88-F 设置二级页动画

### 现状
- 一级页切换：`NativeShellRoot.kt:399-410` 的 `AnimatedContent`，新页 160ms 淡入 + 1/8 屏位移，旧页不动。
- 二级页：独立一层，只有 `animateFloatAsState` 的 **alpha 160ms**（`:424-447`），**没有位移**；
  页面保留组合（关闭后 alpha=0、zIndex 沉底），这是 H4 候选 E 的性能收益。
- 用户观感：设置里进入二级页「动画没了」。

### 方案
1. 保留组合，只给二级页层加位移：`offsetX` 从 `+1/10 屏宽 → 0`，配合 alpha 180ms 进入；
   退出反向 140ms。只动 offset/alpha，不重组合页面内容。
2. 二级页之间切换（同层换内容）也用 6% 位移 + 交叉淡入，避免硬切。
3. 量化：改前/改后各跑一遍 `dumpsys gfxinfo`（设置→显示与行为、设置→权限与能力、聊天→设置），
   记录 janky% / p50 / p90。H4 基线：最好一次 9.1% janky / p50 10ms，常见 p50 19–34ms；
   目标：**动画可见且不劣于当前基线**。
4. 若位移把 jank 拉回 >30%：退回「12dp 位移 + 200ms」，再不行加设置项「页面动效：轻 / 关闭」。

### 测试
- 纯函数 `SubpageShift.dir(from, to)`（进入/返回/同级）单测；
- 真机手势：返回键、系统返回、连续快速切换、横屏/宽屏抽屉不回归；
- 二级页 `clearAndSetSemantics` 在隐藏时仍然生效（无障碍不读两层）。

### 真机验收
设置→显示与行为有可见滑入、返回有反向；聊天直进二级页同样有；连续切换不闪白、不叠两层；
gfxinfo 数字不超过基线。

## 7. M88-G 工具输入过长：显式报错，不再静默停止

### 现状与根因（部分待取证）
- `TurnEngine.parseArgs`（`:1790`）对非法/半截 JSON **静默返回 `{}`**，工具拿空参数执行，
  看起来就是「调用工具后停了、没反应」。
- max_tokens 截断在 tool_use 上已有 H1 收口（`:733-759`：不执行 + error tool_result + `setError` +
  可「继续生成」）；OpenAI `finish_reason=length` 已映射 `max_tokens`（`OpenAiClient.kt:365`）。
- **没有工具输入长度上限**这一层。
- 用户要求：输入过长时工具直接报错，告诉 AI「输入过长」，让它拆小重试。

### 方案
1. **参数完整性 + 长度检查**（`TurnEngine` 执行工具前）：
   - `parseArgsStrict`：非法/半截 JSON → `ToolResult.err("工具参数不是合法 JSON（可能被截断）…请拆成多次调用")`；
   - `call.arguments.length > limit` → `ToolResult.err("工具输入过长：N 字节 > 上限 M 字节，请分段/分批重试")`；
   - 默认上限 64KB；`write` / `edit` 512KB；插件工具 64KB。数值放常量表，可按工具覆盖。
   - 两种情况都按「error tool_result + UI 错误卡」落库，**回合继续**（不 break），模型可重试。
2. UI：工具卡红色错误态（`toolResultLooksFailed` 补「输入过长」「参数被截断」关键词）。
3. **先复现取证**：真机让模型一次写超长内容（`write` 长文件），抓 logcat（`DshEngine` / `DshTurn`）
   + 会话 JSONL，确认到底是「max_tokens 截断」「半截 JSON」还是「UI 冻屏（ANR）」；
   若证据指向冻屏，再限制工具卡对超长参数的渲染（>8KB 只显示摘要 + 展开）。
4. 若证据显示某供应商不返回 `finish_reason`（流中断），补一条「流结束但无 stop_reason 且存在 tool_use」
   → 按截断处理，落 error 结果。

### 测试
- 半截 JSON → error 且工具不执行；
- 超限 → error；恰好等于上限 → 放行；
- 错误后下一个工具调用正常执行（回合不中断）；
- `toolResultLooksFailed` 覆盖新文案。

### 真机验收
复现一次（记录 logcat + JSONL）；修后同样输入 → 工具卡报「输入过长 / 参数被截断」，
回合不中断；模型拆分后写入成功。

| `AttachmentStreams`（app） | 新增分块复制工具（64KB 缓冲，内存与文件大小无关、无字节上限），`copyUriToTemp` 与工作区复制共用 |

保留的「限制」不是文件大小，而是解码安全/发送形态：

- 单边 65535px、解码 6400 万像素（防解码炸弹）；
- 归一化输出 ≤4MB / ≤2048²（模型实际收到的图片大小不变）——源文件再大也只是被缩放后发送。

### 14.3 真机待测（M88-H）

  发送后模型收到归一化图（≤2048²/≤4MB），工具卡/图片块可点开；对比同一张图 <50MB 时行为一致。
