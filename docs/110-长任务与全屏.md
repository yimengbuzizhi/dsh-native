## 二、长任务「干一半自己停」= 单轮 12 步上限，到顶静默退出

**复现**：聊天页发「手机好卡，帮我看看怎么回事？」（英文等价句也复现）。
第一次跑：`22:27:51 → 22:30:57`，`turn end after 185656ms`，界面显示「已完成 · 用时 2 分 52 秒」，
正文停在「……我来测它自己到底吃多少 CPU。」——没有结论。

**会话证据**（`0147fa5e` 的第 2 轮，英文复现句）：`step/start` 恰好 **12** 个、`tool/call` 17 个，
最后一步的工具结果已落库，紧接着 `turn/end {kind:"completed"}`，**没有收尾 assistant 文本**。

**根因**：`core/engine/TurnEngine.kt` 里 `MAX_ROUNDS = 12`，`while (round < MAX_ROUNDS)` 到顶直接
离开循环 → 写 `turn/end completed`。既没有错误、也没有提示，用户看到的就是「AI 干一半不动了」。
这个 12 是 M2 时期定的（`docs/14`「最多 12 轮」），中间一直没有再评估。

**改法**：按用户明确要求「不要有上限」，循环改成 `while (true)`，只在
模型自己不再调用工具、`max_tokens`、用户停止/取消时结束（与上游主循环一致）。删掉
`AppViewModel` 里同名未使用的常量。

**验证**：
- 单测 `TurnEngineTest.toolLoopHasNoRoundCap`：脚本连续 15 轮工具调用 + 最后一条文本，
  断言 16 次请求、16 个 step、15 个 tool/call、`completed`、最终文本生效。`:core:engine:test` 40/40。
- 真机：同一会话让模型「分 15 轮、每轮只调一次 bash」，实跑 **16 步 / 15 次工具调用 / completed**，
  最后给出总结（旧代码在第 12 步就会静默截断）。

**走查中排除的另一条**：22:30:57 那次 `turn/end aborted`（第 9 步、工具执行中）不是模型停的，
是用户误触悬浮窗「回到应用」——`FloatingWindowScreen:211` 的 `onOpenApp` 会 `onClose()`，
`FloatingBallService.closeSelf()` 里有 `ChatMirror.stop()`。用户确认是误触；这条行为**保持原样**，
只把 `stop()` 的调用栈打进日志，便于以后区分「用户停」和「自己停」。

## 三、停止后「正在停止…」永久残留

**现象**：轮次已经「已完成」，聊天页左下角还挂着「● 正在停止…」（截图 `113-24`）。

**根因**：
- `AppViewModel.stop()` 不判断当前有没有在跑的轮次，无条件写 `stopping=true`、`statusText="正在停止…"`；
- 1.5 秒兜底只在「还占着运行集合 / streaming」时才清状态。

所以「空闲时被调用一次 stop()」或「点停止的同一瞬间轮次刚好正常收尾」这两种情况，状态没人清。
最典型的触发路径：**空闲时关悬浮窗** → `closeSelf()` → `ChatMirror.stop()` → `AppViewModel.stop()`。

**改法**：
- `stop()` 开头：没有活动 job 且不在 streaming 时，只清 `stopping/statusText` 然后 return；
- 1.5 秒兜底：仍占用 → `forceStopUi`；只是残留 `stopping` → 静默清掉，不误报「收尾超时」；
- `stop()` 打一条带调用栈的 `Log.i("DshTurn", "stop requested: …")`（以后能区分谁停的）。

**真机验证**：
- 运行中停止：`sleep 30` 的 bash 工具执行中点停止，约 **130ms** 收口，`ps` 里 `sleep 30` 已消失，
  状态条清空、按钮回到发送（`113-26`）；
- 空闲时关悬浮窗（`closeSelf → ChatMirror.stop`）：回到聊天页**没有**「正在停止…」残留（`113-29`）。

## 四、悬浮窗全屏：折叠 + 泛白

**问题**（截图 `113-01`）：全屏的 `FullscreenMessage` 把 `TEXT + REASONING` 拼成正文、工具结果也当正文铺；
整页套在系统浅色主题里，Markdown 行内代码是「浅底 `0xFFEDF1F7` + 白字」，路径看起来就是一片泛白。

**改法**（`device/floating/ui/fullscreen/FloatingFullscreenScreen.kt`）：
- 正文只取 `TEXT`；
- 带工具调用的 assistant 消息整条折成「过程 · N 个工具调用」（流式中「正在执行 xxx…」），点开才看
  思考/中间文本/工具卡；
- 纯文本回复前的思考单独折成「思考过程 · N 字」；
- tool 结果只留一行「⚙ 工具结果 · N 字」；
- 消息区强制 `DshTheme(darkTheme = true)`，行内代码/代码块变成深底白字；
- 遮罩：原来是 0.22（依赖系统 48dp 模糊），这台 ColorOS 的 `isCrossWindowBlurEnabled` 报 true
  但实际没有模糊，白字压在壁纸上发虚；改成固定 **0xB0（约 69%）** 暗底，仍能隐约看到后面的 App。

**真机证据**：`113-14`（流式中：过程/工具结果都折叠）、`113-20`（完成后：暗底、行内代码可读）、
`113-21`（点「展开」后的过程行、中间叙述、bash 工具行）。

## 五、限制 / 没验到的

1. **没有步数上限**是用户明确要求：如果模型反复调同一个工具，本轮不会自己停，只能用户点停止。
   模型自带的工具没有额外的循环刹车（本批没有加）。
2. 悬浮窗的「回到应用」/「关闭 ×」仍会停掉正在跑的轮次（`closeSelf → ChatMirror.stop`，
   用户 22:47 误触确认过）。按用户意思保持原行为，只加了日志。
3. 全屏遮罩加深后不再严格对齐 Operit 的「0.22 + 系统模糊」；这台机器上没有模糊，可读性优先。
4. 12 步上限的「现场」来自会话文件推断（第 2 轮恰好 12 步 + completed + 无收尾文本），
   没有在旧包上再刻意跑一次对照。
