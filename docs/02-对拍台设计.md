# 02 · 对拍台设计（Parity Harness）

> 作用：把「完美移植」变成可自动判定的东西。没有它，7 条契约只能靠目测。
> 它是长期资产：每次追上游 stable 都要跑。

---

## 一、核心思路

模型本身有随机性，所以**不比较模型输出**，而是比较「引擎在两个版本下做的事」：

```
           ┌──────────── 录制（只做一次）────────────┐
旧版引擎 ──► 录制代理 ──► DeepSeek API
           └─ 存下 request/response 对 ────────────┘

           ┌──────────── 回放（每次移植后跑）────────┐
旧版引擎 ──► 回放代理 ─┐
新版引擎 ──► 回放代理 ─┴─► 同一份录制，按顺序返回
           └─ 比对两边的「行为」────────────────────┘
```

比较对象（5 类）：

| # | 对象 | 判据 |
|---|---|---|
| 1 | 发给模型的 request body | 归一化后**逐字节相等** |
| 2 | 工具调用序列（名字 + 参数 + 顺序） | 逐条相等 |
| 3 | 工具输出（stdout/文件内容/错误码） | 逐字节相等 |
| 4 | 工作区最终状态（文件树 + 内容哈希） | 相等 |
| 5 | 写出的会话文件（v4） | 结构化归一后相等 |

## 二、三个组件

### 1. Recorder（录制器）

一个本地 HTTP 代理，监听 `127.0.0.1:18080`：

- 旧版引擎把 `baseURL` 指过来（`dsh-llm-deepseek` 支持自定义 base；不行就用系统 hosts/透明代理）
- 收到请求 → 存 `{seq, request, response_chunks, timing}` 到 `parity/fixtures/<scenario>/llm-<n>.json`
- 流式响应要**逐 chunk 记录**（含 SS E 边界），否则回放出来的时序不一样

注意：录制只做一次；模型换版本不影响对拍（fixture 固定）。

### 2. Replayer（回放器）

同样的本地端口，按请求顺序返回录制内容：

- 匹配策略：默认**按序**；若开启 `strictMatch`，用 `sha256(canonical(request))` 匹配
- 支持「延迟 0」模式（跑得快）和「真实时序」模式（验证中断/超时）
- 记录调用次数：新版多发/少发一次请求 → 直接 FAIL

### 3. Comparator（比对器）

输入：两个 run 目录

```
parity/runs/<scenario>/<impl>/
  llm-requests.jsonl     每次发给模型的请求
  tool-calls.jsonl       工具名 + 参数 + 结果
  workspace/             最终工作区快照
  session/               会话文件（解压后）
  stdout.log             引擎日志
  meta.json              版本、耗时、内存
```

输出：

```json
{ "scenario": "edit-function", "status": "FAIL",
  "firstDiff": { "stage": "tool-call#2", "path": "$.timeoutMs", "expected": 30000, "actual": 30000.0 } }
```

规则：**只报第一个差异**（后续差异往往是它的连锁反应），并附两边的上下文各 5 行。

## 三、归一化规则（必须先归一，否则永远 FAIL）

| 类别 | 处理 |
|---|---|
| 时间戳 / 日期 | 替换为 `<TS>` |
| 会话 ID / 消息 ID / trace ID | 替换为 `<ID:n>`，并在同一次 run 内保持一致映射 |
| 绝对路径（含用户名/临时目录） | 替换为 `<WORKDIR>` |
| 进程号 / 端口 | 替换为 `<PID>` / `<PORT>` |
| 浮点耗时、token 数 | 移除或按 ±2% 容差 |
| 顺序无关字段（如 `tools` 数组） | 按 name 排序后再比 |
| 上游随机短语（如「让我看看」） | **不归一**——模型输出不在比较范围内 |

## 四、场景（Scenario）格式

```yaml
id: edit-function
workspace: fixtures/workspaces/ts-small   # 拷贝一份，两边各跑各的
prompt: "把 src/math.ts 的 add 改成 async"
engine:
  model: deepseek-chat
  maxTurns: 8
assert:
  - workspace-hash-equal
  - session-v4-readable-by-old
  - tool-sequence-equal
allowDiff: []            # 明确允许的差异（必须写理由）
```

## 五、场景库（按阶段扩张）

| 阶段 | 场景数 | 覆盖 |
|---|---|---|
| P0 | 6 | 只读文件、写一个文件、改一个函数、跑一次 shell、失败重试、取消中断 |
| M1 | 30 | 会话/模型/审批/附件/压缩 |
| M2 | 60 | 30 个工具逐个 + 组合任务 |
| M4 | 100+ | 上游 stable 全功能 + 边界 |

> 2026-11-08 落地情况：P0 已有 **5 个真机夹具**——`device-smoke`（bash ls）/ `device-read` /
> `device-write` / `device-edit` / `device-read-error`，全部 run-1 vs run-2 PASS
> （明细见 docs/31 §四.2、docs/32 §四.3）。工具从 20 增到 23（`job_*`）后 `tools` 数组与
> `tool:jobs` 系统提示词段都变了，5 个夹具**整套重录**并重新验证 PASS。
> 「失败重试」「取消中断」还差夹具通道：record 目前只录成功 SSE，
> 流中途注入用户停止需要新的调试参数。写/改类场景用 `parity.ps1 -PreRunClean <相对路径>`
> 保证每次 run 的起点一致（否则 `write` 的 `Created file`/`Updated file` 会让 sha 对不上）。

## 六、怎么跑

```powershell
# 录制（旧版，只做一次；需要设备或本地引擎）
.\tools\parity.ps1 record  -Scenario edit-function -Endpoint http://127.0.0.1:3080

# 回放 + 比对（新旧各跑一次）
.\tools\parity.ps1 verify  -Scenario edit-function -OldApk <path> -NewApk <path>

# 全量
.\tools\parity.ps1 verify-all -Suite p0
```

输出：`parity/reports/<date>.md`（人看）+ `.json`（门禁用）。

---

## 七、P0 阶段的验收线

1. 能录制并回放**一次完整的流式对话**（含工具调用）
2. 同一实现跑两次，报告 **0 diff**（证明工具本身稳定，不是随机 PASS）
3. 旧版跑两次，报告 **0 diff**（证明旧版行为可复现——这是 oracle 成立的前提）
4. 新版跑一次，能产出**结构化差异报告**（哪怕全是差异）

第 2、3 条最容易被跳过，也是最关键的：**先证明「尺子」准，再去量东西。**

## 八、已知陷阱（写死）

1. **SSE chunk 边界**：回放必须按 chunk 返回，不能合并成一个包——否则流式渲染的时序判据全失效。
2. **代理要支持 HTTP/2 与 gzip**：上游若开了压缩，录制存原始字节，回放原样返回。
3. **不要把时间写进 fixture**：录制文件里出现真实时间戳，回放时会被当成差异。
4. **工作区必须每次重新拷贝**：两个 run 共用同一目录会互相污染。
5. **会话文件要先解 zstd 再比**：直接比 `.zstd` 字节会因为压缩实现差异误报。
6. **旧版自己也可能不稳定**（随机 id、并发顺序）→ 先跑两次旧版对齐，把不稳定项写进 `allowDiff`。
