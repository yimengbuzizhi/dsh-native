## 二、做了什么

### 1. 新模块 `:core:plugins`（纯 JVM，16 条单测）

| 文件 | 职责 |
|---|---|
| `PluginPackage.kt` | 读 zip（条目数/单文件/总量上限、zip-slip 校验、剥单顶层目录）、认 `package.json`（DSH）与 `manifest.json`（Operit/ToolPkg 兜底）、校验 `main` 入口存在 |
| `PluginModule.kt` | ESM `import`/`export` → CJS（QuickJS 全局脚本没有模块加载器）、拼试运行脚本（注入 `ctx`/`defineTool`/`z` 宽松代理）、`parseDryRun` 解结果 |
| `PluginModel.kt` | 清单/记录数据结构 + `files/plugins.json` 读写（坏文件降级为空，不阻塞页面） |

**上限**：条目 ≤2000、单文件 ≤4MB、解压总量 ≤32MB、导入 zip ≤64MB。

**清单规则**：
- 路径最短的清单优先；同目录下 `package.json` 优先于 `manifest.json`（Operit 包同时带两个时按 DSH 解析）；
- 两个不同顶层目录各有一份清单 → 直接报「包里多个顶层插件目录，请一次只装一个」，不让用户猜；
- 入口缺失 → 报「清单里的入口 main=… 在包里找不到」。

### 2. App 侧

- `ui/plugins/PluginsScreen.kt` 重写：导入卡（SAF 文件选择器）、已安装卡片（版本/格式/工具数/报错原文/开关）、

- `AppViewModel`：`pluginsUi/pluginsBusy/pluginNotice` + 导入/启停/重载/删除；工作台插件数改成「3 内置 + 已启用本地」。
- 调试通道：`--es dsh_plugin_zip <绝对路径>` 直接导入并落到插件页（锁屏、无 UI 也能验，本轮靠它取证）。

### 3. 踩到的两个坑（写下来省下一棒的时间）

1. **QuickJS 桥的返回值约定是顶层 `return`**：`core:js` 会把脚本包进
   `(function(){ try { const __r = (function(){ … })(); …`，所以脚本结尾写表达式没有用，`__r` 永远是
   `undefined`，现象是「completed 但 value=null」。第一版就这么踩了，改成脚本最后 `return JSON.stringify(__dsh)`。
2. **Kotlin 属性初始化顺序**：`init {}` 里调用了后面才声明的 `pluginsBusy`/`pluginStore` → 真机直接
   `NullPointerException` 崩在 `AppViewModel.<init>`。插件状态声明挪到 `init` 之前（并在代码里留注释）。

另外：`defineTool()` 和 `ctx.tools.register()` 都各自记一次会导致工具重复（第一版 demo 出现
`demo_hello` 两次），现在 `defineTool` 只返回对象、由 `register` 去重登记。

## 五、边界（故意没做，别在群里夸口）

- **插件工具还没接进对话**：`ToolRegistry` 是启动时静态注册的，动态插件工具需要「插件运行时 + 每轮注入」，
  下一轮做；插件页文案和页脚都写明了。
- **不是安全沙箱**：试运行里的 `__require` 全是空实现（fs 读返回空串），但等真正执行插件代码时
  必须按 manifest 限权（文件/网络/child_process），否则等于把 shell 交给插件。
- **异步 `apply` 不等**：返回 Promise 时只提示，不等待（DSH 插件绝大多数同步注册）。
- **相对依赖不支持**：要求自包含单文件（docs/05 的约定），检测到会明说。
