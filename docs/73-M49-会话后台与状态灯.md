## 一、那个 400：`tool_use` 缺 `tool_result`

用户截图（21:25～21:35）反复出现：

```
messages.78: `tool_use` ids were found without `tool_result` blocks immediately after:
call_00_ET_71HyZ8ArvQ1PgRNlkuev7344. Each `tool_use` block must have a corresponding
`tool_result` block in the next message.
```

### 根因（真机取证）

从设备拉了出问题的会话 `88d2ed40-9fd5-4cfd-98e9-0693da2bc753`（改成 jsonl 后用脚本逐事件对账）：

- 39 条 `tool/call`、38 条 `tool/result`，**正好差一条**；
- 缺的是 `seq=207` 的 `bash`（`sleep 3; echo ok`）——turn 4 第 3 步；
- 这不是模型的问题：**工具执行中途切会话/按停止**时，assistant 的 `tool-call` 已经落库，
  但 `session.appendToolResult()` 的 `withContext(Dispatchers.IO)` 在已取消的协程里立刻抛出，
  结果没写进去。之后每次请求都会带这条残缺 assistant，服务端就整条 400。

### 两层修

1. **收尾兜底**（`core/engine/TurnEngine.kt`）：本轮已落库、还没写结果的调用记进 `pendingToolCalls`；
   `CancellationException` 的 `NonCancellable` 收尾里给它们补一条 `is_error` 的 `tool_result`
   （`INTERRUPTED_TOOL_RESULT`）。写之前用 `SessionSession.hasToolResult(callId)` 去重
   （取消恰好发生在 append 内部时不会写两条）。
2. **请求组装兜底**（同一个文件）：`repairToolPairs()` 在 `buildRequest` / `buildCompactionRequest`
   里扫 API 消息，发现 assistant 的 `tool_use` id 没有对应 `tool_result`，就在请求里补一条
   error 结果（只影响这次请求，不改会话文件）。**已经坏掉的历史会话因此不用重建。**

### 证据

- 单测：`orphanToolUseInHistoryIsRepairedInRequest`、`cancellingWhileToolRunsPersistsSyntheticToolResult`
  （`TurnEngineTest`，`:core:engine:test` **82 条 0 失败**）。
- 真机：冷启 `--es dsh_open_session 88d2ed40… --es dsh_send '说话呀'`
  → `DshTurn: turn start session=88d2ed40…` → 13s 正常回话，**没有 400**；
  截图 `docs/shots/73-400-fixed.png`。

## 二、切会话不中断生成 + 会话条状态灯

### 结构改动

原先 ViewModel 只有一份 `handle` / `turnStop` / `planState` / `engine` / `streamJob`，切会话直接取消。
现在每个打开过的会话一份 **`LiveChat`**：

```kotlin
private inner class LiveChat(val state: ChatSessionState) {
    var handle: SessionSession?      // 自己的会话文件
    val stop = TurnStopState()       // 自己的停止位（stop B 不会停 A）
    val plan = PlanModeState()       // 自己的计划模式
    var goalActivation = ...
    var job: Job?                    // 自己的轮次协程
    val engine: TurnEngine by lazy { buildEngine(this) }  // 每会话一个引擎，句柄绑死
}
```

- `openSession`/`newChat`/`closeChat`/`openSubagentSession` 不再 `cancelStream()`；
  切回来时如果这个 state 还在 `lives` 里，直接复用（流式光标/工具卡都还在），不重读文件。
- 只允许**一条**轮次在跑（`activeTurn`）：另一条会话在生成时发送会被拒绝并提示
  「「X」正在生成，等它结束再发」——工具上下文/通知归属是进程级共享的，并发轮次会串会话。
- 后台轮的归属都优先 `activeTurn`：goal 工具、schedule 工具、`exit_plan_mode`、
  审批/提问的弹窗、`job_owner`、子代理 `currentAgentId` / fork seed、`tickSchedules`。
- 保活：`stop()` 不再立刻清 `runningState`，等引擎取消收尾写完 `turn/end` 再清，
  避免前台服务在收尾前先停。

### 状态灯（抽屉 + 「全部会话」页共用 `SessionBadgeMark`）

| 状态 | 视觉 | 条件 |
|---|---|---|
| `RUNNING` | 13dp 转圈（brand） | `runningState.sessionId == id` 且没有待回答 |
| `WAITING` | 8dp 橙点 | 同上，但 `pendingApproval`/`pendingQuestions` 非空 |
| `DONE` | 8dp 绿点 | 跑完时用户不在这个会话（`unreadDone`），打开/切回即清 |

### 证据

- 冷启发「请调用 bash 工具执行 sleep 45…」→ 9s 后开抽屉：该行右侧转圈（`73-badge-running.png`）；
- 移到另一条会话（「第1段。这是用于验证摘要请求…」），**不返回**；logcat：
  `22:17:21 turn start` → `22:18:11 turn end after 49504ms`（不是 aborted）；
- 拉新会话 `9f4699e2…` 的事件：`turn/end {"kind":"completed"}`，`tool/result` 正常；
- 抽屉该行变成**绿点**（`73-badge-done.png`）；点进去看到 bash 卡 + 「完成」，
  再开抽屉绿点消失（`73-bg-complete.png`）。
- `WAITING` 橙点只做了代码路径，**没真机验证**（当前 `approval_mode=auto`，要造审批/提问才会出）。

## 四、文件附件（不只图片）

`ChatSessionState.pendingFiles` + `AppViewModel.attachFile(uri)`：

- 图片（mime `image/*` 或文件头识别）→ 原图片管线（归一化 + 内容寻址 + base64）；
- 文本/代码（`text/*`、`.md/.kt/.py/.json/...`，或未知后缀但 UTF-8 无 NUL）→ 读成文本，
  发送时作为额外 text 块：`[附件: 名字]\n\n<正文>`，跟在用户文字后面（同一个 `user/message`）；
- 二进制（PDF/Word/压缩包）→ 明确提示「暂不支持解析」，不塞乱码给模型；
- 单文件上限 512 KB；输入条有小卡（文件名 + 字数 + 移除），附件面板多了「文件」一行。
- 编译通过；**真机没验**（SAF 文件选择要手动点几层，本轮先留给下一轮）。
