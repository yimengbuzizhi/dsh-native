## 0. 一分钟结论

1. 一个会话 = 一个目录 `…/--<项目键>--/<URL 转义后的会话 id>/`，里面按“格式代”存文件：`session.jsonl.zstd`（v0）、`session.v1.jsonl.zstd` … `session.v4.jsonl.zstd`。
2. 文件是**标准 zstd 帧的简单拼接**：第 1 帧只装 1 行 header，此后**每次 append 批次一帧**；每帧独立带 checksum，帧内明文是若干行 UTF-8 JSONL，**每行以 `\n` 结尾**（最后一帧也以 `\n` 结尾）。解压后**没有第二层**，直接就是 JSONL 文本。
3. v4 行只有两种：header 行 `{"type":"session","version":4,…}`，和事件行 `{"type","seq","time","data"[,"ignorable"][,"sourceEventSeqs"][,"surfaceOp"]}`。字段名/取值有严格白名单，**多一个顶层键就会被判损坏**。
4. 版本链是**相邻整数** v0→v1→v2→v3→v4，只能逐级迁移；写盘时**只写当前版本（v4）的新 generation，旧文件一个字节都不改**。
5. 最大的三个坑：① `sourceEventSeqs` 有**区间压缩**（`[start,end]` 与裸数字混排，且**长度为 2 的数组永远是区间**）；② **首帧必须是且仅是 header 行**，否则整文件判损坏；③ 尾部撕裂帧要按“**完整 JSONL 行**”粒度恢复，不是按帧粒度。

## 1. 术语

| 术语 | 含义 |
|---|---|
| **逻辑会话（logical）** | 内存中的 `SessionHeader` + `SessionEvent[]`，版本永远是“当前版本”（本 build 为 4） |
| **物理行（row）** | 磁盘 JSONL 里的一行 JSON，可能属于历史版本 |
| **格式代 / generation** | 一次格式版本对应的**不可变**文件，例如 `session.v3.jsonl.zstd`；文件名即版本 |
| **当前代** | 数值最高的规范 generation；写句柄只追加它 |
| **继承切点（inherited cut）** | fork 子会话从父会话继承的事件数；v0/v1 存在 header 的 `seedLength`，v2+ 由带标记的 `session/end-seed` 事件推导 |
| **surface（表面）** | 模型可见的消息序列；`system/user/developer/assistant/tool-result` 五类事件进入 surface |
| **log-only（仅日志）** | 不进模型历史的记录，如 `request/header`、`token` 无关的 `job/*` 等 |

## 2. 目录布局与文件命名

### 2.1 三层结构【代码】

```
<root>/                                  # 配置项 root（桌面端默认 <DSH_HOME>/sessions）
  --<projectKey(cwd)>--/                 # 人类可读的项目目录；cwd 缺失时用 _no-cwd
    <encodeSegment(sessionId)>/          # 会话自有目录，id 已被单射转义
      session.jsonl.zstd                 # v0
      session.v1.jsonl.zstd              # v1
      session.v2.jsonl.zstd              # v2
      session.v3.jsonl.zstd              # v3
      session.v4.jsonl.zstd              # v4（当前）
      session.lock                       # 仅 POSIX：flock 用的锁文件（Windows 无此文件）
      session.migration.<token>.jsonl.zstd.tmp   # 迁移中的临时文件（可能出现）
      session.v4.jsonl.zstd.<12hex>.tmp  # 原子写临时文件（短暂存在）
```

本机实测根目录：`C:\Users\user\.dsh\sessions\`，其下有 `--D-dsh--`、`--D-FBD--`、`--D-pusuan--`、`--D-~6742--` 四个项目目录（`~6742` 是路径里“盘符以外的非法字符”被转义的结果）。**实测 22 个会话目录，全部只有 `session.v4.jsonl.zstd` 一个文件，没有 lock 文件**（Windows 锁是命名内核信号量，零文件足迹）。

### 2.2 项目目录名 `projectKey(cwd)`【代码】

规则（`lib/index.js:880-899`）：

1. 遍历 cwd 的 UTF-16 code unit；
2. `'/'`、`'\\'`、`':'` → 输出 `'-'`，**连续分隔符折叠成一个**（`separatorRun`）；
3. `[A-Za-z0-9._-]`（且不是 `~`）→ 原样输出；
4. 其他字符（含中文、空格、`~`）→ `~` + 4 位大写十六进制码元（如 `~6742`）；
5. 去掉开头所有 `-`；结果为空则用 `"root"`；
6. `slice(0, 251)` 截断；最后套上 `--…--`。

> ⚠ 该变换**有损且不可逆**（分隔符折叠 + 截断），只用于“人类可读分组”。要还原 cwd 必须读 header 的 `cwd` 字段。

### 2.3 会话目录名 `encodeSegment(id)`【代码】

`lib/index.js:858-870`，对**全部 JS UTF-16 字符串单射**：

- `"."` → `"~002E"`，`".."` → `"~002E~002E"`（防目录穿越）；
- `[A-Za-z0-9._-]` 且非 `~` → 原样；
- 其他每个 code unit → `~XXXX`（4 位大写十六进制）。孤立代理项也按 code unit 保留。

空串直接抛错（`cannot encode an empty path segment`）。

### 2.4 generation 文件名【代码】

```js
CANONICAL_LOG_FILENAME = /^session(?:\.v([1-9][0-9]*))?\.jsonl$/u     // dsh-session-format/lib/index.js:464
sessionFormatLogFilename(v) = v === 0 ? "session.jsonl" : `session.v${v}.jsonl`
logSuffix('zstd') = ".jsonl.zstd" ; logSuffix('none') = ".jsonl"
generationLogFilename(v, compression) = sessionFormatLogFilename(v) + (compression==='zstd' ? '.zstd' : '')
```

要点：

- **v0 不带 `.v0`**，就叫 `session.jsonl[.zstd]`；
- 版本号**禁止前导 0、禁止大写 V**；
- `.tmp`、压缩后缀在解析前先剥离，故 `session.v4.jsonl.zstd.abc123.tmp` 不是规范名；
- **一个 root 只能有一种压缩编码**：启动与定向查找会拒绝另一种后缀的 generation（`rejectOppositeArtifact`）。发现逻辑会把“对侧后缀”的文件视为错误而不是忽略。

### 2.5 选择规则

- **读/写打开**：选数值**最高**的规范 generation（`resolveGenerationInDirectory`）。
- **修改时间**：取所选文件的 `mtime`。
- **`stat()`/`list()`**：只解压**第一帧**（header），不读正文、不跑迁移；因此列表性能与日志大小无关。【代码 `readFirstZstdLine` / `readZstdHeader`】

### 2.6 原子写、fsync、崩溃语义【代码】

创建/首次落盘（`materialize`）：

1. 逐级 `mkdir`（Windows 用 `.dsh-mkdir-<rand>` staging 目录 + `MoveFileExW(MOVEFILE_WRITE_THROUGH)` 发布，POSIX 用 `mkdir` + 目录 fsync，Android 上目录 fsync 失败被容忍）；
2. 编码出 `header 帧 + 首批事件帧`（**两帧，帧边界不合并**）；
3. 写临时文件 `<finalPath>.<12 位十六进制>.tmp`（`open(...,"wx",0o600)`），写入后 `fsync`；
4. 发布：POSIX `link(tmp, final)`（已存在则失败，不覆盖）→ 成功后 `rm tmp`；Android/不支持 hardlink 时退化为 `rename`（目标已由前置检查保证不存在）；Windows `MoveFileExW(MOVEFILE_WRITE_THROUGH)`，不覆盖、不跨卷；
5. POSIX 再 fsync 父目录。

追加（`appendLines`）：

1. `body = eventLines(events) + "\n"`（**批次尾部补一个换行**）；
2. `zstd` 模式压成一个帧追加；`none` 模式直接追加文本；
3. 追加后 `fsync`；
4. **写失败或 fsync 失败 → 回滚到上次字节长度**（避免重试产生重复 seq）。

迁移发布（`publishSuccessor`）：在同目录写 `session.migration.<token><后缀>.tmp`，streaming 压缩（约 1 MiB 切片），`fsync`，Worker 线程完整校验，复查源文件 revision，未变化才以“不覆盖”方式发布为 `session.v5?`（此处为 `session.v4.*`）；**源文件逐字节不变**。

### 2.7 锁【代码】

- 文件名 `session.lock`，位于会话目录内；**只有 POSIX 会创建它**。
- POSIX：`flock(fd, LOCK_EX|LOCK_NB)`，失败（`EAGAIN/EWOULDBLOCK`）→ `SessionAlreadyOwnedError`；加锁后校验 inode 仍是该路径的 inode，否则重试（最多 3 次）；释放只 `close`，**永不删除锁文件**。
- Windows：`CreateSemaphoreW(Local\dsh-session-lock-<sha256(小写绝对路径)>, 1, 1)` + `WaitForSingleObject(0)`；超时即占用；`CloseHandle` 时内核对象销毁，进程崩溃自动释放。
- 读者**从不加锁**。新建会话在**首次落盘前**才加锁，未落盘的会话零文件足迹。

### 2.8 备份 / 回收站

**【代码】内核层没有任何备份、快照、`.bak`、“回收站”实现。** 明确事实：

- 持久化 seam **没有删除接口**（README 原文：日志在 `root` 下累积，直到外部移除）；
- 迁移**只新增 generation，不删除旧 generation**，源文件保持逐字节不变——这本身是一种“格式级历史备份”；
- 写入失败靠“回滚到上次字节长度”而不是备份文件；
- `stat`/`list` 遇到损坏的 generation 只跳过/报错，不做修复。

所以：**如果原生端需要“删除会话 / 回收站”，必须自己实现**。建议（非上游行为）：把会话目录整体 `move` 到 `<root>/../trash/<timestamp>-<id>/`，不要删单个 generation，否则会破坏“最高 generation 可回退”的语义。

## 3. zstd 容器格式

### 3.1 是“整文件压缩”还是“分帧”？

**分帧：多个独立 zstd 帧首尾拼接**（concatenated frames），不是一个大帧，也不是 tar/seekable 格式。

【代码】`zstd.js` 注释原文：*“The backend owns a concatenated-frame container so it can append and recover batches without exposing compression mechanics.”*
【实测】本机 22 个文件共 **13,656 帧**（会话仍在增长，数字为撰写时快照），逐帧 `decompressobj()` 全部成功，且 `unused_data` 恰好落在下一帧的 magic 上；**13,656/13,656 帧的前 6 字节均为 `28 B5 2F FD 04 58`**。

### 3.2 每一帧的生成方式【代码】

```js
CHECKSUM_OPTIONS          = { params: { [ZSTD_c_checksumFlag]: 1 } }
ZSTD_CHECKSUM_OPTIONS     = 同上（迁移写盘用）
compressZstdFrame(input)  = zstdCompress(input, CHECKSUM_OPTIONS)
```

即：Node 内置 `node:zlib` 的 **一次性 zstd 压缩 + 强制 checksum**，**没有设置压缩级别**（用 libzstd 默认级别 3）。

实测帧头（每个文件第一帧起，全部一致）：

```
28 B5 2F FD 04 58 ...
└─ magic ──┘ │  └─ window descriptor
             └─ Frame_Header_Descriptor = 0x04
```

| 字节 | 含义 | 值 |
|---|---|---|
| `28 B5 2F FD` | zstd magic（LE uint32 = `0xFD2FB528` = 4247762216） | 固定 |
| FHD `0x04` | `FrameContentSize_flag=0`（无内容长度）、`Single_Segment=0`、`Checksum_flag=1`、`DictID_flag=0` | 实测恒为 0x04 |
| WD `0x58` | windowLog = 10 + (0x58>>3) = **21**（2 MiB），mantissa=0 | 实测恒为 0x58 |

结论：**帧头 6 字节恒为 `28 B5 2F FD 04 58`**（对 DSH 自己写的文件）。每帧尾部多 4 字节 **XXH64 低 32 位校验和**（由 checksum flag 决定），libzstd/zstd-jni 解码时会自动校验。

> 注意：这 6 字节是“DSH 写出来的样子”，**不是读取时的硬性要求**。读取端按 zstd 规范通用解析（支持有/无 content size、single-segment、dictID），所以原生端写帧时即使带 content size 也仍可被 DSH 读。

### 3.3 分帧规则（写入端必须遵守）【代码】

| 帧 | 内容 |
|---|---|
| 第 1 帧 | **只含 header 行**（含行尾 `\n`）。`assertZstdHeaderFrame()` 强制“首帧明文必须以 `\n` 结尾且只有一个换行” |
| 第 2 帧 | 创建时的首批事件（若创建时就 append） |
| 第 N 帧 | 此后**每次持久化批次一帧**；批内可含 1…N 行 |

【实测】`0309bc11…` 会话：130 行 / 71 帧；每帧行数 `[1, 7, 8, 1, 1, 2, 1, 3, 1, 3, 1, 1, …]`——首帧 1 行（header），创建批次 7~8 行，之后随实时批处理窗口（200 ms）多为 1~3 行。
【实测】13100 帧**全部**以 `\n` 结尾（含最后一帧）。

### 3.4 读取端：帧扫描算法【代码 `scanZstdFrames`, index.js:1305-1368】

不解压、纯结构扫描，**必须逐帧定位**（Kotlin 直接照抄这段逻辑即可）：

```
offset = 0
while offset < len:
    start = offset
    if len - offset < 4: return (frames, tornStart=start)      # 尾部不足 4 字节
    if u32le(offset) != 0xFD2FB528: throw "invalid frame magic"
    offset += 4
    if offset == len: return (frames, tornStart=start)
    fhd = u8(offset); offset += 1
    if fhd & 24 != 0: throw "reserved frame-header bit"
    fcsFlag = fhd >>> 6; single = fhd & 32; checksum = fhd & 4; dictFlag = fhd & 3
    dictBytes = dictFlag == 3 ? 4 : dictFlag
    fcsBytes  = fcsFlag == 0 ? (single ? 1 : 0) : (1 << fcsFlag)
    if len - offset < (single?0:1) + dictBytes + fcsBytes: return torn
    offset += 该长度
    loop:
        if len - offset < 3: return torn
        bh = u24le(offset); offset += 3
        last = bh & 1; type = (bh >>> 1) & 3; size = bh >>> 3
        if type == 3: throw "reserved block type"
        payload = (type == 1) ? 1 : size          # RLE 块只占 1 字节
        if len - offset < payload: return torn
        offset += payload
        if last: break
    if checksum: if len-offset < 4: return torn; offset += 4
    frames.append(start, offset)
```

返回 `tornStart` 表示“最后一帧不完整”，此时 `frames` 是它前面所有**完整**帧。

### 3.5 解压与撕裂尾部恢复【代码 `readZstdPrefix`, index.js:3018-3083】

读取流程（顺序即语义）：

1. `scanZstdFrames(buffer)` → 完整帧列表 + 可选 `tornStart`；
2. 第一帧单独解码，`assertZstdHeaderFrame` 校验“只有一行”；
3. 用这个 header 行构造行扫描器（`SessionLogScanner`），其余完整帧逐帧解码 → 明文追加给扫描器；
4. 全部完整帧喂完后，若**完整帧的明文里还有没被 `\n` 收尾的残行** → 判为损坏（`complete frame contains a torn JSONL record`）；
5. 若有 `tornStart`：对 `buffer[tornStart..]` 用 **`finishFlush: ZSTD_e_flush`** 做“不完整帧解码”，**吞掉异常**，把能解出的字节喂给扫描器；扫描器只保留**以 `\n` 结尾的完整行**；
6. 返回 `{events, tornTruncateTo: tornStart, recoveredTail: 完整帧之后的那些事件}`。

写句柄在**下一次 append 之前**：把文件 `truncate(tornStart)`，并把 `recoveredTail` 重新持久化（保证恢复出的事件不丢）。

> Kotlin 提示：`ZSTD_e_flush` 的语义是“尽量吐出已能解码的数据、不要求帧结束/校验通过”。zstd-jni 若没有直接等价 API，可退化为“丢弃撕裂帧”（DSH 在解码失败时也是这个效果：`recoveredTail` 为空，只保留完整帧）。

### 3.6 解压后还有没有第二层？

**没有。** 明文就是 `\n` 分隔的 UTF-8 JSON 文本，第一行 header，其后每行一个事件。`compression: 'none'` 时文件就是这份明文本身（后缀 `.jsonl`）。

## 4. v4 JSONL 逐行结构

### 4.1 编码通则【代码 + 实测】

| 项 | 规则 |
|---|---|
| 字符集 | **UTF-8 无 BOM**；非 ASCII 原样输出（`JSON.stringify` 不转 `\uXXXX`） |
| 行分隔 | `\n`（0x0A），**没有 `\r`**；每个记录（含最后一条）都以 `\n` 结尾 |
| 序列化器 | `JSON.stringify(value)`：**无空格、无缩进**，键序＝对象插入序 |
| 行内不允许 | 注释、空行、多行 pretty-print |
| 首行 | 必须是 header 记录，且**独占第一帧** |
| 数值 | 只用安全整数（`Number.isSafeInteger`），拒绝 `-0`；`time`、`seq`、`createdAt`、`delegationDepth` 均非负 |
| 未知顶层键 | **拒绝**（header 与事件行都有精确键白名单） |

字段顺序**对读取端不重要**（解析后按键取值），但对“字节级对拍”重要。DSH 的写出顺序固定，见下。

### 4.2 Header 行

键白名单【代码 `format.js:782-796`】：

- 必需：`type`, `version`, `id`, `createdAt`, `isSeeded`, `delegationDepth`
- 可选：`cwd`, `parentSession`, `origin`, `agentPreset`
- 其他一律拒绝。另外**曾经存在但已退役**的两个键 `sandboxMode`、`approvalPolicy` 会被显式点名拒绝（`assertNoRetiredHeaderFields`）。

写出顺序（`toHeaderLine → encodeCurrentHeader → V2 encodeHeader` 再改 version）【代码 + 实测完全一致】：

```
type, version, id, createdAt, [cwd], [parentSession], isSeeded, [origin], delegationDepth, [agentPreset]
```

字段语义：

| 字段 | 类型 | 说明 |
|---|---|---|
| `type` | `"session"` 字面量 | 固定 |
| `version` | 整数 | v4 文件为 `4`；读到非 4 且本 build 只支持到 4 → 抛 `SessionFormatUnsupported`（提示升级，而不是“文件损坏”） |
| `id` | string | 会话 id。**观测约定**：顶层会话形如 `session-<uuid>`，subagent 子会话是裸 `<uuid>`；格式本身不校验 |
| `createdAt` | 安全整数 | Unix epoch **毫秒**（不是秒、不是 ISO 串） |
| `cwd` | string，绝对路径 | 可选；缺失表示“无项目目录”，文件落 `_no-cwd/` |
| `parentSession` | string | 可选；**subagent 会话的直接创建者**。普通 fork 通常省略（历史普通 fork 可能在此保留来源 id）。**不能**用它的存在判断是否 subagent，要用 `origin`【上游 0.2.2 明确】 |
| `isSeeded` | bool | 是否含 fork 继承前缀。**v4 不存数值切点** |
| `origin` | `"subagent"` | 可选；只允许这一个值 |
| `delegationDepth` | 安全整数 ≥0 | 顶层 0，子会话 = 父 + 1 |
| `agentPreset` | string | 可选；agent 预设 id |

**真实样例 1（实测，subagent 会话首帧原文）**：

```json
{"type":"session","version":4,"id":"0309bc11-99c0-437c-8666-bdd87be7e5e7","createdAt":1793977657234,"cwd":"D:\\dsh","parentSession":"session-49c088a5-69f8-45ca-bc0a-1628036d215e","isSeeded":false,"origin":"subagent","delegationDepth":1,"agentPreset":"standard"}
```

（`cwd` 在 JSON 里是 `D:\\dsh`，即字符串 `D:\dsh`；时间戳 `1793977657234` = 2026-11-06 23:07:37 +08:00。）

### 4.3 事件行（信封）

键白名单【代码 `v1-to-v2/lib/index.js:163-174`，v4 复用】：

- 必需：`type`, `seq`, `time`, `data`
- 可选：`ignorable`, `sourceEventSeqs`, `surfaceOp`
- **其他键一律拒绝**（`has unexpected field …`）

写出顺序（实测 3 种组合全量统计）：

```
① type, seq, time, data
② type, seq, time, data, sourceEventSeqs, surfaceOp
③ type, seq, time, data, surfaceOp
```

`ignorable` 若出现，插在 `data` 之后、`sourceEventSeqs` 之前（`SessionEvent` 接口声明序）。

| 字段 | 规则 |
|---|---|
| `type` | string。必须是**已知事件类型**，或带 `ignorable:true` 的未知类型（未知且非 ignorable → 整个会话拒绝重建） |
| `seq` | 安全整数，**从 0 开始、严格连续**（跳过即“seq gap”，recoverable 模式会丢弃该行及其后直到下一个 `turn/end`） |
| `time` | 安全整数，epoch 毫秒 |
| `data` | 任意 JSON；具体结构由 `type` 决定（见 §4.6） |
| `ignorable` | 存在时必须**恰好为 `true`**；`false` 是错误 |
| `sourceEventSeqs` | 仅 surface 事件允许（`assistant/message` 禁止）；**区间压缩**，见 §4.4 |
| `surfaceOp` | 仅 surface 事件**必须**有；`"append"` 或 `{"op":"replace","startSeq":N,"endSeq":M}` |

**surface 事件集合（v4）**：`system/message`、`developer/message`、`user/message`、`assistant/message`、`tool/result`。其余类型**禁止**携带 `surfaceOp`/`sourceEventSeqs`（带了解析即拒绝）。

### 4.4 `surfaceOp` 与 `sourceEventSeqs`

`surfaceOp`：

```json
"append"
{"op":"replace","startSeq":2490,"endSeq":2494}
```

- 只允许 `op/startSeq/endSeq` 三个键，`op` 只能是 `"replace"`；
- 端点按**当前 surface 顺序**取闭区间，不按 seq 大小比较；
- `startSeq === endSeq` 表示替换单个节点；
- 被替换掉的每个 surface 节点都必须出现在 `sourceEventSeqs` 里。

`sourceEventSeqs` **区间压缩（关键坑）**：

编码规则【代码 `encodeSeqRanges`, v1-to-v2:327-342】：

```
若 values 严格递增：
  扫描连续段；连续长度 >= 3（end-start>=2）→ 输出 [start, end]
                连续长度 == 2            → 输出 start, end 两个裸数字
                单点                     → 输出该数字
否则（非严格递增）：原样输出扁平数组
```

举例：`[3,4,5,6,9]` → `[3,6],9`；`[3,4,9]` → `3,4,9`；`[5]` → `5`。

解码规则：元素是数字 → 直接收；元素是**长度为 2 的数组 → 展开为闭区间**（`[a,b]` → a…b）。所以：

> ⚠ **JSON 里出现 `[a,b]` 时永远是区间，不是“两个引用”**。扁平写法里两个引用必须是两个独立数字 `a,b`。
> 解码后还要求：全部 < 当前行的 `seq`、互不重复。

## 5. 版本历史 v0 → v4

### 5.1 总表

| 版本 | 物理 header | 行结构 | 关键语义 |
|---|---|---|---|
| **v0** | `version:0`，**`seedLength`（数值切点）** | 事件行 + **packed assistant chunk 行** | `steering/message`、`compact/*` 命名；`request/header.header.system`；无确定性消息 id |
| **v1** | `version:1`，`seedLength` | 同上 | v0 的规范化结果（仍是 packed 行） |
| **v2** | `version:2`，**`isSeeded`（无 seedLength）** | **每行一个事件**；`sourceEventSeqs` 区间压缩 | assistant 流**内嵌**到 `assistant/message.stream`；切点由 `session/end-seed` 推导 |
| **v3** | `version:3` | 同 v2 信封 | **系统提示提升为 `system/message` 头节点**；`surfaceOp` 端点为 `startSeq/endSeq`；PTC 改名；`plugin:` 命名空间；预设 `code→ptc` |
| **v4** | `version:4` | 同 v2 信封 | **`tool/result` 用 `role:"tool"`**；`source` 的 `kind/plugin` 归一；`developer/message` 与 tool-addition；父目录 `subagent/catalog` |

### 5.2 v0 细节【代码 `v0-to-v1/lib/index.js:1595-1863`】

物理 header 键：

- 必需：`type`, `version`, `id`, `createdAt`, `delegationDepth`
- 可选：`cwd`, `parentSession`, **`seedLength`**, `origin`, `agentPreset`

```jsonc
{"type":"session","version":0,"id":"…","createdAt":1730000000000,"cwd":"/home/u/p","seedLength":42,"delegationDepth":0}
```

规则：`isSeeded = (seedLength !== undefined)`；`inheritedEventCount = seedLength`（缺省 0）。

> v0 日志里的 `subagent/descriptor` 允许 `version ∈ {1,2,3}`（本地 0.2.1 只认 3，上游 0.2.2 放宽）；`version 1` 的键集合是 `{version, provider, label?}`，`version 2/3` 才带 `mode`。读 v0 时不要只接受 v3 描述符，否则会判“不支持迁移”。

**packed 行**（v0/v1 特有，用于压缩连续的 assistant 增量）：

```jsonc
{"type":"text-chunks","seq0":120,"time0":1730000000123,
 "data":{"turn":1,"step":1,"index":0,"dt":[3,5,2],"texts":["Hel","lo ","wor","ld"]}}
{"type":"reasoning-chunks","seq0":140,"time0":1730000000200,
 "data":{"turn":1,"step":1,"index":0,"dt":[1,1],"texts":["…","…"]}}
{"type":"tool-call-chunks","seq0":160,"time0":1730000000300,
 "data":{"turn":1,"step":1,"index":0,"id":"call_x","name":"bash","dt":[2],"args":["{\"comm","and\":\"ls\"}"]}}
```

- 标签集合：`text-chunks` / `reasoning-chunks` / `tool-call-chunks`；
- 行内只有 4 个键：`type, seq0, time0, data`；
- `data.dt` 长度 = `payload.length - 1`，是相邻成员的时间**增量**（`time[i] = time0 + Σdt[0..i-1]`）；
- 一条 packed 行展开成 `payload.length` 个 `assistant/chunk` 事件，seq 从 `seq0` 连续递增；
- `tool-call-chunks` 的 `data` 有 `id`（必填）、`name`（可选）、`args`；其余两类是 `texts`。
- 【本地没有 v0/v1 文件可比对，上述结构直接来自 codec 校验逻辑，属【代码】而非【实测】】

**v0 事件语义差异**（v0→v1 的“有限规范化”）：

- `steering/message` → `user/message`；
- `compact/*` → `compaction/*`；
- 删除 `turn/start.trigger`；
- 转换已停用的 `turn/end` reason；
- 给旧消息、retry chain、compaction 组**补确定性 id**；
- 删除 `request/header.header.messagePrefix`；
- 遇到 `request/header-delta`、`mode/set`、`request/header` 的 fallback reason → **迁移失败**（不是修复）。

### 5.3 v0 → v1

**恒等迁移**：只把 `version` 从 0 改成 1，其余逐字节保留（校验通过后）。因此 v1 文件 = v0 文件 + 版本号。

### 5.4 v1 → v2（基数改变：事件数会变）

- 消费顶层 `assistant/chunk`（含 packed 行展开的），把**完整有序**的 chunk 流**内嵌**到对应 `assistant/message.stream`，删除顶层 chunk 事件；
- 未被任何 message 认领的 attempt → 在其最后一个 chunk 位置生成 `assistant/attempt`（仅日志）；
- 已结算事件据此**重新稠密编号**，并重写所有同日志引用（`sourceEventSeqs`、`surfaceOp` 端点、`command/done.sourceEventSeq`、compaction 的 `shadowedRange/shadowedSeqs`、title 的 `messageSeqs`）；
- 物理 header 从 `seedLength` 改为 `isSeeded`，切点改由 `session/end-seed {inherited:true}` 表达（目标用最后一个带标记的 marker 的 **seq** 作为继承数，不含该 marker）；
- **每行只写一个事件**（不再有 packed 行）；
- `sourceEventSeqs` 开始用区间压缩；
- 附带修复：`next-turn` inbox 插入后紧跟下一个 `turn/start` 但前一轮缺 `turn/end` → 补一个 `reason:"interrupted"` 的 `turn/end`。

### 5.5 v2 → v3

- **系统提示从 header 提升为 surface 头节点**：首个 `step/start` 之后立即追加空 `system/message`；每次 `request/header` 的 `data.header.system` 与当前提示比较，变化则在 header 之前插入系统消息替换头节点；**所有 `request/header.data.header.system` 都被移除**；
- 合成消息 id：`"v2-to-v3-system-" + sha256hex(JSON.stringify(["session-format-v2-to-v3", id, anchorSeq, anchorType]))`；
- surface 替换端点由 `{op:"replace",start,end}` **改名**为 `{op:"replace",startSeq,endSeq}`；
- `tool/code-dispatch-start` → `tool/ptc-dispatch-start`，`tool/code-dispatch` → `tool/ptc-dispatch`；`source.plugin:"tools-code-mode"` → `"tools-ptc"`；
- `agentPreset` 的 `code` → `ptc`；
- 忽略 `request/header.header.tools: []` 与 `adapterDefaults: {}`（必须省略）；
- 四种 surface（system/user/assistant/tool-result）都**必须**有 `surfaceOp`；仅 assistant 禁止 `sourceEventSeqs`。

### 5.6 v3 → v4（本文重点）

1. **工具结果提升**（`liftToolResult`）：

   v3（user 角色 + `tool-result` 包装块）：
   ```jsonc
   {"type":"tool/result","seq":9,"time":…,"data":{"turn":1,"step":1,
     "message":{"role":"user","id":"m1","source":{"kind":"tool","callId":"c1"},
       "content":[{"type":"tool-result","toolCallId":"c1","content":[{"type":"text","text":"ok"}],"isError":false}]}}}
   ```
   v4：
   ```jsonc
   {"type":"tool/result","seq":9,"time":…,"data":{"turn":1,"step":1,
     "message":{"role":"tool","id":"m1","source":{"kind":"tool","callId":"c1"},
       "toolCallId":"c1","content":[{"type":"text","text":"ok"}],"isError":false}}}
   ```
   包装块消失；`content` 直接成为消息 content；`isError` 变为可选消息字段；**id 与 callId 不重建**。
   包装块其它字段 → `plugin:result:<原名>`；外层消息除 `id/role/source/content` 外的字段 → `plugin:message:<原名>`。

2. **消息来源归一**（`source.kind`）：
   | v3 | v4 |
   |---|---|
   | `{kind:"plugin", plugin:"compact"}` | `{kind:"compact-checkpoint"}` |
   | `{kind:"plugin", plugin:"tools-code-mode"\|"tools-ptc"}` | `{kind:"ptc-mode"}` |
   | `{kind:"plugin", plugin:"dsh-compaction-basic"}` | `{kind:"compact-basic"}` |
   | system 角色 + `@deepseek-ai/dsh-system-prompt` | `{kind:"system-prompt"}` |
   | 其它角色 + 同上 | `{kind:"runtime-context"}` |
   | 第一方同名生产者（`agent-instructions`、`goal`、`skill-invocation`、`subagent-report`、`user-approval`、`schedule`…） | 同名 `kind` |
   | 其他插件 | `{kind:"plugin:<原 plugin 字符串>"}` |

3. **未知可忽略事件重命名**：v3 的未知 ignorable `type` → `plugin:<原 type>`；嵌套 payload 原样。
4. **内容块标签**：v3 未知 `type` → `plugin:<原 type>`（`text/reasoning/image/file/tool-call/tool-result` 六种保留）。
5. **补齐中断回合**：若回合仍开放但无开放 step，且紧接着是非空 `next-turn` 的 `agent/inbox/spliced`，则在下一个 `turn/start` 之前插入 `turn/end{reason:{kind:"interrupted"}}`（time 取该 start 的时间）；
6. **父目录前置证据**：为缺少自身 `subagent/catalog` 项的父子关系追加目录事实（`version 0/1`，按证据完整度决定 mode；无证据则记 `unknown` 模式），追加在**所有源事件之后**，按创建时间 + childId 排序，seq 连续；
7. **序号重映射**：插入后所有后续事件重新稠密编号，并重写 `sourceEventSeqs`、`surfaceOp.startSeq/endSeq`、`command/done.sourceEventSeq`、`session/title(.llm-request).messageSeqs`、`compaction.{summary,prune}.{shadowedRange,shadowedSeqs}`、`image/offload.targets[].seq`。**不重写**：`throughSeq`/`sessionFormatVersion`（投递坐标）、`capturedThroughSeq`、turn/step 编号、流块索引、token/字节计数、任意 id。
8. **投递代际**：v3 源 marker 若声明 `sessionFormatVersion: 4` → 拒绝（不能借迁移激活目标代 watermark）；代际 3 的 marker 校验 `throughSeq` 更早且会话归属；其它代际原样保留。
9. **拒绝项**：退役 `tool-result` 包装出现在非 canonical 位置、`tool/code-dispatch*` 作为 required 事件、`request/header.header.system`、`deferLoading` 出现在 v3 请求工具定义里。

> **最重要的一点**：v3→v4 **不是**“读时自动升级并回写”。读路径永远不发布后继；只有**以写模式打开历史会话**时才会发布 v4 后继文件，源 v3 文件逐字节保留。

### 5.7 迁移链的运行方式【代码 `session-format`】

```
readHeader(物理 header) → { status: "current" | "migration-required" | "unsupported" | "malformed", storedVersion, targetVersion }
createRestore(header, {recovery:'strict'|'recoverable', validation:'transformed'|'current'})
   → decodeRow(row) … finish() → {header, inheritedEventCount, events}
```

- 链必须**唯一、连续、无缺口**：`[v0→v1, v1→v2, v2→v3, v3→v4]`；
- 每个 Stage 只有**有界状态**（不保留整份历史），逐事件 `transformEvent`；
- `finish()` 时做目标校验；
- 若已存版本 == 当前版本 → **完全跳过迁移**（所以同版本新增必须向后兼容）；
- 迁移失败分类：`SessionFormatError`（文件损坏/格式错）vs `SessionFormatUnsupportedMigrationError`（能读懂但拒绝迁移）→ 后者在上层包成 `SessionFormatUnsupported`，**绝不修改源文件、绝不发布半个后继**。

## 6. 写 v4 必须满足的条件（checklist）

写之前逐条自检，任一不满足 DSH 会判“损坏”或“需要升级”：

**文件级**

- [ ] 文件名 `session.v4.jsonl` / `session.v4.jsonl.zstd`（小写 v、无前导 0）；同一 root 不混用两种后缀。
- [ ] 第 1 个 zstd 帧的明文**恰好一行**（header），以 `\n` 结尾。
- [ ] 每个帧都能独立解码（标准 zstd 帧，DC 块/压缩块/RLE 块均可），带不带 checksum 都能被读（DSH 自己写带 checksum）。
- [ ] 每个帧的明文以 `\n` 结尾；整个文件拼接后**没有空行**、没有残行。
- [ ] 追加时只能**在文件末尾追加新帧**，绝不重写已有帧（崩溃后可回滚到上次长度，但已提交内容不改）。

**header 行**

- [ ] `type:"session"`、`version:4`、`id`、`createdAt`、`isSeeded`、`delegationDepth` 全在。
- [ ] 可选键仅 `cwd/parentSession/origin/agentPreset`，`origin` 只能是 `"subagent"`。
- [ ] 没有 `seedLength`、`sandboxMode`、`approvalPolicy` 等退役键。
- [ ] `isSeeded:true` 时日志里必须有 `session/end-seed{inherited:true}`；`false` 时**必须没有**该标记。

**事件行**

- [ ] `seq` 从 0 开始、逐个 +1、无空洞（含 `assistant/attempt` 这类 log-only 事件）。
- [ ] `time` 为 epoch 毫秒安全整数。
- [ ] 顶层仅 7 个允许键；`ignorable` 只能是 `true`。
- [ ] surface 五类事件必须带 `surfaceOp`；非 surface 事件必须不带 `surfaceOp`/`sourceEventSeqs`。
- [ ] `assistant/message` 不得带 `sourceEventSeqs`。
- [ ] `sourceEventSeqs` 里的引用都 `< seq`、互不重复；区间写法符合 §4.4。
- [ ] `tool/result` 的 `message.role="tool"`、`toolCallId` 与 `source.callId` 一致、`content` 是数组、不含 `tool-result` 包装块；`data.error` 只在 `isError:true` 时出现。
- [ ] `request/header` 不含 `header.system`；空的 `tools`/`adapterDefaults` 省略；`reason` ∈ 四值。
- [ ] 未知事件类型必须带 `ignorable:true`。

**语义级（DSH 会做关系校验，原生端可以只做“宽容读”，但写回时建议照做）**

- [ ] turn/step 编号单调、开放/闭合配对；`tool/call` 后必须有结算（或留作开放尾部）。
- [ ] 替换（`replace`）区间必须覆盖当前 surface 上真实存在的节点，且 `sourceEventSeqs` 覆盖全部被替换节点。
- [ ] 受保护的 system 头节点只能被“恰好覆盖该头节点”的 system 消息替换。

**编码细节**

- UTF-8 **无 BOM**；`\n` 而不是 `\r\n`；JSON 紧凑无空格。字段顺序不影响可读性，但如果要做字节级对拍，按 §4.2/§4.3 的顺序写。

### 8.2 zstd-jni 用法

依赖：`com.github.luben:zstd-jni`（有 Android ABI 产物；注意 .so 打包与 16KB page size 兼容）。

**(a) 解压整个文件**：不要用 `Zstd.decompress(src, size)`（帧里**没有 content size**，算不出目标大小）。用**逐帧流式**：

```kotlin
// 1) 先结构性扫描，得到每个完整帧的 [start,end) 与 tornStart
val scan = ZstdFrames.scanFrames(bytes)          // 见 §3.4 伪码
// 2) 逐帧流式解压（zstd-jni 的 InputStream 会自动校验帧尾 checksum）
fun decompressFrame(frame: ByteArray): ByteArray {
    ZstdInputStream(ByteArrayInputStream(frame)).use { ins ->
        return ins.readBytes()
    }
}
// 3) 首帧必须只有一行
check(firstFramePlaintext.count { it == '\n'.code.toByte() } == 1 &&
      firstFramePlaintext.last() == '\n'.code.toByte())
```

> `ZstdInputStream` 默认会**跨帧连续读取**；因为我们是“一帧一喂”，不会误跨。若图省事直接把整个文件丢给 `ZstdInputStream(FileInputStream)`，它会读完全部帧——**但这样就拿不到 tornStart，无法做撕裂恢复与“首帧仅 header”校验**，因此仍建议先扫描。

**(b) 撕裂尾部（可选增强）**：对 `bytes[tornStart..]` 单独尝试流式解码，`catch (IOException)` 后保留**已产出的字节**；再按行切分，只留以 `\n` 结尾的完整行。失败就丢弃该帧（DSH 行为等价：`recoveredTail` 为空）。

**(c) 写帧**：需要**不带 content size、带 checksum**的帧（与 DSH 一致）：

```kotlin
fun compressFrame(plain: ByteArray): ByteArray {
    val out = ByteArrayOutputStream()
    ZstdOutputStream(out).use { z ->
        z.setLevel(3)          // libzstd 默认级别，DSH 未显式设置
        z.setChecksum(true)    // 关键：对应 DSH 的 ZSTD_c_checksumFlag=1
        z.write(plain)
    }
    return out.toByteArray()
}
```

- **不需要**追求与 DSH 字节完全相同：读取端按 zstd 规范通用解析，带 content size / single-segment 的帧也能读。
- 但**必须**：每帧独立可解、帧内明文以 `\n` 结尾、首帧只含 header。
- 一个批次一帧（不要把整个文件压成一帧，也不要把一帧拆成多段分别 append 后忘了 flush）。

**(d) 追加与 fsync**：`FileChannel.open(path, WRITE, APPEND)` → `write(frame)` → `force(true)`；失败时 `truncate(previousSize)` 再抛。

### 8.3 旧版可读性怎么验

1. **单元级**：对每个版本各准备 1 个“黄金文件”（v0/v1/v2/v3 可以从上游测试 fixture 或自己用迁移写出），断言：
   - `readHeader()` 返回 `storedVersion=0..3, status="migration-required"`；
   - 全链迁移后得到与 v4 期望**逐字段相等**的 artifact；
   - 迁移不修改源文件（比对 mtime/哈希）。
2. **对拍级**：用 DSH 本机真实 v4 文件（`C:\Users\user\.dsh\sessions\**\session.v4.jsonl.zstd`）做“读→内存模型→再序列化”，与源码里 `eventLines()` 的输出做 diff（注意字段顺序，见 §4.3）。
3. **写入级（最关键的保险）**：Kotlin 写出的 v4 文件，**用 DSH 自己打开**（`open(id,'read')` / `list()`）。这是唯一能证明“写对了”的验收。建议在原生端加一个“自检导出”按钮：把内存会话写成 `.jsonl.zstd` 到临时 root，再由 DSH 读。

### 8.4 坑清单

1. **`[a,b]` 永远是区间**，不是两个值（§4.4）。
2. **首帧 header-only**：把 header 和首批事件压进同一帧 → 整文件 `corrupt Zstandard session log: first frame is not exactly one header line`。
3. **末行必须换行**：`eventLines(events)` 返回值**不含**尾换行，写盘时要 `+ "\n"`；漏了会变成“残行”被当作撕裂。
4. **不要给行加字段**：`{"...","_note":"x"}` 直接判损坏。
5. **`version` 必须精确等于 4**：写 5 会被当“来自更新版本”→ 拒绝读取。
6. **`isSeeded` 与 `end-seed` marker 必须一致**：`isSeeded:true` 却没有 `inherited:true` 标记 → 恢复失败。
7. **surface 事件漏 `surfaceOp`** → 关系校验失败；非 surface 事件**多** `surfaceOp` → 行解码失败。
8. **`sourceEventSeqs` 引用未来事件** → 拒绝。
9. **`seq` 有洞**（例如跳过 `assistant/attempt`）→ recoverable 模式下该行及后续被丢弃。
10. **路径转义**：会话 id 不能直接拼路径（`../`、`:`、中文）。必须走 `encodeSegment`。
11. **一个 root 一种压缩**：既有 `.jsonl.zstd` 又有 `.jsonl` 的 root 会被判为“对侧产物”错误。
12. **别碰 `session.lock`**：POSIX 上删掉别人正在持有的锁文件会破坏互斥（DSH 自己也不删）。

## 9. 版本相关性清单 & 未来 v5 适配建议

### 9.1 哪些字段/行为是“版本相关”的（不要写死）

| 位置 | 版本相关点 | 兼容写法 |
|---|---|---|
| header.`version` | 决定 codec 与迁移链 | 读出来当**分发键**；仅当写新文件时用 `CURRENT` 常量 |
| header.`seedLength` | 仅 v0/v1 | 只在 v0/v1 解码器里读；v2+ 用 `isSeeded` + marker |
| header.`isSeeded` | v2+ | — |
| 行存在性 | v0/v1 有 packed 行 | 行解码器返回“事件或 run”，扫描器负责展开 |
| 事件 `type` 集合 | 逐版本增长（`developer/message` 仅 v4；`tool/code-dispatch*` 仅 v0–v2） | 用**版本化词汇表**，不要全局 `when(type)` |
| `source.kind` | v3 之前是 `{kind:"plugin",plugin:X}` | 归一化函数按版本挂 |
| `surfaceOp` 端点名 | v2 `start/end`；v3+ `startSeq/endSeq` | 在迁移里改名，逻辑层只认 `startSeq/endSeq` |
| `request/header.header.system` | ≤v2 有；v3+ 退役 | 逻辑层不存该字段 |
| `tool/result` 表示 | ≤v3 user 角色 + 包装块；v4 tool 角色 | 逻辑层只认 v4 形态，v3 由迁移提升 |
| `assistant/chunk` 顶层事件 | 仅 v0/v1 | 逻辑层只认 `assistant/message.stream` |
| 未知事件命名 | v4 用 `plugin:` 前缀 | 保留前缀，不解释 |
| 投递 marker 的 `sessionFormatVersion` | 是“上传代际”，与文件格式版本**同名不同义** | 分开命名，别混用 |
| 压缩后缀 | 与 root 配置绑定 | 读时两种都试；写时跟 root 配置 |

### 9.2 v5 来了怎么扩展（不改现有代码）

原则：**“物理层稳定、版本层可插拔、逻辑层只认当前版本”**。

1. **物理层（帧/行/JSON）不要耦合版本**：`ZstdFrames`、`JsonlScanner` 只认“帧 + 行”，不认事件语义。v5 若仍是 v2 式信封，物理层零改动。
2. **版本注册表**：
   ```kotlin
   object Catalog {
       const val CURRENT = 4
       val codecs = mapOf(0 to CodecV0, 1 to CodecV1, 2 to CodecV2, 3 to CodecV3, 4 to CodecV4)
       val edges  = listOf(V0V1, V1V2, V2V3, V3V4)
       fun chain(from: Int, to: Int = CURRENT): List<Migration>   // 必须连续，否则报“不支持”
   }
   ```
   新增 v5 = 新增 `CodecV5` + `V4V5` + 改 `CURRENT`，**其他文件不动**。
3. **未知版本必须“拒绝而不是猜”**：`version > CURRENT` → 抛“需要升级客户端”，UI 提示升级；**不要**尝试按 v4 解析。
4. **写盘只写 `CURRENT`**：打开旧会话写时，先跑迁移链 → 得到当前版本 artifact → 发布新 generation 文件（`session.v5.jsonl.zstd`），旧文件保留。
5. **前向兼容读**：遇到 `ignorable:true` 的未知事件 → 原样保留（写回时也原样写），**不要丢弃**；遇到未知 required 事件 → 拒绝整个会话。
6. **字段级宽松**：payload 里未知的**嵌套**字段保留（很多是 `plugin:` 扩展），只有**顶层信封**键做严格白名单——这正是 DSH 的策略。
7. **回归护栏**：把 §8.3 的三个层级做成 CI；再加一条“v4 黄金文件字节回归”，防止无意中改动序列化顺序。

### 11.2 逐项差异（上游 = 0.2.2-rc.1）

**(1) `dsh-session-persistence-jsonl`**

- `stat()` / `list()` 的返回快照新增 `location: { kind: "jsonl", path }` 字段（**API 变化，与文件无关**）。原生端如果要对齐上游 `stat/list` 语义，需要带上该字段；不影响读写文件。
- 两处注释把 Node 版本矩阵从 “22/24/26” 改成 “24/26”。

**(2) `dsh-session-format-v3-to-v4`：投递标记归属校验放宽**

```diff
- local:  if (deliveryId !== void 0 && !(header.parentSession !== void 0 && event.seq < inheritedEventCount) && deliveryId !== header.id) throw …
+ upstream: if (deliveryId !== void 0 && event.seq >= inheritedEventCount && deliveryId !== header.id) throw …
```

即：继承前缀内（`seq < inheritedEventCount`）的 `session-log-deepseek/delivery-accepted`，上游**不再要求**父会话存在，只要不是本会话 id 就接受。**只影响校验，不影响字节**。移植时建议按上游（更宽松）实现。

**(3) `dsh-session-format-v0-to-v1`：v0 历史日志里的 `subagent/descriptor` 兼容面扩大**

- 本地只接受 `version === 3`；上游接受 **`version ∈ {1, 2, 3}`**：
  - `version 1`：键集合 `{version, provider, label}` + 允许组合字段 `agentProvider/agentModel/persona/toolFilter`；
  - `version 2/3`：`mode` 可为 `one-shot` 或 `continuable`；
  - 非 `version 3` 的描述符对 `label` 等字符串放宽为“允许空串”，且不再强制 `agentProvider`/`agentModel` 成对；
  - `version 3` 仍保持严格校验。
- `instantValue()` 改用 `@deepseek-ai/dsh-util-time` 的 `fourDigitYearEpoch()`（等价于原来的 UTC 规范时刻正则 + 往返校验）。
- 影响：如果原生端要读**很老的 v0 日志**，必须接受 descriptor v1/v2，否则会判“不支持迁移”。

**(4) `dsh-session` 类型注释（语义澄清，无格式变化）**

- `parentSession` 的语义被明确为：**“subagent 会话的直接创建者；普通 fork 通常省略该字段（历史普通 fork 可能保留来源 id 在这里）。仅凭该字段存在不能判定是 subagent，要用 `origin`。”**
- `turn/end{kind:"error"}` 的 `code` 新增 `TOOL_ACTIVATION_FAILED`（工具条件失败），其余仍 `UNKNOWN`。
- system 消息规范化：新 series 若最新存活节点已是该渲染，则**原地保留**，不再重写头节点。

### 11.3 对移植的净影响

1. **读写 v4 的代码完全不需要改**：帧格式、文件名、header 键、行信封、`sourceEventSeqs` 区间压缩、撕裂恢复策略全部一致。
2. 若原生端实现 `stat/list` 的对外模型，补一个 `location` 字段以对齐上游。
3. 若原生端支持读 v0，`subagent/descriptor` 要接受 v1/v2/v3。
4. 关系校验按“seq < inherited 且 id 不等于本会话”接受外部投递标记。
5. 语义上把 `parentSession`（创建者）与 `origin`（是否 subagent）分开处理，不要再用 `parentSession != null` 推断子会话。

1. `SESSION_FORMAT_VERSION` 是否仍为 4；
2. `CANONICAL_LOG_FILENAME` 是否仍为 `^session(?:\.v([1-9][0-9]*))?\.jsonl$`；
