## 六、工作流 C：bash + curl + CA + PATH 桥

### 6.1 先做真机 exec 验证（半天，决定路线）

Android app 私有目录 `files/` 对 `execve` 是禁止的（targetSdk 34）。可执行体只能放
`nativeLibraryDir`（jniLibs 由系统解压）。先验证：

1. 把任一 ELF（如 `libnode.so`）从 `nativeLibraryDir` 直接 exec：P0 已证明可行。
2. 在 `files/toolchain/bin` 建 `bash -> nativeDir/libbash.so` 的 symlink，exec 该 symlink；
   - 成功 → 用 symlink + PATH。
   - 失败 → 用 `BASH_ENV` 函数/绝对路径兜底（见 6.4）。
3. 若 symlink 失败，**不要**把二进制复制到 `files/` 再 exec，必然失败。

### 6.2 二进制来源

- **curl**：`D:\dsh\build\android-app\staging\runtime\bin\curl`（308,272 B）+ `lib/libcurl.so` 及
  `libnghttp2/nghttp3/ngtcp2/ngtcp2_crypto_ossl/libssh2/libpcre2-8/libssl/libcrypto/libz/libc++_shared`。
  先用 NDK `llvm-readelf -d` 核对依赖；记 SHA256。也可换 Termux 的 curl 包。
- **bash**：Termux aarch64 `bash` 包（GPLv3）；核依赖（libtinfo/libiconv/libandroid-support 等），
  缺什么补什么。旧项目的 `staging/bin/bash` 只是 `exec /system/bin/sh` 的 42 字节 wrapper，**不能用**。
- **CA**：Mozilla `cacert.pem`（curl.se 的 cacert.pem），放 `assets/toolchain/cacert.pem`，记 SHA256。
- **许可证**：bash 是 GPLv3、curl 是 MIT、CA 是 MPL；APK 的 NOTICE/关于页要加来源与许可证文本；
  bash 需要提供对应源码获取方式（至少写清上游地址与版本）。不要声称全是 LGPL。

### 6.3 打包与 PATH

- `app/src/main/jniLibs/arm64-v8a/`：
  - `libbash.so`（bash 可执行体，ELF）
  - `libcurl-bin.so`（curl 可执行体）
  - `libcurl.so`、`libnghttp2.so`、`libnghttp3.so`、`libngtcp2.so`、`libngtcp2_crypto_ossl.so`、
    `libssh2.so`、`libpcre2-8.so`、`libssl.so`、`libcrypto.so`、`libz.so`、`libtinfo.so`（按实际依赖）
  - 注意：`lib*.so` 才会被 jniLibs 打包；`libcrypto.so.3` 这种名字不会被打进去，必要时改名/补依赖。
- `assets/toolchain/`：`cacert.pem`、`bash_env.sh`（可选）、`toolchain.json`（版本/SHA）。
- 首次启动解压**只解非可执行文件**到 `files/toolchain/`（CA、脚本）；可执行体直接用 `nativeLibraryDir`。

## 七、工作流 D：缓存命中（按 DSH 对齐）

### 7.1 已查到的 DSH 事实

上游 `@deepseek-ai/dsh-llm-deepseek`（0.0.1-rc.1，npm）是 **OpenAI chat/completions** 适配器：

```js
const cacheRead = usage.prompt_tokens_details?.cached_tokens ?? usage.prompt_cache_hit_tokens
return {
  inputTokens: usage.prompt_tokens - (cacheRead ?? 0),  // 注意：减掉缓存
  outputTokens: usage.completion_tokens,
  ...(cacheRead !== undefined ? { cacheReadTokens: cacheRead } : {}),
}
```

README 明确：`prompt_tokens = prompt_cache_hit_tokens + prompt_cache_miss_tokens`（两者不相交）；
**模型/路由/系统提示/schema/前缀/历史任何变化都会让缓存从第一个变化 token 开始失效**。

我们现在的差异：
- 内置 DeepSeek 走的是 **Anthropic Messages** 通道（`https://api.deepseek.com/anthropic`），

- `OpenAiClient.parseUsage` 把 `inputTokens = prompt_tokens`（含缓存），与 DSH 的「减掉缓存」语义相反；
  `TokenUsage.totalTokens = input + output`，在 Anthropic 通道下会少算 cache。
- 这两点会直接让「缓存读取」显示/计费口径不对，也可能让用户觉得贵。

### 7.2 诊断（先做，不要盲改）

1. 在 `TurnEngine`/`LlmClient` 加 debug（仅 debug 包，`--ez dsh_cache_debug true` 开）：
   - 每个 step 落一行到 `files/cache-debug.jsonl`：provider、model、system 文本 SHA256、tools JSON SHA256、
     messages 前缀 SHA256、`inputTokens/outputTokens/cacheRead/cacheCreation`、请求号。
2. 同一段 3 轮对话，分别用：
   - 内置 DeepSeek（Anthropic 通道）
   - 临时切到 OpenAI 兼容通道（`https://api.deepseek.com` + `/v1/chat/completions`）
   比较第 2/3 轮的 `cacheRead` 和费用。
3. 若 Anthropic 通道 cacheRead 恒为 0、OpenAI 通道 >0 → **内置 DeepSeek 改用 chat/completions**
   （与 DSH 同一条路）；Anthropic 通道保留给显式选择/兼容，不删。
4. 同时检查前缀稳定性：`TimeContext` 每 10 分钟才追加（正常）；确认 `PromptPack`/工具表/插件段
   没有每次请求都变的字段（排序、时间、随机 id）。有就修。

### 7.3 统计口径（按 DSH）

- `TokenUsage` 改成与 DSH 同语义：`inputTokens` = **未缓存输入**；`cacheReadTokens` 单独；`totalTokens`

## 八·补、工作流 G：`write` / `edit` 大输入上限（用户 2026-11-23 追加）

### 8.4.1 现象与根因

`core/engine/ToolInputGuard.kt` 是 M88-G 加的限制：普通工具 64KB，`write` / `edit` **512KB**。
超限时返回「工具输入过长：… 本次调用未执行」，回合不中断，让模型拆小重试。

用户反馈：**512KB 还是太小，实际使用仍会撞上。** 注意有两种不同的失败，不要混：

1. **守卫拒绝**：完整 JSON 已到，但字节数 > 512KB → 现在这条文案；
2. **模型输出截断**：`max_tokens` 把 tool_use 参数截半，JSON 不完整 → 走 `ToolInputGuard.INVALID_JSON_MESSAGE`
   或引擎的 `MAX_TOKENS` 收口，**即使把上限调到 1GB 也修不了**。大文件必须分段写。

### 8.4.2 Operit 的 `write_file` 是怎么做的（参考）

看了上游 [Operit 的 StandardFileSystemTools](https://github.com/AAswordman/Operit/blob/main/app/src/main/java/com/ai/assistance/operit/core/tools/defaultTool/standard/StandardFileSystemTools.kt)：

```kotlin
val append = tool.parameters.find { it.name == "append" }?.value?.toBoolean() ?: false
if (append && file.exists()) file.appendText(content) else file.writeText(content)
```

配套行为：
- `write_file` 的 schema 有 `path` / `content` / `append` / `environment`；`append` 默认 false；
  追加到不存在的文件仍会创建它；
- 自动 `mkdirs()` 父目录；写后检查 `file.exists()`，内容非空但文件为 0 字节时报错；
- 二进制另走 `write_file_binary`（base64），不混在文本 `write_file` 里；
- **没有 512KB 这种 per-tool 输入守卫**；大文件靠模型多次 `append` 完成，读侧另有 `read_file_part` /
  `read_file_full` 控制返回给模型的量（`MAX_FILE_READ_BYTES = 32_000` 是读结果上限，不是写上限）。

所以我们不是照抄「无上限」，而是：**文本 `write` 学它的 `append` 语义 + 把守卫放到 16MB 防 OOM**；
二进制以后需要时再单开 `write_binary`，不要把 base64 塞进普通 `write`。

### 8.4.3 改法

1. **提高上限**：`LARGE_MAX_BYTES` 512KB → **16MB**；普通工具仍 64KB（避免一次把无关工具输入放大）。
   `ToolInputGuard.limitFor()` 增加可注入的 `largeLimitBytes`（默认 16MB，clamp 64KB..64MB），
   为后续「高级设置/调试覆盖」留口；不要写成散落常量。
2. **`write` 增加追加模式**：schema 加 `append: boolean`（默认 false）；`WriteTool` 用
   `FileOutputStream(file, append = true)` 写 UTF-8。description 明确：
   > 单次 content 尽量 ≤200KB；更大的文件用 `append=true` 分多次写，第一次 false 建文件，后续 true 追加。
3. **`edit` 大文本**：同样受益于 16MB；`old_string`/`new_string` 都按新上限；如果 >2MB，提示改用
   `write append` 重写文件，避免一次 edit 传输两份大文本。
4. **错误文案**：超限时写清「当前上限 16MB；更大文件请用 write 的 append 分块」；
   截断（INVALID_JSON）时写清「参数被截断，请拆分为多次 write/append」。
5. **模型输出侧**：若 `MAX_TOKENS` 时存在未完成的 tool_use，保持现有「不执行 + error tool_result」，
   但文案引导 `write append`；不要悄悄执行半截参数。
6. **JVM**：
   - `ToolInputGuardTest`：limitFor 新值、16MB 边界（用 `limitFor` + 构造小 override 测，避免真分配 16MB）；
   - `WriteTool` append：先 false 写 "A"，再 true 写 "B"，断言文件 "AB"；再验证 false 覆盖；
   - `edit` 大文本用 600KB 字符串（不超 16MB）验证不再被拒；
   - 保持 64KB 普通工具的既有用例。

### 8.4.4 验收

- 真机让模型一次写 600KB 文本：不再出现「工具输入过长」；文件内容完整。
- 真机让模型分 3 次 `write append` 写 2MB：三次都成功，文件按顺序拼接。
- 故意让 `max_tokens` 截断 tool_use：模型收到「参数被截断，请拆分」并能重试成功。
- 不因为 16MB 上限把低端机 OOM：16MB JSON 解析峰值在可接受范围；若实测 OOM，降到 8MB，**用真机数字说话**。

> 说明：用户原话是「writeai 工具」；这里按 `write` 工具理解。如果实际指的是别的工具名（例如某个插件工具），
> 先 `grep` 工具名再改，别改错落点。
