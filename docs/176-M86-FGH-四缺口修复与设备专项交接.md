## 一、本轮修复（源码）

### 1. 删除工作区前 join 真正的 writer（P1）

- 问题：`switchWorkspace` 取消旧运行时后立刻 `lives.clear()`；`deleteWorkspace` 随即 `repo.trashWorkspace` 并移动目录。被取消轮次的 `NonCancellable` 收尾（补 `tool/result`、`step/end`、`turn/end`）还在写原路径，会把回收站历史写缺/写坏。
- 修法：新增 `app/.../chat/SessionWriterBarrier.kt`，`switchWorkspace` 在取消前把每个 live 的 `live.job` 按工作区绝对路径记账；`deleteWorkspace` 的新协程里先 `awaitWorkspaceWriters(path)`（还挂在 `lives` 里的防御性取消 + `writerBarrier.cancelAndJoinAll(path)`），**再**移动目录。`join` 是唯一可靠完成信号，不用 sleep。记账会顺手清掉已完成的 job，不随切换次数增长。
- 单测：`SessionWriterBarrierTest`（3 项，含 `joinWaitsForNonCancellableCleanup` 用 `NonCancellable` + 门闩证明「移动只能在收尾之后」、不同工作区互不影响、已完成 job 不记账）。

### 2. 删会话后前后台运行时一律作废（P2）

- 问题：`discardSessionQueue` 把后台会话 A 置 `acceptingInputs=false`，但 `deleteSession` 只在删除的是当前聊天时才移除 live；从回收站恢复并打开 A 会复用失效运行时，发送/附件一直被拒直到重建 VM。
- 修法：新增 `app/.../chat/SessionLifecyclePolicy.kt` 的 `runtimesForDeletedSession`；`AppViewModel.invalidateLivesForDeletedSession(id)` 统一收口删除/彻底删除/清空回收站：按 id 摘掉**所有** live（不等同于清空其它会话草稿），前台额外 `attach(null)`，返回栈只删除指向该会话的项；`openSession/openSessionById` 增加第二层防御——`acceptingInputs=false` 的旧运行时不复用，丢弃后按磁盘重读。
- 单测：`SessionLifecyclePolicyTest`（4 项，含「前台+后台+其它会话」映射与草稿保留语义）。
- 覆盖边界：**「后台 A → 删除 → 回收站恢复 → 打开 A 可发送/附件」这条端到端真机场景本轮没有写成脚本**（删除入口需要多级 UI 确认，且设备中途掉线两次）；该修复由策略单测 + `openSession` 的失效运行时丢弃防御 + 静态审阅覆盖，没有真机端到端证据，不要据此声称已验证。

### 3. `max_tokens` 截断在 `tool_use` 上的安全处理（P1/P2）

- 问题：`TurnEngine` 只在 `toolCalls.isEmpty()` 分支处理 `max_tokens`；带 `tool_use` 的截断响应会继续执行工具批次，下一步还会领取 steer/队列，后续正常响应又覆盖 `lastStopReason`，破坏「max_tokens 后暂停保留队列」。
- 修法：`core/engine/TurnEngine.kt` 在 assistant/tool-call 落库之后、执行工具之前插入截断分支：本批工具**一次都不执行**（参数可能被切断），但为每条已落库调用补一条 `TRUNCATED_TOOL_RESULT` error `tool_result` 保持配对，`hookStepEnd → endStep` 后直接收口 turn（`errorText` 置「达到 max_tokens 上限，输出被截断（工具调用未执行）」）。下一轮请求仍然合法（`parseArgs` 对坏 JSON 退化为 `{}`），会话平衡。
- 单测：`TurnEngineTest` 新增 2 项——`truncatedToolBatchIsPersistedButNeverExecuted`（两个半截调用；0 执行、配对齐全、只 poll 一次 steer、不领队列、step/turn 平衡，且下一轮能带着该 `tool_result` 正常完成）、`truncationAfterCompletedToolBatchKeepsPairingAndStops`（第一批正常执行、第二批不执行、step 2 对）。

### 4. `newChat` 回收空会话不再丢未落盘草稿（额外风险）

- 问题：回收条件只看 `sessionId/messages/job`，输入框文字、待发图片、待发文件都还没进任何会话文件，跟着运行时一起丢就是用户数据丢失。
- 修法：`SessionLifecyclePolicy.disposeOfUnpersistedChat` 三态——真空白 `RECYCLE`；有草稿/附件 `CARRY_DRAFT`（把文字、光标末尾、待发图片/文件搬到新会话输入框后再回收旧运行时）；已落盘或在跑 `KEEP`。
- 单测：`SessionLifecyclePolicyTest` 覆盖空白/纯空格/文字/图片/文件/已落盘/在跑。

### 5. 顺带修默认 UI 的组合键回归（审阅发现）

FGH 把原生聊天页包进 `key(conversation.stateKey)`：本机会话的 `stateKey` 带 `sessionId`，而新会话的 sessionId 是第一个回合里才落定的，导致**首次发送后整棵 ChatScreen 被销毁重建**（滚动位置、焦点、弹层、选择器回调全丢）。现在本机聊天页只按 `"local-chat"` 组合（恢复原行为），远程仍按 `stateKey` 隔离。`ConversationAdapterTest` 的 `stateKey` 契约未改。
