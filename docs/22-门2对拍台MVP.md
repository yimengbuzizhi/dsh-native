# 22 · 门 2 对拍台 MVP：录制 SSE → 回放 → 0 diff

> 2026-11-07 01:2x｜基线 `16ab753`。落地 `docs/02-对拍台设计.md` 的 P0 验收线 1/2/4，
> 并把「同一实现两次 0 diff」「真实 run 与回放 run 0 diff」都跑成了可复现命令。

## 一、一句话结果

真机录下 1 次完整对话（2 个请求：工具调用 + 收尾回答，共 8655 字节 SSE），
把 App 的 `baseURL` 指到本机回放器：

- 真实 API 跑一次（runA）→ 对拍台重放一次（runB）→ **70 行行为日志 0 diff**；
- 同一夹具再重放一次（runC）→ **70 vs 70 行 0 diff**；
- 两次请求体 sha256 与录制时**逐字节相同**（`086b6e39…` 13220B、`e8a7a616…` 13557B）。

证据：`docs/shots/m5-parity-verify.png`（回放出来的对话）、`parity/reports/*.json`、
`parity/fixtures/device-smoke/llm-000{1,2}.jsonl`（真实 SSE 原始字节）。

## 二、三个组件

### 1. 录制：`core/llm` 的 `SseTap` + `core/parity` 的 `SseCaptureRecorder`

`LlmClient` 增加一个可选 `tapFactory`，把响应体 `InputStream.read()` 的每一段字节旁路出来
（生产路径 `tap == null`，零开销）。App 侧调试通道：

```
--es dsh_dump_sse /data/user/0/<pkg>/files/parity/cap1   # 每次请求一个文件
```

捕获文件 JSONL：

```json
{"type":"parity.capture","version":1,"requestSha256":"086b…","requestBytes":13220,"chunkCount":9,"byteCount":3846}
{"seq":0,"tMs":633,"b64":"ZXZlbnQ6IG1lc3NhZ2Vfc3RhcnQK…"}
```

- `b64` 是**原始字节**，不解析、不规范化；`seq` 从 0 连续；
- `tMs` 是相对首字节的到达时间（**不存绝对时间**，docs/02 §八.3）；
- chunk 边界 = 解析器实际读到的边界。录制文件只有 5–7KB/请求，适合进 git 当夹具。

### 2. 回放：`:core:parity` 的 `ReplayServer`（纯 JVM，无依赖）

只听 `127.0.0.1` 的 60 行手写 HTTP/1.1 服务：

- 默认**按序**返回夹具，`--strict` 改用 `sha256(request body)` 匹配；
- 每个 chunk 单独 `write + flush`，保住流式时序（docs/02 §八.1）；
- `--real-time` 按 `tMs` 间隔重放（验证中断/超时）；
- `--loops N` 让同一批夹具服务 N 次（一次起服跑多次 run）；
- 控制端点：`GET /__parity/stats`、`POST /__parity/reset`（夹具游标归零）、
  `GET /__parity/requests`（每次请求的 sha/夹具号，排查错位用）；
- 响应恒为 `Connection: close`，避免 keep-alive 状态污染下一个请求。

### 3. 比对：`RunRecorder` + `ParityCompare`

App 侧 `--es dsh_parity_run <dir>` 写 `run.jsonl`，一行一个对象：

| 类型 | 内容 |
|---|---|
| `run.meta` | scenario/model/provider/baseUrl/审批模式/工具数/prompt |
| `llm.request` | `n, sha256, bytes, body`（**请求体原文**） |
| `llm.event` | 每个 `LlmEvent` 一条（message_start / block_start / text_delta / thinking_delta / signature_delta / tool_input_delta / message_delta / failed） |
| `tool.call` | `name, args, isError, result`（截断 200KB） |
| `turn.end` | 最终 `state.messages` 全量（role + 每种 block） |

比对器对两边**逐行归一后**比较，只报第一个差异（JSON 路径 + 两边上下文）：

- 工作区路径 → `<WORKDIR>`；UUID/会话 ID → `<ID:n>`（run 内一致映射）；
- 13 位毫秒 / ISO 时间 → `<TS>`；`sessionId` → `<SESSION>`；
- 回放地址/端口 → `<REPLAY_BASE_URL>` / `:<PORT>`；`baseUrl` 字段 → `<BASEURL>`
  （端点属于运行配置，请求体 sha 已经证明发出去的东西一致）。

## 三、怎么跑

```powershell
# 1) 录制（真机 + 真账号 token，自动批准 bash）
.\tools\parity.ps1 record -Prompt "先用 bash 执行 ls -1 看看工作目录，再把文件名列出来。"

# 2) 一条命令验收：起回放器 → 同一夹具跑两次 → reset → 比对
.\tools\parity.ps1 verify -Captures parity\fixtures\device-smoke

# 3) 只起回放器（手动跑/抓包）
.\tools\parity.ps1 serve -Captures parity\fixtures\device-smoke -Port 18080 -Loops 4
```

`verify` 的硬校验：**每个 run 的 `llm.request` sha 必须与夹具头部 sha 逐个相等**
（请求数也要相等），否则自动 `reset` 重跑（最多 3 次）。这条防止「两次都错放成同一个
回答」的假 PASS —— 踩过（见下）。

## 四、单元测试（`:core:parity:test`，8 个全绿）

| 测试 | 证明什么 |
|---|---|
| 同一份录制回放两次 0 diff | 事件序列逐条相同；请求体 sha 与录制一致 |
| strictMatch 按哈希匹配 | 夹具乱序返回也能命中正确的那份 |

| realTime 按录制间隔回放 | 逐 chunk flush + 间隔重放（≥100ms 断言） |

## 五、踩到的坑（都写进脚本了）

1. **Android 默认禁明文 HTTP**：`baseUrl` 指到 `127.0.0.1` 直接
   `CLEARTEXT communication not permitted`。加 `app/src/debug/AndroidManifest.xml`
   的 `usesCleartextTraffic=true`，release 不受影响。
2. **`Wait-TurnEnd` 会被上一次的 `run.jsonl` 骗过**：文件里已有 `turn.end`，
   新进程还没写就被判定完成，拉到旧证据 → 夹具错位、假 PASS。现在启动前
   `rm -rf` 远端 run 目录。
3. **adb reverse 首次连接偶发被拒**：设备端注册有延迟，失败那轮没打到回放器；
   脚本 reset 游标后整轮重跑（最多 3 次）。
4. **PS 5.1 + `$ErrorActionPreference=Stop`** 会把 adb 的 stderr（轮询时 `grep: no such file`）
   当终止错误；轮询段局部放宽并丢弃 stderr。
5. **脚本必须带 UTF-8 BOM**：否则 PS 5.1 按 ANSI 解析，中文 prompt 变乱码。
6. **捕获是消费侧边界**：OkHttp 解压后、`InputStream.read()` 的切分，不是 TCP 包边界；
   回放能保证「解析器看到同样的字节序列和同样的分段」，够用于流式时序判据。

## 六、已知限制 / 下一步

1. 引擎主循环还在 `AppViewModel`，所以 run 日志是「App 级」的；旧版引擎无法在同一套
   harness 里跑（P0 第 3 条「旧版跑两次」仍未做）。下一步把 runTurn 抽到 `core:engine`，
   新旧共用同一个 driver。
2. 录制只有成功流；HTTP 错误体（4xx/5xx）还没录，回放器的 409 是控制面错误。
3. 场景库仍只有 1 个（bash-ls）；`docs/02 §五` 的 P0 6 个场景待补：只读、写文件、改函数、
   失败重试、取消中断。
4. 对拍报告还没有 HTML/Markdown 汇总，目前是单场景 JSON + stdout。
