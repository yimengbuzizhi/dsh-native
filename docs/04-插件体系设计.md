# 04 · 插件体系设计（保留「一切皆插件」）

> 2026-11-06｜结论：**保留，而且要做到内核级**——不是"支持插件"，是"内核本身就是插件拼的"。
> 推荐路线：**cordis 风格 API + ToolPkg 包格式 + QuickJS 运行时 + Kotlin 插件内核**。

---

## 一、先看清 DSH 的插件到底是什么（实测，不是猜）

以 `dsh-tool-todo`（内核自带的 30 个工具之一）为例，它的 `lib/index.js` 长这样：

```js
const name = "tool-todo";                    // 插件名
const inject = ["tools", "sessionProjections"]; // 声明依赖的服务
const Config = z.object({ allowParallelInProgress: z.boolean().required() });

function apply(ctx, config) {                 // 唯一入口
  ctx.sessionProjections.register({ key: "todos", ... });
  ctx.tools.register(defineTool({ name: "todo_write", description, parameters, execute }));
}
```

配套事实：

| 事实 | 证据 |
|---|---|
| 插件入口统一是 `apply(ctx, config)` | 上例；30 个 tool 包同构 |
| 依赖靠 `inject` 声明，运行时注入 | `inject = ["tools", "sessionProjections"]` |
| 配置是 **schemastery schema**，带默认值与校验 | `Config = z.object(...)` |
| 一切能力都是 `ctx` 上的**服务** | `ctx.tools` / `ctx.sessionProjections` / `ctx.llm` / `ctx.api`… |
| 插件通过 **npm 包装**分发，带 `dependencies`/`peerDependencies` | `package.json` |
| 安装器按 **profile** 管理：`package.json` 里 `dsh.bundle.patch`、`pnpm add` 规格、官方目录、可选 bundle | `dsh-plugin-manager/lib/index.js` |
| 连 UI 都是插件 | 62 个 `dsh-client-ui-*` 包，按路由/视图注册 |

所以「一切皆插件」的准确含义是：

> **内核 = 一个服务容器（cordis）+ 一组注册表（tools / llm / session / api / ui …）；
> 每个功能都是一个包，声明 `inject`、提供 `apply(ctx, config)`，由安装器按 profile 组合。**

我们要保留的正是这个结构，而不是"提供几个扩展点"。

## 二、三条路线

| | A. Operit 式扩展点 | B. 纯 Kotlin 插件内核 | C. **内核 + JS 桥 + ToolPkg 包**（推荐） |
|---|---|---|---|
| 核心是否插件化 | ❌ 核心是单体，插件只能加工具/UI | ✅ 是 | ✅ 是 |
| 第三方能否写插件 | ✅（ToolPkg JS） | ❌ 只能写 Kotlin/APK | ✅（JS，沙箱） |
| 与 DSH 插件形似 | ⚠️ 形似（工具+UI+hook） | ✅ 形似 | ✅ **高度形似**（`apply(ctx,config)`） |
| 现有 DSH 插件移植成本 | 高（要改写成 ToolPkg） | 高 | **低**（改 import 即可，见 §8） |
| 工期 | 2–3 周 | 8–10 周 | **6–8 周** |
| 风险 | 名不副实，日后返工 | 生态为零 | 内核复杂度可控 |

选 **C**。理由：DSH 的灵魂是「内核由插件组成」，只做扩展点等于把这个卖点丢掉；
但纯 Kotlin 插件又没有生态（用户不可能为装个工具去编译 APK）。C 两边都占。

## 三、总体结构

```
┌─────────────────────────────────────────────────────────┐
│ :app                                                    │
│  ┌───────────────────────────────────────────────────┐  │
│  │ :plugins:kernel   插件内核（Kotlin）               │  │
│  │   PluginContext / ServiceRegistry / 生命周期 /      │  │
│  │   配置 schema / 依赖解析 / 启用禁用 / 故障隔离      │  │
│  └───────────────────────────────────────────────────┘  │
│         ▲ 注册                          ▲ 注册           │
│  ┌──────┴──────┐                 ┌──────┴──────────┐    │
│  │ 系统插件     │                 │ JS 插件（QuickJS）│    │
│  │ (Kotlin)     │                 │  apply(ctx, cfg) │    │
│  │ 聊天/工具/   │                 │  第三方 .toolpkg │    │
│  │ provider/UI  │                 │                  │    │
│  └─────────────┘                 └──────────────────┘    │
│         │                                │               │
│  ┌──────┴────────────────────────────────┴──────────┐    │
│  │ 注册表（服务）：tools / llm / session / prompt /   │    │
│  │ api / ui / hooks / themes / mcp / schedule        │    │
│  └───────────────────────────────────────────────────┘    │
└─────────────────────────────────────────────────────────┘
```

**关键决定**：我们自己的聊天、工具、provider、设置页、控制台，**全部写成"系统插件"**，
走同一套 `apply(ctx, config)`。这样「一切皆插件」是真的，不是对外话术。

## 四、插件契约

### 4.1 Kotlin 侧（系统插件）

```kotlin
interface DshPlugin {
    val name: String                       // 唯一名，如 "dsh.chat"
    val inject: List<String>               // 依赖的服务名
    val provides: List<String>             // 自己提供的服务
    val configSchema: ConfigSchema         // 可空
    fun apply(ctx: PluginContext, config: JsonElement)
}
```

`PluginContext` 提供与 cordis 对齐的能力：

```kotlin
ctx.tools.register(toolDef)
ctx.llm.register(provider)
ctx.ui.registerRoute(route)
ctx.sessionProjections.register(projection)
ctx.on("turn/start") { ... }
ctx.provide("myService", impl)      // 供别的插件 inject
ctx.plugin(childPlugin)             // 子插件（组合）
ctx.effect { /* dispose */ }        // 生命周期清理
ctx.logger
```

### 4.2 JS 侧（第三方插件）——与 DSH 同形

```js
exports.name = 'tool-weather'
exports.inject = ['tools', 'net']
exports.Config = { city: { type: 'string', default: 'Shanghai' } }

exports.apply = (ctx, config) => {
  ctx.tools.register({
    name: 'weather_now',
    description: 'Get current weather',
    parameters: { city: { type: 'string', required: true } },
    execute: async ({ city }) => {
      const r = await ctx.http.get(`https://api.example.com/?city=${city}`)
      return { text: r.body }
    }
  })
}
```

JS 侧的 `ctx` 是 Kotlin `PluginContext` 的代理，能力和权限由 manifest 决定。

## 五、服务与注册表（第一批）

| 服务名 | 能力 | 谁提供 |
|---|---|---|
| `tools` | 工具注册/查找/执行 | 内核 |
| `llm` | 模型通道注册 | 内核 + 系统插件 |
| `session` | 会话读写事件 | 系统插件（DSH 格式） |
| `prompt` | 系统提示词片段 | 系统插件 |
| `ui` | 路由/页面/侧栏入口/消息渲染器 | 内核 + 插件 |
| `hooks` | 生命周期、消息处理、工具前后置 | 内核 |
| `http` / `fs` / `shell` | 受权限管控的能力 | 内核（JS 侧代理） |
| `mcp` | MCP 客户端 | 系统插件 |
| `schedule` / `jobs` | 定时与后台任务 | 系统插件 |

**注册表是唯一扩展点**：任何新能力 = 新增一个注册表 + 一个服务接口，不改进别处。

## 六、清单、Profile、依赖

### 6.1 清单（借 ToolPkg 的格式，换成我们的字段）

```json
{
  "schema_version": 1,
  "id": "com.example.weather",
  "name": { "zh": "天气", "en": "Weather" },
  "version": "1.0.0",
  "api_version": "1.0.0",
  "main": "main.js",
  "inject": ["tools", "http"],
  "provides": [],
  "permissions": ["net:api.example.com"],
  "config": { "schema": { ... }, "default": { ... } },
  "requires": [{ "id": "com.example.shared", "min_version": "1.2.0" }]
}
```

### 6.2 Profile（照搬 DSH 的 profile 概念）

```json
{
  "name": "default",
  "plugins": [
    { "id": "dsh.chat",        "enabled": true },
    { "id": "dsh.tools.fs",    "enabled": true },
    { "id": "com.example.weather", "enabled": true, "config": { "city": "Beijing" } }
  ]
}
```

- 多 profile（default / dev / 极简），切换即换一套插件组合
- 依赖拓扑排序 + 循环检测；被依赖的不能直接关
- 启用/禁用即时生效（非关键插件可热重载，关键插件提示重启）

## 七、权限（这是 JS 插件必须有的东西）

| 权限 | 说明 | 默认 |
|---|---|---|
| `fs:workspace` | 只能读写当前工作区 | 允许 |
| `fs:any` | 任意路径 | 询问 |
| `net:<domain>` | 指定域名 | 询问 |
| `net:any` | 任意网络 | 询问 |
| `shell` | 执行命令 | 询问 + 红框 |
| `ui` | 注册页面/弹窗 | 允许 |
| `notify` | 发通知 | 询问 |
| `device` | 无障碍/Shizuku/虚拟屏 | 禁止（需用户显式开） |

原则（沿用旧项目红线）：**危险能力永远不能静默获得**——红框 + 原文 + 点击确认。

## 八、与现有 DSH 插件的兼容度

| 插件类型 | 兼容性 | 代价 |
|---|---|---|
| 纯工具插件（如 `todo_write`、`weather`） | **高**：把 `import { defineTool } from '@deepseek-ai/dsh-tools'` 换成宿主注入的 `ctx.tools`，逻辑不动 | 每个约 10–30 行改动 |
| 带 session projection 的插件 | 中：需要 `ctx.sessionProjections` 的兼容实现 | 投影 API 要单独做 |
| 依赖 Node API（fs/child_process）的插件 | 中：提供 shim（`fs` → 我们的 fs 服务） | 逐个 shim |
| UI 插件（React） | 低：React → Compose DSL 或原生路由，必须重写 | 不承诺 |
| 深度钩子（改 agent loop）的插件 | 低：需要内核暴露同等 hook | 按需 |

**结论**：不承诺"旧插件二进制兼容"，但承诺「**API 同形、简单工具插件改几行就能跑**」。
这比 Operit 的 ToolPkg（完全另一套 API）对生态友好得多。

---

## 九、UI 插件（第二阶段）

- 先用 **Compose DSL**（Operit 已验证：JS 写声明式 UI，宿主渲染），让插件能画设置页/小面板
- 再用「原生路由注册」让插件挂到侧栏/设置入口
- 消息渲染：允许插件注册自定义消息块渲染器（对应 DSH 的 XML render 插件）

## 十、里程碑与成本

| 项 | 工期 |
|---|---|
| 内核（Context / 服务注册表 / 生命周期 / 依赖 / 配置 schema） | 3–4 周 |
| JS 桥（QuickJS 宿主 + `ctx` 代理 + 权限门 + 模块 shim） | 2–3 周 |
| 清单/Profile/安装器（本地导入、启用禁用、配置 UI） | 1–2 周 |
| 把我们的核心改写成系统插件（伴随 M1–M3 进行，不额外计） | — |
| **合计新增** | **6–9 周** |

工期从 9 个月 → **10–11 个月**。但这 6–9 周买的是「这个产品的身份」，
否则做完只是一个"能用的原生 App"，不是 DSH。

---

## 十一、风险

| 风险 | 应对 |
|---|---|
| 内核过度设计，拖慢主线 | 第一版只做「工具 + hook + 配置」三类注册表，UI/投影后置 |
| 插件把 App 搞崩 | 每个插件独立作用域 + apply 超时 + 异常隔离；核心插件不可禁用 |
| JS 桥性能 | 工具调用是低频操作，QuickJS 足够；渲染路径不走 JS |
| 兼容承诺过头 | 文档写明「API 同形，不保证二进制兼容」 |
| 安全（第三方插件拿设备权限） | 权限清单 + 运行时询问 + 危险操作红框 |
