## 一、做了什么

### 1. 服务容器（`core/plugins/PluginServices.kt`，新文件）
- `ctx.provide(name, value)`：值的 `JSON.stringify` 快照记进 `PluginRecord.provides`（持久化到 `files/plugins.json`）。
- `ctx.inject(deps, callback)`：依赖参数支持 `['a','b']` 与 `[{name, optional}]` 两种写法；apply 时宿主把
  **其他已启用插件的服务快照**交给回调（`scope[name] = JSON.parse(value)`）；非 optional 缺服务 → 回调不执行、
  服务名记进 `missingDeps`。
- 依赖解析 `PluginServices.resolve(records)`：提供方 → 边（谁依赖谁、提供者是谁、是否满足）→ 缺失列表 →
  依赖排序（提供者在前，环里的插件按清单顺序保留并标记 `cycles`）。
- `ctx.effect(fn)`：apply 时调用并登记（`cleanup` / `effect`）；**没有常驻 JS 运行时，停用时不回调清理器**（插件页写明）。
- `ctx.on(event, handler)`：登记事件名（`subscriptions`）+ 把 handler 存进 `__dshDefs['event:<name>']`；
  宿主事件总线本阶段只做登记面（派发在后续阶段接）。
- `ctx.plugin(sub, config)`：JS 侧内联执行子插件的 `apply`（组合），不新建插件记录。
- `PluginServiceHost`：宿主侧 `plugin.services.values / provide / effect / on` 的实现；
  试运行（`PluginStore.dryRun`，带服务快照）和插件工具执行（`PluginToolRuntime`）都接同一套。

### 2. 依赖重算（`PluginStore.reconcileServices()`）
- 启用/停用/导入/卸载/重载插件后调用：按依赖排序重跑「提供 / 依赖 / 以前缺依赖」的插件 apply；
  最后把 `missingServices` 写回记录。
- 关掉提供者：依赖它的插件工具消失、`missingServices` 有值；开回来：重新注册工具。
- 真机日志：关 A → `services reconcile: reloaded=1 missingPlugins=1`；开回 A → `reloaded=2 missingPlugins=0`。

### 3. 能力清单（`PluginCapabilities`）
- 24 个原语登记（id / 标题 / JS 写法 / 权限 / 是否已实现 / 备注），宿主版本 `m83.1`，当前 **19/24 已实现**。

## 三、已知限制（如实记录）

1. **没有常驻 JS 运行时**：`ctx.effect` 的清理器不会在停用时回调；`ctx.on` 只登记，事件派发还没接宿主总线；
   `ctx.inject` 的回调在每次 apply（试运行/工具调用）时重新执行——这就是本项目的模型，后续「回合钩子」阶段再补事件派发。
2. `ctx.provide` 的值走 JSON 快照：`function`/`Map`/循环引用会丢；跨插件传「活对象」不支持（设计如此）。
3. 同名服务多个插件提供时，**后启用者覆盖**（清单顺序后者生效），插件页只显示当前生效的提供者。
4. `PluginRecord` 里 `provides` 值可能包含插件自己的敏感配置快照（例如令牌），插件页只显示服务名、不显示值；
   备份 `plugins.json` 会带上快照（和工具 schema 同级的既有行为）。
