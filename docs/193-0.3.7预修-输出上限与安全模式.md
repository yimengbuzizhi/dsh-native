## 一、取消 8192 输出上限

### 1.1 现象与根因

- 0.3.6 的请求固定 `max_tokens = 8192`：
  - `ui/shell-api/.../SettingsStore.kt`：`DEFAULT_MAX_TOKENS = 8_192`，`maxTokens` 直接返回它；
  - `core/llm/.../LlmClient.kt`：`LlmConfig.maxTokens` 默认 8192。
- 2026-11-09 删「最大输出 tokens」设置时就写死了这个值（用户当时要求删设置项），结果长回复/长文件总在 8k 处 `stop_reason=max_tokens`，UI 走「继续生成」。
- 上游 dsh 自己不是这个口径：`dsh-llm-deepseek` 适配器默认 **`maxTokens = 256_000`**（`.upstream/oracle/.../dsh-llm-deepseek/lib/index.js`：`maxTokens: config.maxTokens ?? 256e3`），模型目录里 `models[].maxTokens` 优先。

### 1.2 改动

| 文件 | 改动 |
|---|---|
| `core/model/src/main/java/xin/dshaa/core/model/OutputBudget.kt`（新） | 纯计算：`DEFAULT_MAX_TOKENS = 256_000`（对齐上游）、`MIN_MAX_TOKENS = 1_024`、`effective(desired, contextWindow)`：窗口未知（≤0）→ 用 desired；已知 → `min(desired, window/2)`（不低于 1024） |
| `ui/shell-api/.../SettingsStore.kt` | `DEFAULT_MAX_TOKENS = OutputBudget.DEFAULT_MAX_TOKENS`；`maxTokens` getter 改成 `OutputBudget.effective(_maxTokens.value, _contextWindow.value)`；`setMaxTokens` clamp 到 `[MIN, 1_000_000]` 并写 `max_tokens_override` 标记；初始化只认「显式改过」的值（老设备 prefs 里残留的 8192 不会复活） |
| `core/llm/.../LlmClient.kt` | `LlmConfig.maxTokens` 默认 **256_000** |
| `app/.../MainActivity.kt` | 调试通道 `--ei dsh_max_tokens N` 同步写 `max_tokens_override`（原来只写值、被固定默认值盖住，等于不生效） |
| `ui/native-shell/.../ModelConfigScreen.kt`、`ui/shell-api/.../TruncationResume.kt` | 注释/文案口径更新（截断提示里显示的是实际上限） |

### 1.3 为什么是「256k + 窗口一半」而不是字面「无限」

- Anthropic 协议 `max_tokens` 是必填正整数，不能省略；OpenAI 兼容通道省略会掉回服务端默认（常见 4k），比 8192 更小。**「不发这个字段」在两条通道上都不成立**。
- 发一个固定超大值（如 1,000,000）会让小窗口/小输出模型直接 4xx。用 `min(256k, window/2)` 同时满足：
  - deepseek-flash（窗口 1,048,576）→ 发 **256,000**；
  - 128k 窗口的自定义模型 → 64,000；
  - 8k 窗口 → 4,096；
  - 自动压缩策略 `Compaction.Policy.resolve(W, O)` 要求 `W > O + headroom`，O=W/2 时恒成立（`OutputBudgetTest.compactionPolicyAlwaysResolvableWithHalfWindowCap`）。
- 仍保留隐藏设置：调试通道可以 `--ei dsh_max_tokens 2048` 把小值写进去（验收用），普通用户界面不暴露。

### 1.4 验证

- JVM：`core:model:test` 通过；新增 `OutputBudgetTest` 6 例（默认 256k、未知窗口不裁、128k→64k、8k→4096、下限、压缩策略恒可解）。
- 构建：`:app:assembleDebug` 通过；`:app:testDebugUnitTest`、`:core:engine:test`、`:core:llm:test`、`:core:model:test` 全绿（2026-11-24 21:2x，33 s）。
- 模拟器（FBD_API30 / x86_64）：装的是这一版 APK，App 正常启动（证明改动没有破坏初始化）。
- **未验**：真实请求体里的 `max_tokens`（模拟器没有可用 key）；不同 provider 对 256k 的接受度。DeepSeek 的 anthropic 端点是上游默认口径，风险低；自定义 OpenAI 兼容端点若回 `max_tokens too large`，目前只能靠调试通道下调——见 §四的后续项。

### 1.5 回滚

`SettingsStore.DEFAULT_MAX_TOKENS` 改回 8_192、`LlmConfig` 默认改回 8_192、删 `OutputBudget.kt` 即可；prefs 里没有迁移数据（`max_tokens`/`max_tokens_override` 只是普通键）。

## 二、崩溃循环安全模式

### 2.1 现象

用户装了「写坏的插件」后 App 一开就崩，重启也崩，**只能重装**。插件与 App 同进程（QuickJS），插件在加载/注册期抛异常或卡死，会把启动流程一起带走。

### 2.2 设计

- **判定**：`Application.onCreate` 每次进程启动记一个时间戳；**60 秒内第 5 次启动** → 判定崩溃循环。用启动次数而不是崩溃回调，是因为崩溃可能在原生层/JS 里直接杀进程，来不及写标记（Android 官方安全模式同思路）。
- **动作**（都在插件加载之前）：
  1. `PluginStore.setAllEnabled(false)`：把所有**导入的第三方插件**停用（写 `plugins.json` 的 `enabled`，等同用户在插件页手动关掉；不删插件、不丢配置、不丢会话）；
  2. 把「本来开着的是哪些」记到 `safe_mode_disabled_plugins`；
  3. 本次开机不自动拉起 Node 宿主（`AppViewModel` 的 autostart 条件加 `!safeMode.active`）；Node 宿主自己的崩溃策略（5 分钟 3 次）继续生效；
  4. 聊天页顶部出红色横幅，一键「恢复第三方插件」：按名单 `setEnabled(id, true)`，清安全模式标记。
- **为什么在 `Application.onCreate`**：`AppViewModel`/Activity 之前执行，才能保证坏插件一个都没加载；注册表是一个 JSON，主线程读写毫秒级。异步化会让首个 Activity 抢在停用之前把坏插件加载起来。
- 内置插件（`builtin.*`）不在 `PluginStore` 里，不受影响——所以界面/回合/存储仍是内置实现，App 一定能画出「恢复」入口。

### 2.3 改动

| 文件 | 改动 |
|---|---|
| `app/.../data/SafeMode.kt`（新） | `SafeMode`：SharedPreferences 持久化（`safe_mode_launches` / `safe_mode_active` / `safe_mode_disabled_plugins` / `safe_mode_triggered_at`）；`recordLaunch()`、`activate(disabled)`、`deactivate()`；`SafeModePolicy`：纯判定（`WINDOW_MS=60_000`、`MAX_LAUNCHES=5`、`recent()`、`shouldTrigger()`） |
| `app/.../DshApplication.kt` | `onCreate` 最前面 `enterSafeModeIfCrashLooping()`：触发 → 记录名单 → `setAllEnabled(false)` → 日志 `DshSafeMode` |
| `app/.../chat/AppViewModel.kt` | `safeModeNotice`（横幅文案）、`exitSafeMode()`（恢复名单 + 清标记 + 刷新 `pluginsUi` + `pluginNotice`）；Node autostart 加 `!safeMode.active` |
| `ui/shell-api/.../NativeShellHost.kt` | 接口默认实现：`safeModeNotice`（null）、`exitSafeMode()`（空）——壳不强制实现 |
| `ui/native-shell/.../chat/ChatScreen.kt` | 新参数 `safeModeNotice` / `onExitSafeMode`；在连接提示下面用现成 `RoleSafetyBar` 画「安全模式（插件已被停用）」+「恢复第三方插件」 |
| `ui/native-shell/.../pages/NativePageDispatch.kt` | 把 `vm.safeModeNotice` / `vm.exitSafeMode()` 接进 ChatScreen |
| `app/src/test/.../data/SafeModePolicyTest.kt`（新） | 纯判定 5 例：第 5 次触发、第 4 次不触发、窗口外不计、边界算、排序去重 |

### 2.4 验证（模拟器实测，2026-11-24）

设备：`emulator-5554`（FBD_API30 / x86_64）。装的是本轮 `:app:assembleDebug` 的 APK。

1. `pm clear` 后启动一次 → prefs 出现 `safe_mode_launches=1795526430818`；
2. 再 `am force-stop` + `am start` 4 次（每次间隔 ≤2 s）→ 第 5 次：
   ```
   W DshSafeMode: safe mode: 5 launches within 60000ms
   W DshSafeMode: safe mode on: disabled=0 plugins
   W DshSafeMode: entered safe mode: plugins disabled=0 (0 known)
   ```
   prefs：`safe_mode_active=true`、`safe_mode_disabled_plugins`（空集，本次没装第三方插件）、`safe_mode_triggered_at` 有值；
3. 跳过 onboarding 后聊天页顶部出现「安全模式（插件已被停用）…」+「恢复第三方插件」（截图 `docs/192-evidence/safe-mode-banner.png`，未跟踪）；
4. 点「恢复第三方插件」→ prefs `safe_mode_active=false`，日志 `I DshSafeMode: safe mode off`，横幅消失。

JVM：`SafeModePolicyTest` 5/5；全量 `:app:testDebugUnitTest` 通过。

**未验**：
- 「名单非空」的停用/恢复（模拟器是 x86_64，没有 QuickJS，第三方原生插件装不上：`debug import ok=false … libdshquickjs.so not found`）——需要 arm64 真机；
- 真机上「恢复后坏插件再次把 App 拖崩」的二次循环（逻辑上是：再 5 次启动再进安全模式，名单会重新记录）；
- Node 宿主侧的崩溃是否也会被算进安全模式（不会直接算；Node 在独立进程，它崩不会杀 App）。

### 2.5 恢复入口与边界

- 恢复只把**当时开着的那批**插件开回去；安全模式期间用户手动开的插件不受影响。
- 恢复后如果仍崩，5 次启动会再次进入安全模式（名单按当时的 enabled 重算）——不会出现「恢复一次就永远回不去」。
- 安全模式不碰 Node 的开关值（`node_plugin_host_enabled` 原样保留），只是本次不自动启动；用户可在插件页手动启动。

## 四、后续风险 / 待办（给下一轮）

1. **provider 对 256k 的接受度**：如果某个 OpenAI 兼容端点回 `max_tokens too large`，当前没有自动降级重试；建议下一轮在 `OpenAiClient`/`LlmClient` 的 400 响应里识别 `max_tokens`，自动用 `min(effective, 8192)` 重试一次（只重试一次、只对 400 且文案命中）。
2. 安全模式「名单非空」的恢复需要在 arm64 真机上补验（装一个能加载的测试插件 → 触发 → 检查 `plugins.json` 的 enabled → 恢复）。
3. 安全模式目前只覆盖「冷启动崩溃循环」；如果插件是在**使用中**（打开某个插件页/选中某个壳）崩溃，用户下一次冷启动会照常触发（5 次内）。更细的「按插件归因」不做（会变成运行时监控，成本高）。
4. 本轮不升版、不打 tag、不动 `D:\dsh\native-publish`；发布前按 `docs/184` 流程走。

## 五、第二版补丁（2026-11-24 晚，用户三条新反馈）

用户：「缓存写入总显示 0 或者未计算；把计算上下文的机制照着 dsh 做；加一个显示缓存命中率」＋「安全模式应该是在加载插件之前就检测是否进入；现在加的这个，进入方式只有重启应用五次」。

### 5.1 缓存与上下文（照 `dsh-token-meter` 口径）

上游口径（`.upstream/oracle/.../dsh-token-meter/README.md`）：`tokenUsage` = 未缓存输入 / 输出 / 缓存读 / 缓存写；`contextPressure.pressureTokens` = 最新一次 provider 报告的提示词大小；命中率 = 缓存读 ÷ 整份提示词。

改动：

- `core/model/ContextUsage.kt`：新增
  - `cacheHitRate`：`缓存读 / (未缓存输入 + 缓存读 + 缓存写)`；没有缓存读或提示词为 0 → **null（未报告）**，不是 0；
  - `cacheWriteKnown`：区分「端点没返回」与「明确的 0」；
  - `cacheReported`：是否报告过缓存。
- `ui/native-shell/.../ChatComposer.kt`（上下文明细面板）：
  - 新增「缓存命中：62%（读 12.3K / 提示词 19.8K）」；端点没返回缓存读时显示「—（该端点没有返回缓存读）」；
  - 「缓存写入」三态：>0 显示数字；**=0 显示「0（自动缓存端点不单独计写入，只按命中/未命中计费）」**；null 显示「—（该端点不返回缓存写入）」——不再把未报告写成 0；
  - 拆开「本次输出 / 未缓存输入」，三段构成保留「按文本比例分摊到真实输入」的说明，避免和 DSH 的启发式构成混淆。
- 测试：`ContextUsageTest` 新增 3 例（命中率口径、未报告为 null、写入 0 与缺失区分）。

### 5.2 安全模式：不再只靠「5 次重启」

- `app/.../data/SafeMode.kt`：
  - 每次启动先看**上一次开机有没有走到就绪**（`safe_mode_last_boot_ok`）：没走到 → `failed_boots + 1`，连续 **2 次**（`SafeModePolicy.MAX_FAILED_BOOTS`）就进安全模式——插件加载期崩溃、或用户等不到界面就强杀，都算；不再需要挤在一分钟内凑 5 次；
  - 启动真正就绪时调 `markBootOk()` 清零；
  - 记录触发原因 `safe_mode_reason`（`launches` / `boot_failed` / `manual`），横幅文案按原因显示；
  - 保留原口径：60 秒内第 5 次启动。
- `app/.../chat/AppViewModel.kt`：`runtimeReady = true` 时 `markBootOk()`；新增 `enterSafeModeNow()`（手动进入：立即停用全部第三方插件）；横幅显示原因。
- `app/.../MainActivity.kt`：调试通道 `--ez dsh_safe_mode true` → 下一次界面初始化即手动进入安全模式（自救/验收用）。
- `app/src/test/.../SafeModePolicyTest.kt`：新增「连续 2 次未就绪触发」用例。

### 5.3 模拟器验证（FBD_API30 / x86_64，2026-11-24 13:32）

- 正常首启：`safe_mode_last_boot_ok=true`、`failed_boots=0`；
- 两次「启动 2s 内强杀」后：`failed_boots=1`、`last_boot_ok=false`；
- 第三次启动：
  ```

  W DshSafeMode: safe mode on: disabled=0 plugins reason=boot_failed
  ```
  prefs：`safe_mode_active=true`、`safe_mode_reason=boot_failed`；

- 横幅文案实测：「安全模式（手动进入）：已停用 0 个第三方插件…」；
- 点「恢复第三方插件」→ `safe_mode_active=false`、日志 `safe mode off`。

**新增未验**：真机上「名单非空」的两次失败触发与恢复（模拟器装不了原生插件）；`boot_failed` 在「用户手动强杀启动中的 App」时也会计数（连续两次会误进安全模式，概率低，先接受）。
