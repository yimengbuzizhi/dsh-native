## 一、问题：现在「精简」在哪里

Node 插件宿主不是真 dsh 运行环境，是**自写宿主 + 剪枝依赖树**：

| 项 | 现状 | 证据 |
|---|---|---|
| 运行时包 | `app/src/main/assets/node/runtime.zip`，zip **25,080,557 B**，解压 **2526 条 / 65,790,493 B** | `NodeRuntimeInstaller.kt:331-353`、`docs/188-evidence/p5-pre.md:39` |
| npm 包 | **36 个**（`@deepseek-ai/dsh` + 24 个 dsh-* + cordis/zod/ws/js-yaml 等） | 解压 zip 的 `dsh/node_modules/` |
| 宿主代码 | 自写 `dsh/host.mjs`（**34,091 B**）：起 cordis，只装 `dsh-system-prompt` / `dsh-tools` / `dsh-session-projection` 三个服务，外加自实现的 `llm` / `commands` 门面 | `host.mjs` 头注释 |
| 版本 | `RUNTIME_VERSION = node26.4.0-dsh0.2.2-rc.5-p3.1`；arm64 `libnode.so` 49,715,528 B（bionic Node v26.4.0） | `NodeRuntimeInstaller.kt:333`、`docs/185-evidence/P0-node-probe.md` |
| 上游树（参考） | `.upstream/oracle` 是 pnpm 全量树（0.2.2-rc.1，329 个 @deepseek-ai 包） | `docs/port/02-提示词与工具schema.md:11` |

后果（用户遇到的「写插件写坏」同类问题）：

- 插件 `import '@deepseek-ai/dsh-llm-deepseek'`／`dsh-session-persistence-jsonl`／`dsh-mcp-client` 之类 → **模块不存在**，加载失败；
- 插件 `inject` 了 `agents` / `mcp` / `skills` / `jobs` / `schedule` / `commands` 以外的服务 → cordis 报缺服务，插件「加载成功但 apply 不执行」（`docs/188-evidence/node-p2.md:174` 已记录 book-deconstruct 的案例）；
- 宿主只认领 `systemPrompt`/`tools`/`session-projection` 三类注册，**没有 turn engine、没有会话落盘、没有真实 MCP/技能/目标/子代理**；
- 所以「Node 插件」目前只能写纯工具/提示词/命令/声明式模型供应商，写不了真正的 dsh 插件。

用户要的是：**把 Node 环境做成完整的 dsh**（不要剪枝），让 dsh 插件能原样跑。

## 二、「完整」到底多大（2026-11-24 实测，不是估算）

在 PC 上用 npm 装上游生产依赖（本机 node v24.18.0，npm 走 `D:\New Folder\npm.cmd`）：

```powershell
$d='D:\dsh\.tmp-fulltree'
New-Item -ItemType Directory -Force $d | Out-Null
Set-Content "$d\package.json" '{"name":"fulltree-probe","private":true}'
cd $d
& "D:\New Folder\npm.cmd" install --omit=dev --ignore-scripts --no-audit --no-fund @deepseek-ai/dsh@0.2.2-rc.5
```

结果（Windows 宿主口径，`@deepseek-ai/dsh@0.2.2-rc.5`，670 packages）：

| 指标 | 数值 |
|---|---|
| 文件数 | **95,327** |
| 解压总字节 | **1,133.9 MB**（1,189,028,942 B） |
| 顶层包目录 | **201**（其中 `@deepseek-ai/*` **338** 个，`dsh-*` 326 个） |
| zip（Deflate Optimal，第二次独立实测） | **352,420,789 B = 336.1 MiB** |
| zip（Deflate Fastest，第一次实测） | 399,159,981 B = 380.7 MiB |
| 其中 win32 专属（`.exe/.dll/.pdb`、`win32-x64` 目录） | 265.4 MB / 921 文件 |
| 其中 office 两套 kit | **335 MB**（`libreoffice-kit-win32-x64` 189.7 MB + `libreoffice-kit-wasm` 145.3 MB） |
| 去掉 win32 后 | 868.6 MB / 94,406 文件 |
| 单独压两个 office kit | 118.8 MB（113.3 MiB）；去掉它们 ≈ **233.6 MB（222.8 MiB）** |
| 全量树里的 `*.node` 原生模块 | **16 个**（node-pty 8、office frame-forwarding 4、sharp/koffi/require-builtin/sherpa 各 1 起） |

对比现状：**解压后 1.13 GB vs 现在 66 MB（17 倍），压缩包 336–381 MB vs 现在 25 MB（13–15 倍）**。

结论（硬事实）：

1. **不可能打进 APK**：arm64 APK 现在 152,475,450 B，加 336 MB 会到 490 MB+，且首解要一分钟级。
2. Android 口径会小一些（去掉 win32 的 265 MB，换成 linux-arm64 的 sharp/node-pty 预编译，约 10–30 MB；wasm office 仍在），**估 ≈ 850–950 MB 解压 / ≈ 180–230 MiB zip（按 sdk 运行时闭包再裁 office/sharp/sherpa/map/pdb 之后）**。这个数字必须在 Linux/arm64 环境实测（见 T1），本文件不把它当定稿。
3. 所以「完整」只能是：**首次启用时联网下载 + 校验 + 落盘 + 可回滚**；或者「核心完整 + 重量级组件按需补装」。

### 2.5 但体积不是唯一的坎：Android 上「真 dsh」现在起不来

2026-11-24 的第二轮核对（读了全量树的平台包与 `dsh-app-boot` 源码）发现了比体积更硬的阻塞：

| 阻塞点 | 事实 | 证据 | 后果 |
|---|---|---|---|
| **`node-addon-require-builtin`** | optionalDependencies 只有 darwin-x64/arm64、linux-x64/arm64-**gnu**、linux-x64/arm64-**musl**、win32-x64/arm64/ia32-msvc；**没有 android** | `.tmp-fulltree/node_modules/node-addon-require-builtin/package.json` | `dsh-app-boot` 启动时 `createRequire(...)("node-addon-require-builtin")` 且**没有 try/catch**（`dsh-app-boot/lib/index.js:2565-2566`，用于 `installRuntimeInterception`，`:4030` 必走）→ **真 dsh 在 bionic 上一启动就抛**。这是 B 路线的**第一个、必须先解决**的问题 |
| ripgrep | `@vscode/ripgrep` 只有 darwin/win32/linux 平台包，无 android | `dsh-util-ripgrep` 依赖表 | `glob`/`grep` 工具 `SEARCH_FAILED`；要么自带 android `rg` 进 PATH，要么关掉这两个工具 |
| landlock 沙箱 | `@deepseek-ai/node-addon-system` 只有 glibc/musl 的 `landlock-run` + `system.node` | `dsh-sandbox-local` README:12-13 | 沙箱探针不可用；是启动失败还是每次调用失败未验证 |
| bash | dsh 按 PATH 找裸名 `bash` | `dsh-tool-bash` README:57 | Android 无 `/system/bin/bash`；App 已有 `libbash.so`，但得让 PATH 里可见 |
| node-pty | 只有 darwin/linux/win32 预编译（linux 是 glibc） | `dsh-subprocess-local/lib/index.js:1448-1449` | 普通子进程可用，**终端（PTY）不可用**；懒加载，失败报 `SUBPROCESS_PTY_UNAVAILABLE` |
| pnpm | `dsh-plugin-manager` 直接 `execa("pnpm")` | `dsh-plugin-manager/lib/index.js:538,752` | 设备上没 pnpm → `plugin_manager` 工具不可用；可用 profile patch 关掉 |
| sharp / sherpa / office | 无 android 平台包 | 依赖表 + 文件清单 | 图片解码、语音输入、Office 转换不可用；sdk profile 的 `read_image` 会受影响 |
| koffi（fs/session 的 win32 分支） | 只在 win32 分支懒加载 | `dsh-fs-local/lib/index.js:16,27-29` 等 | **不是 Android 阻塞项**（POSIX 路径不 import） |

结论：**B 路线要先解决 `node-addon-require-builtin` 的 android arm64 版本**（自己用 NDK 编一个 N-API addon，或改 boot 逻辑跳过 interception——后者等于给上游打补丁，违反 `docs/185` D7）。这是「完整 DSH」真正的技术门槛，比 336 MB 的下载更关键。

## 三、三条路线（必须先让用户拍板）

| | A. 完整依赖树，保留自研宿主 | A+. 完整依赖树 + 完整服务面（cordis base） | B. 真 DSH 内核（sdk profile） |
|---|---|---|---|
| 做法 | runtime 换成全量 npm 树；`host.mjs` 仍只提供现有 4 类注册 | 全量树 + 在宿主里把 dsh 的完整 cordis 组合（`dsh-base` 等）装起来，插件 inject 什么都有 | 子进程跑 `dsh --profile sdk`（真 dsh 内核），App 通过 stdio JSON-RPC 当客户端 |
| 插件能 import 任意 dsh 包 | ✅ | ✅ | ✅ |
| 插件 inject 任意服务 | ❌（宿主没有） | ✅（服务在，但宿主仍是 App 的从属） | ✅（真内核） |
| 原生 App 的聊天/工具/审批 | 不变 | 不变 | **全部重做**：turn engine、会话、工具、审批、目标、子代理、定时都改由 dsh 负责 |
| 工作量 | 中（下载器 + 打包） | 大（要 patch 组合、服务归属、双引擎冲突） | 很大（等于换内核，月级） |
| 风险 | 低（不碰现有链路） | 中高（两个引擎抢会话/工具） | 高（ABI、内存、启动、数据归属） |
| 回滚 | 关开关回精简版 | 同左 | 同左 |

**建议**：先做 **A**（满足「环境完整」这个字面诉求，风险最低），B 的 PC spike 已经跑通（§6.5），但 Android 侧还卡在 `node-addon-require-builtin` 没有 android 包（§2.5）——**这不是「接一个协议」能绕过的，要么自编 arm64 addon，要么放弃 B**。T1 之后把「A 的真实体积」和「B 的 addon 工作量」一起给用户拍板，不要先动 App 的回合链路。

## 四、一句话的现状对照（为什么 B 很贵）

App 现在自己就是一套内核：`core/engine/TurnEngine.kt`（工具循环/审批/压缩/子代理/目标）、`core/session`（session.v4）、`core/tools`（90+ 内置工具）、`AppViewModel`（约 11,000 行编排）。`dsh --profile sdk` 提供的是同一层能力（真 dsh agent loop + 真 session.v4 + 真工具集），两者会**抢会话文件、抢工具名、抢审批**。B 不是「接一个 API」，是「把 App 的编排层换成 dsh 的编排层」，界面状态（ChatSessionState 等）要重写成 `session.event` 的投影。

## 五、方案 A：完整依赖树（推荐先做）

### 5.1 产物

- `runtime-full-<version>-arm64.zip`：
  ```
  lib/<abi>/*.so            # 现有依赖库（arm64 只放 arm64；x86_64 见 §7.2）
  dsh/host.mjs              # 现有宿主（A 阶段不改）
  dsh/node_modules/...      # 全量生产树（含所有 @deepseek-ai/*）
  dsh/node-host-plugins.json
  install.json              # version/entries/bytes 由安装器写
  ```
- 同时保留现在的精简 `runtime.zip`（25 MB）作为**离线兜底**：完整包下载失败/校验失败 → 提示并回落到精简版，Node 宿主照常可用（只是能力回到 0.3.6）。
- 校验：构建时算 SHA256，写进 APK 的常量（`NodeRuntimeInstaller` 新增 `FULL_RUNTIME_SHA256`），下载后先校验再解压；解压后再用条目数/字节数与 `install.json` 对账（现有 doctor 逻辑复用）。

### 5.2 构建（在 Linux/arm64 或 WSL/docker 里做，不要在这台 Windows 直接装）

```bash
# 目标：Android arm64 口径
mkdir -p /tmp/full && cd /tmp/full
cat > package.json <<'EOF'
{"name":"dsh-full-runtime","private":true}
EOF
npm install --omit=dev --ignore-scripts --no-audit --no-fund \
  --os=linux --cpu=arm64 @deepseek-ai/dsh@0.2.2-rc.5   # --os/--cpu 是否生效要实测；不生效就用 arm64 容器
```
- 若 `--os/--cpu` 不生效：用 `docker run --platform linux/arm64` 或 arm64 CI 跑同一命令。
- 装完把 `node_modules` 按上面结构打包；`host.mjs` 从当前 zip 里原样取出（不要重写）。
- 记录：文件数、解压字节、zip 字节、SHA256、构建机口径，写进 `docs/` 证据。

### 5.3 安装器改造（`NodeRuntimeInstaller.kt`）

新增（与现有 assets 解压并行，不替换）：

1. `fullRuntimeUrl` / `fullRuntimeSha256` / `fullRuntimeBytes` 常量（或从 BuildConfig 读，避免污染）；
2. `ensureFullRuntime(onProgress)`：HEAD 探大小 → 磁盘余量检查（需要 `zip + 解压 ≈ 1.3 GB`）→ 断点续传（OkHttp `Range`，临时文件 `runtime-full/<v>.part`）→ SHA256 校验 → 解压到 `runtime/<version>-full/`（复用现有流式解压与限额，但**不能套用插件的 64 MB/256 MB 限额**，要单独放开）→ 写 `install.json`；
3. 取消/失败：删除 `.part` 与半成品目录；把失败原因写 prefs（供 `nodehost_doctor` 报）；
4. 并发：同一时刻只允许一个下载（mutex + prefs 标记），进程被杀后靠 `.part` 续传；
5. 版本切换：`data/node_modules` 软链指向当前生效运行时（现有逻辑）；
6. 回滚：设置里「运行时：完整 / 精简」两档，切回精简即删/忽略 full 目录（不要删用户插件）。

UI（插件页 Node 分区）：

- 关 → 开时先弹「完整运行时需要下载约 XXX MB」确认（数值来自常量，不要写死文案）；
- 进度：复用现有 `NodeBootProgressUi` 五态（Extracting 之外新增 Downloading），显示 MB/MB 与取消；
- 失败横幅：「下载失败 / 空间不足 / 校验失败」+ 重试 + 「用精简版继续」。

### 5.4 验收（A）

1. JVM：下载器单测（假 HTTP server / 假文件）、校验失败回滚、空间不足文案、断点续传、并发互斥；
2. 模拟器：x86_64（见 §7.2）上「下载 → 解压 → host READY → 导入一个 import 了 `@deepseek-ai/dsh-llm-deepseek` 的测试插件 → 能加载」；
3. 真机（拿到 adb 后）：同链路 + 首次下载耗时/解压耗时/磁盘占用/RSS 记录；
4. 证据存 `docs/192-evidence/`（未跟踪）。

## 六、方案 B：真 DSH 内核（spike 之后再决定）

### 6.1 上游事实：`dsh --profile sdk` 就是为「外部客户端驱动」准备的

`.upstream/oracle/node_modules/.pnpm/node_modules/@deepseek-ai/dsh-sdk-protocol/README.md`：

- 传输：**stdio 每行一个 JSON-RPC 2.0 帧**（`id+method`=请求，`id`=响应，`method`=通知）；
- client→server：`initialize`、`session/prompt`、`session/query`、`session/resume`、`session/wait`、`session/working-directory/get|set`、`shutdown`；
- server→client：`approval/request`、`user-question/ask`、`user-question.cancelled`、`session.event`、`session.status`、`session.query.completed`、`subagent.started`、`subagent.finished`；
- `initialize.approvalRequests=true` 才有审批卡；`initialize.maxTokens` 可选（输出上限，**正好接本轮取消 8192 的改动**）；`capabilities.userQuestions=true` 才有原生提问；
- stdout 只能是协议帧，日志必须走 stderr（`dsh-sdk-jsonrpc-server/README.md`：`stdout is the protocol`）。

`dsh --profile web` 起 HTTP（浏览器 GUI）、`headless` 一次性任务退出——都不适合当 App 内核；**sdk profile 是唯一合适的内嵌形态**。

### 6.2 桥接改造清单（若用户选 B）

| 现类 | 现状职责 | B 下的变化 |
|---|---|---|
| `NodeHostProcess.kt` | spawn `libnode.so host.mjs`，等 `HOST_READY <port>`，走回环 WS | 改成 spawn `libnode.so dsh/lib/bin.js --profile sdk`，**stdin/stdout 做协议**，等 `initialize` 响应而不是 HOST_READY；stderr 进日志缓冲；进程组回收保留 |
| `NodeBridgeCore.kt` | WS 帧（hello/tool.invoke/prompt.assemble…） | 重写为 JSON-RPC 帧编解码 + pending 表（请求 id 关联；通知分发） |
| `NodeHostTools.kt`（53 KB，9 个 `nodehost_*`） | 管理自研宿主 | 保留 `status/logs/doctor/control/repair` 的**外壳**，内部改成管理 sdk 进程；`install/uninstall` 改成 dsh 插件管理（`dsh plugin` 需要 pnpm，见 §6.4） |
| `NodePluginHost.kt`（31 KB） | 状态机/崩溃重启/审计/隔离 | 生命周期与崩溃策略可复用；「插件」概念变成 dsh profile 的插件（cordis yml），隔离粒度要重新定义 |
| `NodePluginInstaller.kt` | 插件 zip/目录导入 | dsh 插件是 npm 包 + profile 行；导入语义要改（或保留「zip 解到 profile plugins 目录」） |
| `AppViewModel` | 原生回合/会话/工具/审批 | 会话事件改成订阅 `session.event` 投影；工具审批改成 `approval/request` 应答；提问改 `user-question/ask`；`TurnEngine`/`Compaction`/`ToolRuntime` 逐步退役或只服务「本机模式」 |
| `NodeLlmProviders.kt` / `NodeCommands.kt` / `NodePromptSections.kt` | 自研宿主的扩展面 | 由真 dsh 的 `llm`/`commands`/`systemPrompt` 取代，代码可删 |

### 6.3 数据归属（必须写死一个口径）

- dsh 用 `DSH_HOME`（`dsh-home-paths`）落 session.v4；App 现在也写 session.v4（`core/session`）。
- **不要两个进程同时写同一棵树**。B 的方案里建议：dsh 用 `files/node/dsh-home/`，App 的会话库只读导入 dsh 的会话（或反过来把 App 会话作为 workspace 内容给 dsh 读）。
- 迁移/互操作需要先做格式对拍（App 的 `session.v4` 与 dsh 0.2.2-rc.5 的 codec 是否逐字节兼容，`docs/port/01-会话v4格式.md` 有旧对拍，需要按 rc.5 复查）。

### 6.4 B 的硬风险

1. **ABI/平台（详见 §2.5）**：`node-addon-require-builtin` 没有 android 包且启动必经 → **真 dsh 在 bionic 上一启动就抛**；其次是 `rg`、landlock-run、bash、node-pty、pnpm、sharp/office。要么自编 arm64 addon + 补 PATH + profile patch 关工具，要么给上游打补丁（禁止）。
2. **内存**：dsh 是桌面级进程，冷启 RSS 预计 150–300 MB（现在宿主 73 MB）；低端机会被系统杀。
3. **启动**：全量树 + cordis 组合，冷启估计 2–6 s（现在 1.3–1.7 s），要有启动卡与超时。
4. **权限**：dsh 的 bash/terminal/fs 工具默认跑在 App 的 uid 里；审批、路径沙箱、workspace 目录都要重新映射到 App 的 `files/workspace`。
5. **插件管理**：dsh 的 `plugin` 命令依赖 pnpm；手机上要么内置 pnpm（+ 网络装包），要么只支持「预装 profile 内的插件」。
6. **升级**：dsh 版本与 App 的 session 格式、提示词、工具名强耦合；升级要重跑对拍（`parity/`）。

### 6.5 B 的 spike：**PC 上已跑通（2026-11-24）**

在 Windows + node v24.18.0 上，用 `.upstream/oracle` 的 pnpm 全量树（0.2.2-rc.1）跑成了完整链路，证据脚本在 `D:\dsh\.tmp-probe2\`（`probe-sdk.mjs`、`probe-tools.mjs`，dshhome 也在那里）：

```powershell
$env:DSH_HOME="D:\dsh\.tmp-probe2\dshhome"
& "D:\New Folder\node.exe" "D:\dsh\native\.upstream\oracle\node_modules\@deepseek-ai\dsh\lib\bin.js" --profile sdk --help
# -> Usage: dsh --profile sdk … EXIT=0；首次自动生成 profiles\sdk\{package.json,cordis.yml,cordis.patch.yml,pnpm-workspace.yaml}
```

## 七、PC 验证（没有手机 adb 时怎么做）

用户 2026-11-24：「目前没有无线调试 先用电脑虚拟机」。两条路都要准备：

### 7.1 桌面直跑（最快，验证 JS/host/协议，不验证 Android 集成）

- Windows 上已有 node v24.18.0（`>=24.9`，满足 dsh engines）。
- 解压 `runtime.zip`（或全量树）到临时目录，直接 `node dsh\host.mjs` 跑现有宿主（注意：`DSH_NODE_TOKEN`/`DSH_NODE_DATA` 两个环境变量必须给，否则宿主拒绝监听）。
- 全量树跑 `node ...\@deepseek-ai\dsh\lib\bin.js --profile sdk`，按 §6.5。
- 局限：Windows 与 bionic 的路径/二进制不同，**只能证明 JS 层与协议层**；`.so` 相关（libnode、icu）不参与。

### 7.2 Android 模拟器（x86_64）：现在缺 `libnode.so`，可以补

现状：模拟器包是 x86_64，`libnode.so` 只有 arm64 → Node 宿主必然 FAILED（`docs/190` 已把它当已知 ABI 限制）。

补法（Termux 有 x86_64 包，实测仓库可达；2026-11-24 两轮核对）：

- `nodejs` **26.13.1**，x86_64 deb **11,218,604 B**（`pool/main/n/nodejs/nodejs_26.13.1_x86_64.deb`），`Installed-Size: 51472`，解包后 `data/data/com.termux/files/usr/bin/node` **50,715,096 B**；依赖 `libc++, openssl, c-ares, libicu, libsqlite, zlib, libffi`。
- 备选：`nodejs-lts` **24.22.3**（deb 10,434,768 B，同样满足 `>=24.9`）。
- 把 `bin/node` 复制成 `app/src/main/jniLibs/x86_64/libnode.so`（必须叫 `libnode.so` 才会被装进 `nativeLibraryDir` 并获得 exec 权限；`NodeRuntimeInstaller.binaryFile` 就是读这个名字）；
- 依赖库从对应 deb 取：`libc++_shared.so`、`libcrypto.so.3`、`libssl.so.3`、`libcares.so`、`libffi.so`、`libicu{uc,i18n,data}`、`libsqlite3.so`、`libz.so.1`，放进运行时的 `lib/`（x86_64）；
- **版本必须同一快照**：Termux 现在的 ICU 是 **79.1**，而 arm64 `runtime.zip/lib` 里是 **78**；混搭会 `dlopen` 失败（`libicudata.so.78` vs `79`）。x86_64 这套库只能配 26.13.1 一起用。
- `libcrypto.so.3` 这种名字不能进 jniLibs（只收 `lib*.so`），只能走 assets 解压 + `LD_LIBRARY_PATH`（现有 `runtime.zip` 就是这么做的）；
- `runtime.zip` 的 `lib/` 目前只有 arm64，两个 ABI 不能混用：要么按 ABI 分 zip，要么 `lib/<abi>/` 分目录（安装器按 `Build.SUPPORTED_ABIS[0]` 选）；
- 构建：`gradle :app:assembleDebug -PabiSplits`（x86_64 包），装到 FBD_API30 模拟器验证 `HOST_READY`。
- 注意：Termux Node 26.13.1 与 arm64 的 26.4.0 不同，**只用于模拟器功能验证**；真机仍用 arm64 26.4.0。`OPENSSL_CONF=/dev/null` 在 arm64 上是必需的（`NodeHostProcess.kt:18-20`），x86_64 是否同样需要**未验证**。

### 7.3 JVM 测试（不依赖设备）

- 下载器/校验/回滚（§5.3）；
- JSON-RPC 编解码与 pending 表（B 方案）；
- `NodeRuntimeInstaller` 条目数对账（现有 `NodeRuntimeInstallerEntryCountTest` 要按新 zip 更新）。
