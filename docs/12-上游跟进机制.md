# 12 · 上游跟进机制（从第一天就要留的门）

> 2026-11-06｜用户要求：这个项目以后要跟上游，**创建时就要预备升级门路**。
> 本文是「怎么跟」的工程约定；节奏见 `00-立项与契约.md`（只追 stable，季度合并）。

---

## 一、总原则

1. **版本只有一个来源**：`upstream.toml`。代码里不许写死上游版本号。
2. **每个上游包都要有归属**：上游 309 个包 → 我们的模块，一张映射表说得清。
3. **升级 = 一次可复现的流水**，不是「凭记忆改一遍」。
4. **契约夹具是尺子**：先用旧内核生成夹具，再用对拍台量新实现。
5. **易变的东西关进防腐层**：提示词、schema、会话格式、provider 协议，各自一个适配点。

---

## 二、版本源

根目录 `upstream.toml`：

```toml
[upstream]
package   = "@deepseek-ai/dsh"
version   = "0.2.1-rc.2"
channel   = "stable"
ported_at = "2026-11-06"
notes     = "首次移植基线"
```

构建时由 Gradle 任务生成 `UpstreamInfo.kt`（版本/通道/日期），并进 `BuildConfig`；
「关于」页和日志都从这里取，**永远不手写**。

## 三、包 → 模块映射

`docs/upstream/mapping.tsv`：一行一个上游包。

| 列 | 含义 |
|---|---|
| `package` | 上游包名（`@deepseek-ai/dsh-tool-fs`） |
| `group` | 归类（tool / api / session / llm / agent / ui / infra） |
| `module` | 我们的 Gradle 模块（`:core:tools`） |
| `status` | `planned` / `ported` / `adapted` / `ignored` |
| `note` | 差异说明（为什么 adapted/ignored） |

规则：
- `status=ignored` 必须写理由（例如 `dsh-experimental-inspector`：开发工具，不做）
- 升级时跑 `tools/upstream/check.ps1`：**出现未映射的包就报错**，防止上游新增功能被漏掉

## 四、增量报告（每次升级的输入）

`tools/upstream/fetch.ps1 -Version <ver>`：
1. 从 npm 拉**未剪枝**的包（带 `src/*.ts`，当初为了省体积剪过，别用剪过的树）
2. 解到 `upstream/cache/<ver>/`（不入库）
3. 对比上一版：按包统计改动文件数 / 行数 / 是否动到 schema
4. 产出 `docs/upstream/reports/<old>-to-<new>.md`，分三类：
   - **A 提示词/文案**（低风险，直接搬）
   - **B 工具 schema / API**（中风险，要同步适配层）
   - **C 行为/协议**（高风险，要对拍）

升级时先看报告，再决定这次是「小补」还是「大合并」。

## 五、防腐层（`:core:port`）

上游最容易变的四样东西，各自一个接口，改动只落在适配器里：

| 接口 | 隔离什么 | 上游变了怎么办 |
|---|---|---|
| `PromptAssembler` | 系统提示词怎么拼 | 只改这一个类 + 重新生成夹具 |
| `ToolSchema` | 工具参数怎么描述 | 改 schema 定义 + 跑 schema 对拍 |
| `SessionCodec` | v0~v4 会话格式 | 注册新版本 codec，旧版本保留只读 |
| `ProviderAdapter` | 模型通道协议 | 只改 adapter，不动 agent 循环 |

纪律：**UI 和 agent 循环不许直接碰上游镜像的内部结构**，只能调这些接口。

## 六、契约夹具（升级的尺子）

`parity/fixtures/upstream-<version>/`：

```
tools.json          # 30 个工具的 JSON Schema
prompts/            # N 个场景下发给模型的完整 request body
session/            # 一条样本会话的 v4 文件 + 解压后的 JSONL
behaviors/          # 工具行为的输入/输出样本
```

生成方式（开发机，用旧内核的 Node）：

```bash
node tools/upstream/export-fixtures.mjs --home <旧内核> --out parity/fixtures/upstream-<ver>
```

升级后重新生成 → 与旧夹具 diff → 差异就是这次要移植的清单。

## 七、版本化与迁移

| 东西 | 策略 |
|---|---|
| 会话格式 | 读 v0~v4 全支持；只写 v4；新版本先加只读 codec |
| 插件 API | `api_version` 主次版本；不兼容变更升 major，旧插件提示升级 |
| 配置 | 每个字段带引入版本；读取时跑迁移链 |
| 数据库/索引 | schema version + 迁移脚本，禁止隐式改表 |

## 八、升级流水（每季度一次）

```
① 改 upstream.toml（版本 + 日期）
② tools/upstream/fetch.ps1  → 增量报告
③ 生成新夹具 → 与旧夹具 diff
④ 按报告分派：A 直接搬 / B 改适配层 / C 跑对拍
⑤ tools/upstream/check.ps1  → 映射完整、无遗漏
⑥ 对拍台全绿（7 条契约）
⑦ 真机冒烟（装机/起会话/调工具）
⑧ 打 tag `port/<ver>`，写 CHANGELOG-PORT，归档
```

## 九、提交与分支

- 提交前缀：`port(<上游包>): ...`，正文写「对应上游 <ver>」
- 每个完成版打 tag：`port/1.20.1`、`port/1.21.0`
- 长期分支：`main`（我们的实现）+ `upstream/<ver>`（移植快照，可选）
- `CHANGELOG-PORT.md` 由报告汇总生成，人可读
