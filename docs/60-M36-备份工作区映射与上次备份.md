# 60 · M36：跨设备恢复的工作区映射 + 「上次备份」

日期：2026-11-08 03:17–03:3x（第三十二棒）
基线：`c1d60a3` + 本轮

> 补 `docs/59 §七.2` 的缺口：从别的设备恢复备份时，会话 `header.cwd` 还是原设备路径；
> 新设备上那个目录不存在时，聊天能看、工具写入会失败。这一轮把「恢复时映射到当前工作区」
> 做了，并顺手补了备份页的「上次备份时间/大小」。
> 设备整夜锁屏（`mDreamingLockscreen=true`），**本轮仍没有 UI 截图**；功能用单测 + 调试通道真机验证。

---

## 一、一句话结果

- **恢复会话时**：原 `header.cwd` 在本机不存在/不可写 → 只改会话 header 的 `cwd` 到**当前工作区**，
  并把会话目录挪到对应的 `<workspace-slug>/<id>`；事件帧**逐字节保留**；
- 只读的旧版导入会话（有 `imported.json`）**不映射**，保留历史工作区标签；
- `manifest.json` 每条会话多了 `cwd`（导出时快照）：恢复确认弹窗会提前提示
  「其中 N 条会话的原工作区在本机不可用，会映射到当前工作区」；
- 恢复结果卡显示「N 条会话的工作区已映射到 …」；
- 备份页新增「上次备份」卡（时间 / 包大小 / 会话数 / 插件数），记录在独立 prefs，**不进备份包**；
- 单测：`SessionCwdTest` **10 条**全过；`NativeBackupTest` 从 7 → **9 条**全过；全量 **369 条 0 失败**。

真机（PLT120，锁屏调试通道）：

## 二、映射规则（保守优先）

| 情况 | 行为 |
|---|---|
| `cwd` 空白（旧版/异常会话） | 不动（按默认工作区语义） |
| `cwd` 在设备上 `isDirectory && canWrite` | 不动（同设备恢复、App 私有默认工作区都走这条） |
| 旧版只读会话（目录里有 `imported.json`） | 不动（保留原工作区，方便回看来源） |
| 原 `cwd` 不存在/不可写 | 改成当前工作区，目录跟到新 slug |
| 当前工作区本身不可写 | 不改，恢复结果里报一条错误（会话仍恢复成功） |
| 会话文件 > 64MB | 不改，报「跳过工作区映射」（App 打开这种文件本身也会 OOM） |
| 第一帧不是标准 zstd / header 不是 JSON | 不改，报错并保持原文件 |
| 目标目录已有同 id 会话 | 不改目录（header 已映射；会话仍能按 id 打开），报一条错误 |

**只改第一帧**：`header` 一行 JSON 里只覆盖 `cwd`，其它字段（包括未来新增的未知字段）原样保留；
后面的每条事件帧按原字节接回去。写入是 `同目录临时文件 + rename`，失败时原文件不动。

## 三、实现

| 层 | 文件 | 职责 |
|---|---|---|
| `:core:session` | `SessionCwd.kt`（新） | `readCwd` / `remapIfNeeded`：只解析第一帧，改 header，保留事件帧 |
| `:core:session` | `ZstdFrames.kt` | 新增 `firstFrameLength()`（按 zstd 帧格式走 block header）与 `decompressFrame()` |
| `:core:backup` | `NativeBackup.kt` | `BackupSessionEntry.cwd`；`export(sessionCwds=…)` 把导出时的 cwd 写进 manifest（旧备份无此字段照常解析） |
| App | `BackupManager.kt` | `restore(..., mapMissingCwdTo=当前工作区)`：恢复后逐条映射 + 挪目录；`ExportRecord`（含 zip 字节数）、`LastExport`（独立 `backup_state` prefs） |
| App | `BackupScreen.kt` | 「上次备份」卡、导出包大小、恢复确认里的映射提示、结果卡里的映射条数；`currentWorkspace` 参数 |
| App | `App.kt` / `AppViewModel.kt` | 传当前工作区；调试通道 `dsh_backup_import` 也带映射、日志多 `cwdRemapped=` |
| 工具 | `tools/backup-fixture/CrossDeviceBackup.java`（新） | 从真实会话造一份「原 cwd 不存在」的备份，供真机验证 |

为什么不改所有会话？只处理**本次真正恢复落盘**的 id；恢复时同 id 已存在会跳过，不会碰旧数据。
为什么 legacy 不映射？它是只读回放，映射没有收益，还会把「这条会话原来在哪个目录」的信息弄丢。

## 七、边界（诚实清单）

1. **只映射「恢复时新落盘」的会话**；已存在的同 id 会话不会改（恢复语义就是只补不删）。
2. **legacy 只读会话不映射**：保留历史工作区标签，避免把来源信息改掉。
3. **映射是「原路径不可用」触发，不是「和当前工作区不同」触发**：例如另一台设备恢复后
   `cwd=/storage/emulated/0`（路径存在且可写）就不改，会归到 `/storage/emulated/0` 工作区。
4. **>64MB 会话跳过映射**：App 打开这种文件本身会 OOM；先保证恢复成功。
5. **不改事件正文**：历史消息里的旧路径文字保持原样（工具结果里的路径是历史记录）。
6. **manifest 的 cwd 是导出时快照**：导出后会话 header 再变，旧备份里的 cwd 不会自动更新。
7. **UI 仍未截图**：本轮所有 UI 改动只有编译保证。
8. 只改 header，不改 `header.createdAt`/`id`/`parentSession` 等其它字段。
