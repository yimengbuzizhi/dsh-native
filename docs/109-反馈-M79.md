### 1）长线任务「突然停下来」（原因未知）

**能拿到的最硬证据**：`adb shell dumpsys activity exit-info xin.dshaa.nativeapp` 里，
鲸歌进程有两次**被系统杀掉**的记录，importance 都是 **125（前台服务进程）**：

```text
timestamp=2026-11-12 21:19:37.055 pid=20475 reason=13 (OTHER KILLS BY SYSTEM) subreason=2040
  importance=125 description=stop xin.dshaa.nativeapp due to from pid 1602|40|F|M:211,64|J:250
timestamp=2026-11-12 03:49:05.744 pid=30323 reason=13 (OTHER KILLS BY SYSTEM) subreason=2003
  importance=125 description=stop xin.dshaa.nativeapp due to from pid 1602|3|F|C:[84]|U:1|M:301,180|J:200
```

ColorOS 在「长任务跑着」时把带前台服务的进程也杀了，这是「突然停、原因未知」最可能的外部原因；
**这轮没有复现到「模型自己停住而进程还活着」的回合**，所以没有把它写成已修。代码侧只做兜底：

- LLM 流式读取超时：`readTimeout(0)`（永不超时）→ **180 秒**（`LlmClient.defaultClient` /
  `OpenAiClient`）。服务端假死时原来这一轮会永远挂着，现在 180 秒没有任何字节就按网络错误收口；
- 空收口可见化（`AppViewModel.startTurn` finally）：一轮结束、没有错误、但最后一条 assistant
  既没正文也没工具调用时，给一条提示「本轮结束但没有正文（模型只回了空内容），发「继续」可以接着做」，
  日志 `DshTurn: turn ended without assistant text session=…`；
- 常驻 FGS 仍是待用户拍板项（`docs/103 §十`），这轮没动。

### 2）人设字段：导入 md/txt + 全屏（照 RikkaHub `TextArea`）

**根因**：`SettingsTextField` 的多行输入框没有高度上限、没有导入入口，长文只能在小框里滚。

**改法**（`ui/design/component/Settings.kt` + `ui/settings/AssistantScreen.kt`）：

- `SettingsTextField` 新增 `collapsedMaxHeight`（多行默认 **132dp ≈ 6 行**，超出框内滚动）和
  `footerActions`（输入框下方动作条）。
- 新组件 `AssistantLongField`（简介/开场白/人设/系统提示词四个字段都换它）：
  - 左下角字数，右下角「**导入文件**」「**全屏**」两个带文字图标的按钮；
  - 导入：SAF `OpenDocument`，MIME 收 `text/*`、`text/markdown`、`application/json`、
    `application/octet-stream`（.md 常被识别成 octet-stream）；IO 线程读，**上限 2MB**，
    BOM 探测（UTF-8 / UTF-16LE / UTF-16BE）→ 严格 UTF-8 → 失败回退 **GB18030**；
    CRLF→LF、去尾部空白；成功 Toast「已导入 N 字」，空文件不覆盖；
  - 全屏：`Dialog(usePlatformDefaultWidth=false)` 整页编辑，「取消 / 编辑·字段名 / N 字 / 保存」，
    返回键=取消（本地草稿，不保存不落库——RikkaHub 是点外面直接丢，这里没有照抄）。
- 与 RikkaHub 的差别：RikkaHub 每个输入即整份 Settings 序列化；我们仍走
  `SettingsStore.updateAssistantProfile`（只落当前这份）。

**真机证据**：`111-03`（四个字段的字数 + 导入文件 + 全屏）、`111-04`（从
`Download/test-persona.md` 导入，Toast「已导入 128 字」、字段完整显示）、
`111-05`（全屏编辑器，128 字全文）。

### 3）全部二级页的进入/退出动画

**根因**：`ui/App.kt` 的 `body` 是 `Box { when (screenName) { … } }`，直接换内容，没有转场。

**改法**：路由收成 `NavRoute(page, sub)`，用 **`AnimatedContent`** 统一包住所有一级页/二级页：

- 方向按层级差（聊天 0 < 一级页/设置 1 < 设置二级页 2）：进更深一层从右滑入、返回从左滑入；
  同层级（设置→会话列表）用 `navForward` 标记是「进」还是「退」；
- 时长：滑入 260ms / 淡入 200ms，滑出 260ms / 淡出 160ms，`SizeTransform(clip=false)`；
- 设置→二级页、二级页→设置、聊天→记忆库/插件/任务、抽屉→设置，全部走同一条路径。

**真机证据**：`111-01`（聊天→设置，设置页在滑动途中叠在聊天上）、
`111-02`（设置→助手配置，二级页滑入途中）。

### 4）记忆库退回到设置（应回聊天页）

**真机证据**：`111-06`（输入栏→记忆→打开记忆库→系统返回，落回聊天页，不是设置）。

### 6）悬浮窗输出把思考/工具文字铺进正文

### 7）可设置「用到一定程度自动压缩上下文」

**根因**：自动压缩 M44 就有，但触发线写死 `窗口 × 0.8`，界面上既看不到也改不了；
模型窗口只在「模型配置」里按模型填，聊天页只显示一个圆环，用户不知道有这功能。

**改法**：

- `SettingsStore`：`auto_compact`（开关，默认开）+ `auto_compact_ratio`（0.3–0.95，默认 0.8）；
- 引擎：`TurnDeps.compactionRatio`（默认 0.8，兼容旧测试）→
  `Compaction.Policy.resolve(window, maxOutput, ratio)`，阈值
  `min(floor(W×ratio), W−O−B)`；关掉自动压缩时 `contextWindow` 直接给 null（手工压缩不受影响）；
- 设置 → 显示与行为新增「**上下文与压缩**」：开关、触发比例 50/70/80/90、当前模型窗口说明；
- 聊天页输入栏设置新增「**上下文**」分组：已用 % / 最近请求 tokens / 窗口、自动压缩开关、
  比例 chips、「**立即压缩上下文**」（`/compact`，不占模型轮次）；
- 本会话还没发过请求时圆环与面板用模型窗口兜底（显示 0%，不再是「窗口未知」）。

**真机证据**：`111-11`（设置页：开关 + 80% + 窗口 1048576）、
`111-13`（输入栏面板：0% / 0 / 1048576、80% 选中、立即压缩）、`111-18`（未发消息时的兜底显示）；
prefs 落盘 `auto_compact_ratio=0.8`；`:core:engine:test` **20/20**，新增
`autoPolicyUsesUserRatio`（0.5→32768、0.9→被 pressureBudget 夹到 49152、越界值收敛）。

### 8）工具执行中点「停止」不能立刻停

**根因**：引擎里的取消依赖协程在挂起点收到 `CancellationException`；工具内部大量
`runCatching`（包 `Throwable`）会吞掉取消，`stop()` 又要等引擎 finally 写完 `turn/end`，
界面 3 秒兜底才复位，所以「点了没反应」。

**改法**：

- `ChatSessionState.stopping`：点停止立刻置 true、状态条改「正在停止…」，
  finally 复位；兜底从 **3s → 1.5s**；
- `TurnEngine` 工具循环每进一个工具前显式检查 `deps.stop.requested`，
  已点停止就直接抛 `CancellationException`（防工具吞取消）；
- `BashTool` 本身已是可取消（`readCancellable` 取消时 `destroyForcibly`），真实杀进程。

**真机证据**：`111-16`。设备上发
`Use bash to run sleep 90 then reply OK only.`，等 bash 跑到第 14 秒点停止：

```text
22:03:33.466 turn start …
22:03:47.5xx  点「停止生成」
22:03:47.573 I/DshTurn: turn end after 14107ms
```

从点击到 `turn end` **约 540ms**（含 250ms 轮询粒度）；`ps -A` 里 `sleep 90` 已不存在；
界面回到可发送状态（`111-16` 工具卡折叠、停止图标变回发送箭头）。

### 9）「发消息后长时间没反应，重进后会话不在」

**实测结论：这轮复现不到「会话不在」。** 用黑洞端点（`--es dsh_base_url http://10.255.255.1:9`）
发一条消息，在请求挂着时读会话目录：**发消息的同一帧里会话目录已创建**（59→60），
随后 `am force-stop` 杀掉进程，冷启动后目录仍在（60），抽屉里能看到 `HANGTEST 只回复两个字：OK`（`111-17`）。

- 会话语义：`TurnEngine.runTurn` 第一步就是 `sessions.create()`（IO 线程、写 header 帧）→
  `request/header` → `turn/start` …，全部同步落盘，`create()` 里还立刻 `refreshSessions()`，
  所以「发出去」的会话不会只存在于内存。
- 但「长时间没反应」是真的：原来 LLM 读取 `readTimeout(0)` **永不超时**，服务端假死时这一轮会一直挂着，
  用户只能杀进程——杀进程这一轮就没有 assistant 消息，观感像「会话丢了」。
  这轮改成 **180 秒无字节即失败**，并给「空收口」提示（见第 1 条）。
- 仍可能有「列表看不到」的场景：抽屉/会话页按**当前工作区**过滤；如果重启后当前工作区变了，
  其它工作区的会话不会显示。这轮没有改列表语义（会涉及产品取舍），先如实记录。
