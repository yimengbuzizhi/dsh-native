## 二、用户新需求（优先级最高）

1. **AI 通过终端调用 Shizuku 权限很麻烦**（用户 2026-11-28 20:2x 明确补充，原话：「终端用 shizuku 麻烦主要是 ai 通过终端调用 shizuku 权限很麻烦」）：
   - 现状：AI 的 `bash` 工具跑在 PTY/proot 里，uid 是 app；需要 shell 权限的命令（`pm` / `settings` / `am` / `dumpsys` / `input` / `cmd` 等）只能靠 Shizuku 的 `rish` 手工套，`rish` 要自己找/复制/授权，`cd`、环境变量、引号、退出码都容易丢；失败时 AI 只看到 `Permission denied`，不知道该换什么方式。
   - 目标：让「需要特权的那条命令」对 AI 变成一个**直接可用**的通道，而不是每轮手工拼 `rish`。
   - 建议方案（实现前先和用户确认走哪条，可组合）：
     a) **预置 rish**：宿主把 Shizuku 的 `rish` 装到 `files/toolchain/bin/rish`（或 `busybox-bin`，PATH 能命中），包装脚本要保留 `cwd`/`env`/`$?`；AI 可直接 `rish -c 'pm list packages'`。
     b) **专用执行通道**：宿主暴露 `shizuku.exec` 能力（Binder 调用 Shizuku API，参数 `command`/`cwd`/`env`/`timeout`），AI 用专用工具调用；`bash` 工具在 app uid 失败时返回结构化提示「该命令需要 Shizuku 权限，请用 shizuku_exec 或 `rish`」。
     c) **授权引导**：终端页/设置显示 Shizuku 状态（未安装 / 未运行 / 未授权 / 可用），一键跳转授权；Shizuku 授权是持久的，不要做成每次弹窗。
   - 安全：特权执行走现有 approval/审计（记录命令 + shizuku 标记），危险命令（`pm`/系统设置/`rm -rf`）保持审批。
   - **代码现状（已查，2026-11-28）**：宿主其实已经有 root→Shizuku→App 身份链——`support/src/main/java/xin/dshaa/nativeapp/device/DeviceShell.kt`（`runElevated` / `runShizuku` / `runShizukuBytes` / `hasShizuku`）、`app/.../device/tools/TerminalTools.kt`（终端工具支持 `identity=shell/root/app`）、`ui/native-shell/.../permissions/PermissionCenter.kt`（Shizuku 四态 + 一键授权）。**但 AI 最常用的 `BashTool`（`core/tools/.../shell/BashTool.kt`）没有 identity 参数、也不经过 `DeviceShell`**，所以 AI 想跑 `pm`/`settings`/`am`/`cmd` 时要么换工具（`shell.exec` / 终端工具），要么手工套 `rish`——这就是「麻烦」的根。
   - 最小可行改法：给 `BashTool` 加 `identity`（默认 `app`，可选 `shell` / `root`），`shell`/`root` 时整条命令交给 `DeviceShell.runElevated` 一次性执行（保留 cwd/env/timeout），工具描述里写明「需要系统权限的命令加 identity=shell」；失败返回「需要 Shizuku 授权，去 设置→权限与能力」而不是裸 `Permission denied`。另一个选择是让整个终端会话以 shell 身份启动（proot 外层套 `su`/Shizuku），更省事但更危险，需用户拍板。
   - 先做：在真机上确认 Shizuku 是否在运行、是否已授权、AI 现在具体卡在哪一步（让用户给一条实际失败的命令与输出），再定方案。
2. **终端无法调用 root 权限**——需要支持有 root 的设备上用 `su` 执行：
   - **本测试机没有 root**：`id` 是 uid=2000(shell)，`/system/bin/su`、`/system/xbin/su`、`/sbin/su` 均不存在，`ro.debuggable=0`。需要用户提供一台已 root 的设备（或明确「只做代码路径、不做真机验证」）。
   - 设计方向：检测 `su`（`su -c id` 探针）→ 在 PTY 启动时可选以 root 运行（`su -c <proot 命令>` 或给 proot 加 `--root` 相关能力）→ 设置里加开关 + 失败回退；同理可提供 `sudo`/`su_exec` 给 AI 单条命令用。注意 `docs/196` 里 jniLibs/bash 的教训，别改 `liboperit_terminal_bash.so`/`libbash.so` 命名。
   - PR #7 明确**没有**动终端 Shizuku/Root（作者原话「按需求暂未改动，留待后续单独处理」）。

## 三、PR #7 里已知要修的 bug（合并后补丁，按严重度）

### P1-a Node 插件安装越权继承 config
- 位置：`app/src/main/java/xin/dshaa/nativeapp/node/NodePluginInstaller.kt`（安装时 `sameId` 那段，PR 把 `sameModule` 判断删了）。
- 现象：`sameId` 由「声明 id || module || 目录 meta.id」任一匹配即成立；随后 `if (!resetConfig) { (obj["config"])?.let { config = it } }` 不再要求 `module == installed.module`。恶意包只要声明成受害插件的 id，就能继承它保存的 `config`（常含 apiKey），紧接着旧目录还被 `deleteRecursively()`。
- 修法（最小）：config 继承恢复 `val sameModule = module == installed.module` 且仅 `sameModule` 时继承；目录清理也只在 `sameModule`（同 module 改名）时做，或干脆只删「同 module 且路径不同」的旧目录。

### P1-b `summarizeZip` 无总量上限（安装前 OOM）
- 位置：`core/plugins/src/main/java/xin/dshaa/core/plugins/PluginPackage.kt` → `summarizeZip`。
- 现象：每份清单最多 1MB、最多扫 5 万条，但没有**累计字节上限**、清单数量上限和压缩比检查；几 MB 的 zip（大量浅层 `x/package.json`）可在「选择归属」弹窗**之前**把堆打爆，且 `runCatching` 连 `OutOfMemoryError` 一起吞。
- 修法：加 `totalBytes`（建议 ≤8MB）、清单数量（≤32）、单条 1MB 上限对齐；保留最多 5 万条目扫描但**读了就计数**；`runCatching` 只捕 `Exception` 或单独处理 OOME。参照同文件 `read()` 的 64MB/200× 比例思路。

### P2-a `PluginClientEntry` 入口未归一化
- 位置：`core/plugins/.../PluginClientEntry.kt`（`dsh.package.json` 的 client 入口）。
- 现象：只 `removePrefix("./")` 就 `File(pluginDir, entry).isFile`，可声明 `../../other-plugin/x.js` 通过校验（真正读文件时 `ClientPluginWindowService` 的 canonical 检查兜住了，属纵深防御）。
- 修法：走 `PluginPackage.normalizePath` 并做 `canonicalFile` + `startsWith(pluginDir + sep)` 检查，越界直接判非法。

### P2-b Node 宿主 PATH / CA 信任根可被插件改写
- 位置：`app/.../node/NodeHostProcess.kt`。
- 现象：把 `files/toolchain/bin` 放在 PATH **首位**并继承 app 进程 PATH，还把 `files/toolchain/cacert.pem` 设为 `SSL_CERT_FILE`/`NODE_EXTRA_CA_CERTS`。`files/toolchain/` 是 app 私有但 `fs:any` 插件可写 → 可劫持后续 bash 命令、给全部 Node 插件换 HTTPS 信任根。
- 修法：PATH 只保留系统目录（`/system/bin:/system/xbin:/product/bin`）或把 toolchain 目录放末尾；CA 改用只读来源（随包 `assets/toolchain/cacert.pem` 复制到只读位置，或用 Node 自带 CA），不要指向插件可写目录。

### P2-c 视频热路径每帧解析 + 拷贝（性能）
- 位置：`thirdparty/shower/.../ShowerController.kt` → `rememberParameterSet` / `extractAnnexBNals`。
- 现象：每个视频帧都 `extractAnnexBNals`，并对每个 NAL `copyOfRange`（AVCC 还要整帧转换拷贝）；旧实现只扫到首个起始码。1080p30 每帧几百 KB 垃圾，和 PR 的「卡顿治理」目标相反。
- 修法：只在首帧/关键帧/参数集变化时解析，热路径只做「是否含 SPS/PPS/IDR」的轻量判断；缓存结果。

### P2-d 虚拟屏 `show()` 阻塞与全屏输入
- 位置：`ui/native-shell/.../device/shower/VirtualScreenOverlay.kt`。
- 现象：`show()` 用 `CountDownLatch.await(1500ms)` 等主线程，超时返回 false 但窗口随后可能仍加上 → `virtual_screen` 工具误报失败；全屏去掉 `FLAG_NOT_FOCUSABLE` 后只拦 BACK，其他物理键被窗口吞；退出全屏不 `clearFocus`。
- 修法：改挂起/回调语义（或失败后补偿 hide）；全屏只拦截需要转发的键，其余放行；退出时 `clearFocus`。

### P3（产品/体验，先和用户确认再动）
- `Backdrop` 默认改 `animated=false, withSheen=false`：所有未显式传参的调用方（含 `LiquidWall`）静默失去流动背景 → 液态玻璃卖点弱化，建议加开关或恢复默认。
- 顶栏 `dshTopBarSurface()` native/liquid 的 padding 顺序不一致（native 通栏到状态栏、liquid 整体下移约一个状态栏）。
- `MainActivity` 改 `selectShell(v.trim())` 后，插件壳选择值不匹配时不再回退 native（只弹 notice）。
- `ShowerController.lastIdr` 只在 destroy/重建时失效；分辨率/序列切换可能先重放旧 IDR（闪旧帧）。
- `ChatScreen` 的 `remember(messages)` key 是同一个 `SnapshotStateList` 实例；`import.meta` 替换只替每行第一处；入口模块不进 `__dshModuleCache`（`require('./index.js')` 会二次执行）。
- 死代码：`liquidEnter`、`inkReveal`、`threadEdgeFade` 实现还在但调用点被删。
