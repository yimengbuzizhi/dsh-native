## 一、用户要求与旧限制

用户要求「AI 并行」：A 会话正在生成时，切到 B 会话仍能发消息并得到回复，而不是被
「另一个会话正在生成，等它结束再发」挡住。

旧实现（`53c8846` 及之前）不是 UI 层随便挡的，而是有一整套单例假设：

1. `AppViewModel.activeTurn: LiveChat?` 全局只有一个；`startTurn()` / `send()` / `submit()` 都有
   `activeTurn != null && activeTurn.state !== state` 的互斥；
2. 所有引擎共用一个 `ToolContext`，其中：
   - `goalHost` 的当前 handle / activation，
   - `scheduleHost` 的当前 sessionId，
   - `jobOwner`（`bash run_in_background` / `job_*` 的归属），
   - `agents = RootAgentHost()`（`subagent` / `list_agents` / `send_message` 的父会话），
   - `planMode`（`exit_plan_mode`）
   全部在调用时读 `activeTurn` / 前台 `chat`。两条轮次并行时，A 的工具会认成 B 的会话；
3. `buildEngine(live)` 的 `systemPrompt` 用的是前台 `planState.selected()`，不是 `live.plan`；
   `jobNotices` / `nextSchedulePrompt` / `tickSchedules` 也读前台会话；
4. `approvalDeferred` / `questionDeferred` 全局各一个，后台轮次的审批会覆盖前台的那份。

所以只删 guard 会让工具上下文、通知、审批、计划模式串会话——HANDOFF 明确要求先看这些再动。

## 二、改法（最小可用并行）

### 2.1 每个 LiveChat 一份 ToolContext

`LiveChat` 新增 `val toolContext by lazy { buildToolContext(this) }`：

- 从基础 `toolContext.copy()` 共享 `registry / attachments / webSearchHost / jobs / workflowHost`；
- 覆盖成本会话自己的：`goalHost`（`live.handle` + `live.goalActivation`）、
  `scheduleHost`（`live.state.sessionId`）、`jobOwner`（`live.state.sessionId`）、
  `agents = RootAgentHost { live }`、`planMode`（`live.plan`）、`askUser`（`live`）；
- `state = mutableMapOf()`：todo 等工具状态按会话隔离；
- `cwd` 用当前工作区；工作区仍是全局的（会话本来就按工作区分组）。

`RootAgentHost` 从无参单例改成 `RootAgentHost(owner: () -> LiveChat?)`：`currentAgentId` /
fork seed 都取自己这条会话，不再取「最近在跑的那条」。

### 2.2 多轮次集合替代单槽

- `activeTurn: LiveChat?` → `activeTurns: LinkedHashSet<LiveChat>` + `lastActiveTurn`
  （最近启动、仍在跑；后台通知/停止兜底用）；
- `runningState: ChatSessionState?` → `runningStates: Set<ChatSessionState>`（Compose 状态，
  抽屉右侧转圈/橙点 `badgeFor()` 按会话 id 查）；
- `markRunning()` / `markStopped()` 统一维护集合与 Compose 状态；
- `stop()`：停**当前前台且正在跑**的那条；前台没在跑时停 `lastActiveTurn`。3 秒兜底
  `forceStopUi()` 只清这一条；
- `syncKeepAlive()` 看 `activeTurns.isNotEmpty()`（并行时前台服务不会提前停）。

### 2.3 引擎依赖改为绑定 live

`buildEngine(live)` 现在：

- `toolContext = live.toolContext`；
- `goals = { session -> goalStore(session, live.goalActivation) }`；
- `systemPrompt` 的 `planMode = live.plan.selected()`；
- `approval = { call -> awaitApproval(live, call) }`；
- `nextSchedulePrompt = { nextSchedulePrompt(live) }`、`tickSchedules = { tickSchedulesFor(live) }`；
- `jobNotices = { takeNoticesFor(live.state.sessionId) }`；
- `onPlanChanged = { syncPlanUiFor(live) }`。

`LiveChat` 新增自己的 `pendingSchedules`、`approvalDeferred`、`questionDeferred`；
`resolveApproval()` / `resolveQuestions()` 优先当前前台有挂起项的那条，再找其它在跑的会话。

### 2.4 入口放行

- `submit()` / `send()` 删除跨会话互斥提示；
- 同一会话仍串行（`state.streaming` + `live.job?.isActive`）；
- `startTurn()` 不再要求 `state` 是当前前台（提醒/通知可以在后台会话上起一轮），
  但同一会话只允许一条轮次。

## 四、限制 / 未验

> M77 时点的三条限制已由 **M78** 修掉（审批提示/跳转、大肥鱼按会话状态、后台根会话唤醒），
> 见 §五；这里保留原文并标注现状。

- **审批模式**：设备是 `approval_mode=auto`。`ask` 模式下后台轮次如果弹审批，会一直等，
  抽屉显示橙点（WAITING），切回该会话才能点允许/拒绝；这是有意行为，避免后台偷偷放行。
  → **M78**：前台聊天页顶部加横幅「「会话」正在等你点审批」+「切过去」，点一下跳到那条会话；
  卡片仍然只在该会话里点（§5.1）。
- **大肥鱼/悬浮窗**：`BigFish` 是进程级单状态，并行时后开始的轮次会覆盖前一条的状态文案；
  这是观感问题，不影响会话落盘。
  → **M78**：改成每会话一份快照 + 合并发布，前台/在跑的那条优先（§5.2）。
- **通知投递**：后台根会话的 job/子代理通知仍只在它被打开时投递（`wakeOwner` 只处理当前根会话）；
  本次没改这块。
  → **M78**：后台根会话也会被唤醒（§5.3），未打开过的会话仍是打开时补投。
- **同会话并行**：不支持，也不应该支持（工具结果/流式写入同一会话文件会乱序）。
- **子代理并行**：`RootAgentHost` 已按 live 绑定，但没有专门压测「两条会话同时各开子代理」。
- **工作区切换**：已存在的 LiveChat 保留创建时的工作区上下文；切工作区后新会话用新根。
- `:app:assembleDebug` 通过；`:core:engine:test` 本次代码未改 core，任务 UP-TO-DATE（此前 82/82）。

### 5.2 大肥鱼/客户端插件状态按会话分开

- `fish/BigFish.kt` 从「进程级单快照」改成**每会话一份**：`owners: LinkedHashMap<Any, FishSnapshot>`
  （键 = 该会话的 `ChatSessionState` 对象，同一条会话稳定；上限 8 份，超出丢最旧的非前台那份），
  本轮 token 也按会话累加。所有状态机入口加第一个参数 `owner: Any?`（`null` 只给
  `--es dsh_fish_demo` 调试通道用：直接写对外快照、不参与合并）。
- 对外 `BigFish.state` 是**合并结果**（`publish()`）：

  1. 前台会话在跑 → 发前台；
  2. 否则最近一条在跑的会话（THINKING/WORKING/WAITING）；
  3. 再否则最近一条完成脉冲（SUCCESS 2.4 秒）——挂件照旧播报；
  4. 最后退到前台会话 / 最新一条。

  `setForeground()` 由 `AppViewModel.attach()` 调；`forget()` 在草稿回收（`newChat`）时清。
- 客户端插件宿主（`ClientPluginWindowService`）继续 collect `BigFish.state` / 用 `sessionJson()`，
  协议字段不变，插件侧不用改。
- 真机（并行，approval=auto）：A 跑 `bash sleep 25`（`owner=@455aa10`）→ 切到 B 发
  「Reply with OK only.」→ B 1.1 秒结束；**紧接一条 publish 仍是 A 的 WORKING**：

  ```text

  00:00:59.091 DshFish: publish owner=@455aa10 state=WORKING            # A 执行命令
  00:01:20.354 DshTurn: turn start session=46b43bd4-… foreground=true   # B（切过去发的）
  00:01:21.465 DshTurn: turn end after 1111ms                           # B 结束
  00:01:21.466 DshFish: publish owner=@455aa10 state=WORKING            # ★ 仍是 A，没被 B 的 SUCCESS 盖掉
  00:01:24.149 DshFish: publish owner=@455aa10 state=THINKING           # A 继续
  00:01:25.365 DshTurn: turn end after 30021ms                          # A 自己结束
  00:01:25.366 DshFish: publish owner=@455aa10 state=SUCCESS
  ```

  截图 `110-11`（B 前台、A 还在跑）。收尾后用 `--es dsh_client_plugin @dsh-external/dsh-client-ui-pet`

### 5.3 后台根会话也会被通知唤醒

- `wakeOwner(owner)` 以前只认 `chat?.sessionId`（当前打开的那条），其余 owner 一律走
  `wakeChildAgent`（子代理续轮）；后台根会话的后台任务/子代理结算通知就只能等用户打开那条会话
  才补投。现在先 `liveById(owner)`（本进程打开过的会话都能对上）→ `maybeDeliverNoticesFor(它自己)`；
  对不上才走子代理分支。
- 真机：A 会话起 `bash run_in_background sleep 25` → 切到别的会话（App 甚至退到桌面）→ 25 秒后
  后台唤醒并跑完一轮：

  ```text
  00:00:12.160 DshTurn: notice wake session=b46c8546-… foreground=false notices=1
  00:00:12.182 DshTurn: turn start session=b46c8546-… foreground=false
  00:00:14.555 DshTurn: turn end after 2373ms
  ```

- 仍有限制：**只在本次进程里打开过**的会话才会被后台唤醒；从未打开过的会话，通知留在注册表里，
  等下次打开该会话时补投（不丢）。
