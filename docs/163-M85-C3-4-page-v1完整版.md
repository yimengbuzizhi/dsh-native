## 1. 做了什么

### 1.1 注册表搬进 `ui:shell-api` 并升级为统一页面表

`app/ui/shell/ShellPages.kt` 删除，新增 **`ui/shell-api/PageRegistry.kt`**：

| 类型 / 函数 | 作用 |
|---|---|
| `PageOrigin { Shell, Plugin }` | 页面来源 |
| `RegisteredPage` | 统一表项：`id/title/level/origin` + `pluginId/pluginName/routeId/pluginTarget/overridesShellPage` |
| `ShellPageRegistry.declared()` | 壳声明页（`NativeShells.pages()`） |
| `ShellPageRegistry.table(shellPages, pluginPages)` | **唯一合并点**：同 id 插件覆盖壳页；其余插件页追加为独立页（Primary） |
| `ShellPageRegistry.drawerPluginPages(...)` | 抽屉「插件页面」段：只列独立插件页（M84-K 语义） |
| `ShellPageRegistry.resolve(...)` | M84-G 路由解析：`pageId` 优先、`subId` 次之；返回插件项（含渲染目标） |
| `catalogMatch/unknownPluginScreens/duplicatePluginScreens/unownedPages` | 原来的校验函数，改为接收宿主内置插件元数据（`BuiltinPlugins` 仍留 app） |

`PluginPageEntry` 新增 `target: PluginPageTarget?`（record+route）：壳的 dispatch 直接把它交给宿主
页面槽 `NativeShellHostUi.PluginPage`，壳仍不 import `pluginui`/WebView。
`AppViewModel.pluginPageEntries()` 不再排除与内置页同名的 route（同 id 项由注册表标记
`overridesShellPage=true`）；`pluginPageFor()` 保留给未接注册表的老壳实现。

### 1.2 三个消费方全部改读注册表

| 位置 | 之前 | 现在 |
|---|---|---|
| `NativePageDispatch`（壳内路由） | `vm.pluginPageFor(pageId, subId)` 直接查插件 | `ShellPageRegistry.resolve(...)` → `RegisteredPage.pluginTarget` → `hostUi.PluginPage`（target 为空才回落 `pluginPageFor`） |
| `DshDrawer` 数据（`NativeShellRoot`） | `vm.pluginPageEntries()` 全量映射 | `ShellPageRegistry.drawerPluginPages(...)`（覆盖项不重复列） |
| 调试 dump（`AppViewModel.applyDebugPages`） | 只 dump 壳声明 22 页 | 同一张表；新增 `pluginPages[]`（`id/title/level/plugin/pluginName/overrides`），`pages[]` 仍是 22 页（M84-B 断言不变） |

渲染边界不变：壳页由壳自己的 dispatch `when` 画；插件整页由宿主 `pluginui` 的
`NativeShellHostUi.PluginPage` 画。注册表只决定「哪一项可见、谁覆盖谁」，不搬 UI 实现。
